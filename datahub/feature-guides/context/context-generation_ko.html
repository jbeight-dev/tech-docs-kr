    Context Generation

    기능 제공 범위: DataHub Cloud 전용 · 공개 베타

    정보: Context 애드온

    Context Generation은 DataHub Cloud Context 애드온에 포함됩니다.

    팀은 이미 분석 질문 대부분에 답해 왔습니다. 그 답은 웨어하우스 쿼리 기록, BI 도구, 시맨틱 모델에 있지만, 에이전트가 사용할 수 있는 문서에는 거의 없습니다. Context Generation은 이러한 분석 활동의 산출물을 Semantic Anchors라는 컨텍스트 문서로 바꿉니다. 각 문서는 사용할 테이블, 테이블의 연결 방식, 비즈니스에서 결과를 부르는 이름 등 팀이 반복되는 비즈니스 질문에 답하는 방법을 에이전트에게 보여 줍니다.

    직접 작성한 문서는 모두가 묻는 질문을 다룹니다. Context Generation은 모든 도메인에 걸쳐 드물게 나오는 다양한 질문(롱테일)을 다루므로, 전문가는 빈 페이지에서 시작하지 않고 초안을 다듬으면 됩니다.

    Context Generation 동작 방식

    1. 범위를 선택합니다. 도메인이나 데이터베이스 또는 스키마 집합 등을 선택합니다.
    2. DataHub가 해당 범위의 분석 활동을 읽습니다. 웨어하우스 쿼리 기록, Looker explore와 Snowflake 시맨틱 뷰 같은 BI 및 시맨틱 정의, DataHub가 이미 알고 있는 설명, 소유자, 사용량이 대상입니다. 메타데이터만 사용하며 테이블의 데이터는 절대 읽지 않습니다.
    3. 반복되는 패턴을 찾습니다. 팀이 반복해서 실행하는 분석을 찾고 일회성 쿼리는 제외합니다.
    4. 패턴별로 컨텍스트 문서를 작성합니다. 문서에는 패턴이 답하는 비즈니스 질문과 그 바탕이 되는 쿼리의 일반적인 형태를 설명합니다.
    5. 문서를 게시합니다. 자동으로 또는 검토 후에 게시하며, 데이터와 사용량이 변경되면 새로 고칩니다.

    스크린샷: Settings > Context에서 Context Generation 작업을 구성하는 화면.

    Context Generation 설정하기

    Context Generation은 작업(job)으로 실행되며, Settings > Context에서 관리합니다. 작업을 설정하려면 Manage Platform Settings 권한이 필요합니다. 각 작업에 대해 다음을 선택합니다.

    • 도메인이나 특정 데이터베이스 또는 스키마 같은 포함할 범위
    • 문서를 보낼 위치: 도메인 에이전트가 볼 수 있도록 할당할 도메인과, 선택적으로 Documents의 폴더
    • 문서 게시 방식: 자동 또는 선택한 검토자의 승인 후
    • 작업 실행 빈도: 데이터와 사용량 변화에 맞춰 컨텍스트를 유지합니다

    하나의 도메인으로 시작해 eval로 결과를 확인한 뒤 확장하세요. Build a Data Agent 가이드의 3단계: 컨텍스트 생성을 참고하세요.

    문서 게시와 검증

    생성된 문서는 자동으로 게시하고 eval로 검증하기를 권장합니다. 한 번의 실행으로 많은 문서가 생성될 수 있으며, eval을 사용하면 문서가 도움이 되는지 빠르게 알 수 있습니다. eval 결과가 나빠지면 그 원인이 되는 문서를 편집하거나 게시 취소하세요. 민감한 도메인에서는 게시 전에 승인을 요구할 수 있습니다. 컨텍스트 변경 사항 검토를 참고하세요.

    생성된 문서 편집하기

    생성된 문서는 자유롭게 편집할 수 있습니다. 문서를 편집하면 Context Generation에서 분리됩니다. 이후 실행에서 덮어쓰지 않고, 정리 중에 제거되지 않으며, 에이전트는 편집한 버전을 사용합니다. 아무도 편집하지 않은 문서는 데이터와 사용량이 변경되면 계속 업데이트됩니다.

    시작하기 전에

    Context Generation은 웨어하우스 쿼리 기록에 의존합니다. 웨어하우스의 데이터 소스가 분석 작업을 대표하는 기간 동안의 쿼리와 쿼리 사용량 통계를 수집하는지 확인하세요. BI 도구와 dbt를 연결하면 생성된 문서의 비즈니스 용어가 개선됩니다.

    참고 recipe

    Context Generation은 웨어하우스 수집이 내보내는 다음 두 가지에 의존합니다.

    • 쿼리 엔터티(queryProperties): SQL 텍스트와 SQL이 읽고 쓰는 데이터셋
    • 쿼리 사용량 통계(queryUsageStatistics): 각 쿼리의 실행 빈도

    분석 작업을 대표하는 기간을 포함하도록 start_time을 설정하세요. CLI 버전 1.6.0.9 이상을 사용합니다. UI 수집에서는 Advanced Settings에서 설정합니다.

    Snowflake 
    source:
  type: snowflake
  config:
    account_id: "<account>"
    warehouse: "<warehouse>"
    username: "${SNOWFLAKE_USER}"
    password: "${SNOWFLAKE_PASS}"
    role: datahub_role
    start_time: "-7 days"

    include_queries: true # default true -> Query entities
    include_query_usage_statistics: true # default true -> queryUsageStatistics
    include_operational_stats: false # default true; off = no DDL/write operations

    Snowflake Enterprise Edition과 IMPORTED PRIVILEGES ON DATABASE SNOWFLAKE가 필요합니다. 쿼리 추출은 ACCOUNT_USAGE.QUERY_HISTORY와 ACCESS_HISTORY를 읽으며, 이 데이터는 실시간보다 약 45분에서 3시간 늦습니다.

    Databricks 
    source:
  type: unity-catalog
  config:
    workspace_url: https://<workspace>.cloud.databricks.com
    token: "${DATABRICKS_TOKEN}"
    warehouse_id: "<sql_warehouse_id>" # recommended
    start_time: "-7 days"

    include_usage_statistics: true # default true -> runs query extraction
    include_queries: true # default true -> Query entities
    include_query_usage_statistics: true # default true -> queryUsageStatistics
    include_operational_stats: false # default true; off = no DDL/write operations

    서비스 주체에는 웨어하우스에 대한 CAN_USE와 system.query.history 및 system.access.table_lineage에 대한 SELECT가 필요합니다. 시스템 테이블은 약 365일의 기록을 보관하고, REST API 폴백은 약 30일을 보관합니다.

    BigQuery 
    source:
  type: bigquery
  config:
    project_ids: ["<project>"]
    start_time: "-7 days"

    include_queries: true # default true -> Query entities
    include_query_usage_statistics: true # default true -> queryUsageStatistics

    # Query extraction runs only if lineage or usage is on (both default true)
    include_table_lineage: true
    include_usage_statistics: true

    usage:
      include_operational_stats: false # nested under usage on BigQuery
    Redshift 
    source:
  type: redshift
  config:
    host_port: <cluster>.<region>.redshift.amazonaws.com:5439
    database: <database>
    username: datahub
    password: "${REDSHIFT_PASS}"
    email_domain: example.com # required when include_usage_statistics is on
    start_time: "-7 days"

    lineage_generate_queries: true # default true -> Query entities
    include_usage_statistics: true # default FALSE -> enables the usage path
    include_query_usage_statistics: true # sub-flag of include_usage_statistics
    include_operational_stats: false # default true; off = no DDL/write operations

    Redshift는 쿼리 기록을 며칠(보통 2~5일)만 보관하므로, 이보다 오래된 start_time은 아무것도 반환하지 않습니다. 데이터베이스마다 별도의 recipe가 필요하며, 수집 사용자가 다른 사용자의 쿼리를 읽으려면 SYSLOG ACCESS UNRESTRICTED가 필요합니다.

    API 접근

    DataHub GraphQL API로 작업 생성과 생성된 문서 작업 등 프로그래밍 방식으로 Context Generation을 관리할 수도 있습니다.

    FAQ

    Context Generation이 데이터를 읽나요? 아니요. 쿼리 기록, 스키마, BI 및 시맨틱 정의처럼 DataHub가 이미 수집한 메타데이터로 동작합니다. 테이블의 데이터는 절대 읽지 않으며, 원시 쿼리 로그는 언어 모델로 전송되지 않습니다.

    Context Generation에 AI 크레딧이 사용되나요? 예. eval, Ask DataHub, 커스텀 에이전트와 마찬가지로 Context Generation 실행에도 AI 크레딧이 소비됩니다. 필요한 도메인으로 작업 범위를 지정하면 사용량을 집중할 수 있습니다.

    실행에서 예상보다 적은 문서가 생성되었습니다. Context Generation에는 반복되는 쿼리 패턴이 필요합니다. 범위 내 테이블의 쿼리 기록이 충분히 긴 기간에 걸쳐 수집되고 있는지 확인하세요. Settings > Context의 어시스턴트가 실행 진단을 도울 수 있습니다.
