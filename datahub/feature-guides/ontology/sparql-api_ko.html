    SPARQL을 사용한 고급 쿼리

    기능 제공 범위: DataHub Cloud 전용 · 비공개 베타

    traverse API는 탐색을 매개변수로 표현합니다. 여기서 시작해 이 유형들을 따라 이만큼의 홉을 이동한다는 식입니다. 대부분의 질문은 이것으로 해결되지만, 여러 관계에 걸친 조인, 대안, 폐포, 중간 노드의 조건처럼 특정한 형태가 필요한 질문은 해결되지 않습니다.

    이러한 질문을 위해 DataHub는 SPARQL을 지원합니다.

    DataHub Cloud v2.2.1 이상에서 사용할 수 있습니다.

    SPARQL 지원의 성격

    DataHub는 SPARQL을 관계 그래프에 대한 쿼리 언어로 사용합니다. 쿼리는 실시간 메타데이터를 대상으로 실행되므로 동기화하거나 최신 상태로 유지할 것이 없습니다.

    DataHub는 완전한 RDF 데이터베이스가 아닙니다. 트리플을 저장하지 않으며 SPARQL의 일부만 지원합니다. 아래의 지원되는 범위를 참고하세요. 그 이상이 필요하면 그래프를 내보내 전용 트리플 스토어에 로드하세요.

    권한 부여

    호출자에게 RELATIONSHIP READ 권한이 필요합니다. 뷰 기반 접근 제어는 탐색이 바인딩을 생성할 때 적용됩니다. 엣지는 호출자가 볼 수 있는 끝점 사이에서만, 경로는 경로상의 모든 엔터티를 볼 수 있을 때만 해석됩니다. 따라서 리프 위의 어떤 필터나 표현식도 호출자가 볼 수 없는 엔터티를 관찰할 수 없습니다.

    쿼리 실행하기

    엔드포인트는 /openapi/v3/sparql이며, 세 가지 표준 SPARQL 프로토콜 형식을 허용합니다.

    # GET with ?query=
curl -H "Authorization: Bearer $DATAHUB_TOKEN" -G "$DATAHUB_GMS_URL/openapi/v3/sparql" \
  --data-urlencode 'query=SELECT ?t WHERE { ?t <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr> }'

# POST with Content-Type: application/sparql-query
curl -H "Authorization: Bearer $DATAHUB_TOKEN" -X POST "$DATAHUB_GMS_URL/openapi/v3/sparql" \
  -H 'Content-Type: application/sparql-query' \
  --data 'SELECT ?t WHERE { ?t <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr> }'

# POST as a form parameter
curl -H "Authorization: Bearer $DATAHUB_TOKEN" -X POST "$DATAHUB_GMS_URL/openapi/v3/sparql" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'query=SELECT ?t WHERE { ... }'

    어휘

    DataHub URN이 곧 IRI입니다. 엔터티는 URN이고, 술어는 관계 유형 URN입니다.

    <urn:li:glossaryTerm:customer>            # a glossary term
<urn:li:relationshipType:governedBy>      # a custom relationship type

    내장 관계에도 관계 유형 URN이 있습니다. 스키마 내보내기로 찾을 수 있습니다.

    쿼리 형식과 출력

    형식 반환 협상 가능한 형식
    SELECT 바인딩 application/sparql-results+json(기본값), XML, CSV, TSV
    ASK 불리언 SELECT와 동일
    CONSTRUCT RDF 그래프 Turtle(기본값), JSON-LD, N-Triples, RDF/XML

    출력 계열은 쿼리 형식을 따르며, 정확한 직렬화 형식은 Accept 헤더로 협상합니다.

    예시

    GDPR이 적용되는 모든 항목:

    SELECT ?term WHERE {
  ?term <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr>
}

    전이적 폐포 탐색으로, 깊이와 관계없이 Customer 아래의 모든 개념을 찾습니다. 여기서 rdfs_subClassOf는 RDF 수집 소스가 rdfs:subClassOf 공리를 기록하는 잘 알려진 관계 유형이며, 다른 전이적 관계 유형도 같은 방식으로 동작합니다.

    SELECT ?concept WHERE {
  ?concept <urn:li:relationshipType:rdfs_subClassOf>+ <urn:li:glossaryTerm:customer>
}

    두 관계에 걸친 조인으로, 규제 대상 개념에서 파생된 용어가 적용되는 자산을 찾습니다.

    SELECT ?asset WHERE {
  ?mid   <urn:li:relationshipType:governedBy>  <urn:li:glossaryTerm:gdpr> .
  ?asset <urn:li:relationshipType:derivedFrom>+ ?mid
}

    여러 관계 유형에 대한 대안:

    SELECT ?asset WHERE {
  ?asset (<urn:li:relationshipType:governedBy>|<urn:li:relationshipType:derivedFrom>)+ <urn:li:glossaryTerm:pii>
}

    집계한 다음 바인딩 대신 그래프를 내보냅니다.

    SELECT (COUNT(?asset) AS ?count) WHERE {
  ?asset <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr>
}

    CONSTRUCT { ?asset <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr> }
WHERE     { ?asset <urn:li:relationshipType:governedBy> <urn:li:glossaryTerm:gdpr> }

    함의

    기본적으로 쿼리는 단순 함의(simple entailment)로 실행됩니다. 단일 홉 패턴은 단일 홉으로 유지되고 아무것도 추론하지 않습니다. 표준 어휘 매핑과 전이성은 옵트인 방식이므로, 쿼리가 요청한 것보다 많은 결과를 조용히 반환하는 일은 없습니다.

    선언된 관계 의미에 RDFS 스타일 추론을 활성화하려면 X-DataHub-SPARQL-Entailment: rdfs 헤더(또는 동등한 ?entailment=rdfs 쿼리 매개변수)를 보냅니다.

    RDFS 체제에서는 다음이 적용됩니다.

    • 관계 유형의 동등 속성이 해석됩니다. skos:broader 같은 표준 술어를 쿼리하면 이를 동등 속성으로 선언한 모든 관계 유형에 저장된 엣지에 도달합니다.
    • 전이적 관계는 단일 홉 질문에 전체 체인으로 답합니다.
    • 클래스 계층 앵커는 rdfs:subClassOf와 owl:sameAs / owl:equivalentClass 엣지로 확장됩니다.

    동등 속성과 전이성을 선언하는 방법은 커스텀 관계 추가하기에서 다룹니다.

    동등 속성으로 쿼리하기

    skos:broader를 동등 속성으로 선언한 커스텀 관계 유형 broaderThan이 있다고 가정해 보겠습니다. 엣지는 여전히 urn:li:relationshipType:broaderThan에 저장되며, 이 URN을 쿼리하면 함의 여부와 관계없이 동작합니다.

    curl -H "Authorization: Bearer $DATAHUB_TOKEN" \
     -G "$DATAHUB_GMS_URL/openapi/v3/sparql" \
     --data-urlencode 'query=SELECT ?broader WHERE {
       <urn:li:glossaryTerm:individualCustomer> <urn:li:relationshipType:broaderThan> ?broader
     }'

    {
  "head": { "vars": ["broader"] },
  "results": {
    "bindings": [
      { "broader": { "type": "uri", "value": "urn:li:glossaryTerm:customer" } }
    ]
  }
}

    함의 헤더를 사용하면 DataHub에서 관계를 무엇이라고 부르는지 몰라도 표준 SKOS로 같은 질문을 할 수 있습니다.

    curl -H "Authorization: Bearer $DATAHUB_TOKEN" \
     -H 'X-DataHub-SPARQL-Entailment: rdfs' \
     -G "$DATAHUB_GMS_URL/openapi/v3/sparql" \
     --data-urlencode 'query=PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
     SELECT ?broader WHERE {
       <urn:li:glossaryTerm:individualCustomer> skos:broader ?broader
     }'

    이 쿼리는 같은 바인딩을 반환합니다. 헤더를 제거하면 아무것도 반환하지 않습니다.

    { "head": { "vars": ["broader"] }, "results": { "bindings": [] } }

    이 빈 결과가 바로 옵트인의 핵심입니다. skos:broader에서 관계 유형으로의 매핑은 요청할 때만 적용되므로, 쿼리가 지정하지 않은 엣지를 조용히 가져오는 일은 없습니다.

    덕분에 표준 기반 도구가 자체 어휘에 대해 동작합니다. SKOS를 아는 클라이언트는 관계 이름이 broaderThan이라는 사실을 몰라도 그래프를 쿼리할 수 있습니다.

    지원되는 범위

    컴파일러는 제한된 그래프 탐색에 매핑할 수 있는 쿼리에 답하고, 매핑할 수 없는 쿼리는 조용히 부분 답변을 내지 않고 명확한 501로 거부합니다.

    지원: SELECT, ASK, CONSTRUCT, 기본 그래프 패턴, FILTER, BIND, VALUES, OPTIONAL, UNION, DISTINCT, ORDER BY, LIMIT/OFFSET, 집계, +, *, ?, 역방향(^), 단순 술어에 대한 대안((a|b)+), 제한된 반복(p{0,m}, p{1,m})을 사용하는 속성 경로.

    미지원:

    미지원 항목 대신 할 일
    시퀀스 경로(p1/p2) 명명된 중간 변수로 트리플 패턴을 명시적으로 작성합니다.
    앵커가 없는 위치의 변수 술어 술어를 IRI에 바인딩합니다.
    앵커가 없는 패턴과 앵커가 없는 전이적 폐포 한쪽 끝점을 IRI에 바인딩하거나 다른 패턴으로 바인딩합니다.
    정방향과 역방향을 섞은 대안(a|^b) UNION으로 나눕니다.
    최솟값이 1보다 큰 제한된 반복(p{2,5}) p{0,m} 또는 p{1,m}을 사용합니다.
    명명된 그래프(GRAPH), 쿼드, SERVICE 페더레이션 해당 없음. 그래프는 하나입니다.
    DESCRIBE, 업데이트(INSERT/DELETE) 엔터티 및 관계 API로 메타데이터를 읽고 씁니다.

    꼭 익혀야 할 규칙은 앵커링입니다. 모든 패턴에는 바인딩된 IRI 끝점이나 다른 패턴으로 바인딩된 변수가 필요합니다. 전체 그래프에 대한 ?s ?p ?o는 DataHub가 효율적으로 답할 수 없는 쿼리이므로 시도하지 않고 거부합니다.

    오류 코드

    코드 의미
    400 유효한 SPARQL 쿼리가 아닙니다.
    501 유효한 SPARQL이지만 지원 범위를 벗어납니다. 메시지에 해당 구문이 표시됩니다.

    엔진의 한도를 초과하는 쿼리(너무 많은 엣지에 대한 앵커 없는 스캔, 중간 집합이 폭증하는 조인, 너무 큰 클래스 계층 확장, 탐색 시간 초과에 도달한 탐색)도 전체 그래프로 오해할 수 있는 부분 결과를 반환하지 않고 설명 메시지와 함께 거부합니다.

    그래프 내보내기

    내보내기는 관계 유형과 엔터티 간 엣지의 두 부분으로 진행됩니다.

    1. 관계 유형. traverse API가 탐색에 사용하는 것과 같은 스키마 내보내기입니다. 모든 관계 유형을 RDF 온톨로지로 반환합니다.

    curl -H "Authorization: Bearer $DATAHUB_TOKEN" \
  "$DATAHUB_GMS_URL/openapi/v3/relationship/schema?format=n-triples" > schema.nt

    2. 엣지. 변수 술어를 사용하는 CONSTRUCT는 모든 관계 유형을 내보냅니다.

    curl -H "Authorization: Bearer $DATAHUB_TOKEN" \
     -H "Accept: application/n-triples" \
     -G "$DATAHUB_GMS_URL/openapi/v3/sparql" \
     --data-urlencode 'query=CONSTRUCT { ?s ?p ?o } WHERE { ?s ?p ?o }' > edges.nt

    schema.nt와 edges.nt를 이어 붙이면 원하는 도구에 로드할 수 있는 독립적인 RDF 그래프가 됩니다.

    내보내기가 너무 큰 경우

    단일 스캔은 100,000개 엣지로 제한됩니다. 이를 초과하면 조용히 잘리지 않고 쿼리가 501로 거부됩니다.

    {
  "error": "scan exceeds the supported result cap of 100000; add a bound endpoint or narrow the query."
}

    제한은 내보내기별이 아니라 쿼리별이므로, 엣지가 100,000개를 넘는 그래프는 나눠서 내보내야 합니다. 그래프를 가장 고르게 나누는 축을 따라 범위를 좁히세요.

    # One relationship type at a time
--data-urlencode 'query=CONSTRUCT { ?s <urn:li:relationshipType:governedBy> ?o }
                        WHERE     { ?s <urn:li:relationshipType:governedBy> ?o }'

# Everything attached to one entity, across all relationship types
--data-urlencode 'query=CONSTRUCT { <urn:li:glossaryTerm:customer> ?p ?o }
                        WHERE     { <urn:li:glossaryTerm:customer> ?p ?o }'

    각 결과를 같은 파일에 덧붙입니다. 이 엔드포인트에는 페이징이 없으므로, 단독으로 제한을 초과하는 관계 유형은 앵커링으로 나눠야 합니다.

    이 기능 활성화하기

    인스턴스에서 활성화하려면 DataHub 담당자에게 문의하세요.

    자체 관리 배포에서는 GMS에 플래그를 설정하고 재시작합니다.

    SPARQL_API_ENABLED=true

    또는 Helm을 사용합니다.

    datahub-gms:
  sparqlApiEnabled: true
