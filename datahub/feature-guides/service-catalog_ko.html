    DataHub Service Catalog 소개

    기능 제공 범위: DataHub Cloud 전용

    DataHub Cloud v2.1에 도입된 Service Catalog는 스택의 소프트웨어 계층을 타입이 지정되고 거버넌스가 적용되는 엔터티로 DataHub에 가져와, 해당 시스템이 생성하는 데이터 바로 옆에 둡니다. 리포지토리는 서비스를 빌드하고, 서비스는 API를 노출하며, 애플리케이션은 이 API를 호출하고, API는 데이터셋을 생성하고 소비합니다. 서비스는 REST, GraphQL, gRPC, MCP 서비스라는 실제 모습 그대로 모델링되며, 소유자가 지정되고, 버전이 관리되고, 상태가 점검되고, 모든 다운스트림과 연결됩니다.

    이로써 오랜 격차가 해소됩니다. 시스템에 대한 엔지니어링 관점과 비즈니스 및 데이터 관점이 이제 하나의 연결된 그래프에 있으므로, 장애, 스키마 변경, 데이터 의존성을 소스 코드에서 대시보드나 AI 에이전트까지 추적할 수 있습니다.

    개념

    Service Catalog는 소프트웨어에서 데이터에 이르는 수명 주기를 모델링하는 네 가지 엔터티 유형을 도입합니다.

    엔터티 나타내는 대상
    Repository 소스 코드 리포지토리(GitHub, GitLab, 내부 SCM)입니다. 시작 노드로, 서비스, API, 앱을 빌드합니다.
    Service 연결 세부 정보와 수명 주기 단계가 있는 실행 중인 서비스(REST, GraphQL, gRPC, MCP 서버)입니다.
    API 타입이 지정된 시그니처가 있는 호출 가능한 단일 명명 작업(엔드포인트, gRPC 메서드, GraphQL 필드, MCP 도구)입니다.
    Application API를 호출하고 데이터를 생성하는 비즈니스 수준 시스템으로, 엔지니어링 관점과 데이터 관점을 잇는 다리입니다.

    이들은 하나의 리니지 축으로 연결되며, 데이터셋, 대시보드, AI 에이전트 등 모든 다운스트림이 같은 그래프에 연결됩니다.

    repository ──builds──▶ service ──exposes──▶ api ──produces/consumes──▶ dataset ──▶ dashboard
                                             ▲
                        application ──calls──┘   aiAgent ──invokes──┘

    설정, 사전 요구 사항, 권한

    서비스, API, 리포지토리, 애플리케이션은 다른 자산을 카탈로그화할 때와 마찬가지로 수집을 통해 채우거나 SDK/API로 직접 내보냅니다. OpenAPI 사양에서 REST 서비스를 바로 수집하는 방법을 포함해 API 튜토리얼을 참고하세요. 이들을 탐색하고 관리하려면 사용자에게 표준 엔터티 권한이 있어야 합니다.

    • View Entity Page: 서비스, API, 리포지토리 프로필을 찾아 열 수 있습니다.
    • Edit Entity(및 소유권, 태그, 용어집 용어, 문서 관련 하위 권한): 내용을 보강할 수 있습니다.

    조직에서 Service Catalog를 활성화하려면 DataHub 담당자에게 문의하세요.

    Service Catalog 사용하기

    서비스 찾기

    서비스는 데이터 바로 옆, DataHub에 있습니다. 서비스로 필터링한 검색 한 번이면 REST, GraphQL, gRPC, MCP 서버까지 모든 항목이 실제 모습 그대로 반환되며, 각각 타입이 지정되고 소유자가 있으며 상태가 점검됩니다. sub-type(REST/GraphQL/gRPC/MCP), domain, owner, health 검색 필터로 원하는 시스템을 좁힐 수 있습니다.

    서비스

    Order Entry API 같은 서비스를 열면 Service 프로필을 볼 수 있습니다. 한 화면에서 서비스의 엔드포인트, 계약, 프로덕션 수명 주기 단계, 소유 팀 등 서비스를 신뢰하고 의존하는 데 필요한 모든 정보를 얻습니다.

    MCP 서버도 하위 유형이 MCP인 Service로 여기에 카탈로그화되며 실제 연결 세부 정보를 포함합니다. 서버, 서버가 노출하는 도구(API), 도구를 호출하는 에이전트가 모두 같은 그래프에 있습니다.

    참고: Service(카탈로그 엔터티)와 DataHub MCP Server의 차이

    이 페이지는 외부 서비스와 MCP 서버를 메타데이터 엔터티로 카탈로그화하는 방법을 다룹니다. AI 에이전트가 카탈로그를 쿼리할 수 있도록 DataHub 자체를 MCP 서버로 노출하는 DataHub MCP Server와는 다릅니다.

    API와 엔드포인트

    서비스가 노출하는 모든 작업은 별도의 엔터티로 모델링됩니다. Place Order 같은 엔드포인트에는 필수 입력과 타입이 지정된 출력으로 이루어진 타입 지정 시그니처가 있으며, 팀이 데이터셋에 이미 사용 중인 것과 같은 풍부한 스키마 뷰로 렌더링됩니다. 그 결과 REST 경로, gRPC 메서드, GraphQL 필드, MCP 도구 등 실행하는 모든 엔드포인트에 강력한 타입의 검색 가능한 계약이 생깁니다.

    소프트웨어에서 데이터까지의 체인

    이들을 별개의 엔터티로 모델링하면 그 사이의 체인이 명확해집니다. payments 리포지토리가 Order Entry 서비스를 빌드하고, 서비스가 엔드포인트를 노출합니다. 리포지토리에서 서비스, 엔드포인트로 이어지는 구조가 실제 시스템의 동작 방식 그대로 중첩됩니다. 각 홉은 설명에 묻힌 불투명한 문자열이 아니라 타입이 지정된 그래프 엣지입니다.

    애플리케이션

    비즈니스 관점으로 시야를 넓혀 보겠습니다. Commerce 도메인의 Checkout 같은 Application에는 소유자와 문서가 있고, 호출하는 API와 생성하는 데이터에 연결됩니다. 비즈니스 관점과 엔지니어링 관점이 하나의 같은 그래프가 됩니다.

    참고: Applications 기능과의 관계

    Service Catalog는 비즈니스 목적별로 자산을 묶는 데 사용하는 것과 같은 Application 엔터티를 재사용합니다. Service Catalog에서 Applications에는 API 호출과 데이터 생성 관계가 추가되므로, Application 프로필에 의존하는 서비스가 표시됩니다.

    계약

    서비스의 계약은 위키 링크가 아니라 카탈로그에서 바로 버전 관리되는 전체 사양입니다. REST 서비스에서는 모든 경로와 스키마를 포함한 완전한 OpenAPI 문서이고, MCP 서버에서는 입력과 출력을 JSON Schema로 표현한 실시간 도구 목록입니다. 개발자, 파트너, AI 에이전트를 위한 권위 있는 단일 사양이 서비스와 함께 동기화되고 버전 관리됩니다.

    영향 분석

    서비스, API, 애플리케이션, 에이전트가 하나의 그래프를 공유하므로 영향 분석이 이 모두에 걸쳐 수행됩니다. Place Order 엔드포인트에 의존하는 자산을 물으면, 데이터에 이미 사용 중인 같은 리니지 뷰에서 서비스, 앱, AI 에이전트에 걸쳐 Checkout 애플리케이션과 FX Risk Scoring agent 같은 답을 바로 얻을 수 있습니다.

    인시던트와 상태

    서비스 상태는 카탈로그의 나머지 부분과 같은 인시던트 시스템을 따릅니다. Auction Service에 우선순위가 높은 활성 인시던트가 있으면 보는 즉시 배지에 unhealthy로 표시됩니다. Incidents 탭을 열면 무엇이 고장 났고, 얼마나 심각하며, 누가 처리 중인지 전체 내용을 볼 수 있습니다.

    OAuth Authorization Servers

    DataHub나 에이전트가 외부 API를 호출해야 할 때 OAuth Authorization Server 엔터티는 토큰의 출처를 모델링합니다. 권한 부여 서버를 카탈로그화하면 자격 증명 발급 단계가 구성 안에 숨겨지지 않고 드러나며 거버넌스가 적용됩니다.

    FAQ 및 문제 해결

    Service는 Dataset과 어떻게 다른가요?

    Dataset은 표 형식 데이터를 모델링하며 컬럼, 스키마, 쿼리, 통계가 있습니다. Service는 실행 중인 소프트웨어를 모델링하며 엔드포인트, 계약, 수명 주기 단계, 연결 세부 정보가 있습니다. Service Catalog 이전에는 팀이 서비스를 스키마 없는 데이터셋에 억지로 넣는 경우가 많았습니다. Service로 모델링하면 적절한 프로필, 타입이 지정된 API 시그니처, 실제 그래프 엣지를 갖게 됩니다.

    Services를 사용하려면 리포지토리를 카탈로그화해야 하나요?

    아니요. 각 엔터티는 독립적으로 유용합니다. 리포지토리는 체인(리포지토리 → 서비스 → API)의 시작 노드를 추가하지만, 서비스와 API만 카탈로그화하고 리포지토리는 나중에 추가할 수 있습니다.

    AI 에이전트가 API에 의존할 수 있나요?

    예. API가 공유 엔터티인 핵심 이유입니다. Agent Registry를 참고하세요. 에이전트의 도구는 API 엔터티이므로 "어떤 에이전트가 이 엔드포인트를 호출하는가"를 같은 영향 분석 뷰로 답할 수 있습니다.

    관련 기능

    • Agent Registry — AI 에이전트, 스킬, 에이전트가 호출하는 API
    • Applications — 비즈니스 목적별 자산 그룹화
    • DataHub MCP Server — AI 에이전트를 위한 MCP 서버로서의 DataHub
    • Lineage — 종단 간 의존성 추적과 영향 분석
    • Incidents — 카탈로그 전반의 상태 및 인시던트 관리
