    Agent 사람 상호작용(HITL): 2단계 일시 중단과 복구

    상태: 초안(P1 구현 완료) 관련: issue #1173(MCP 도구 사람 승인)

    0. 범위: 도구 승인만이 아닌 범용 사람 상호작용

    "Agent가 멈춰서 사람을 기다린다"에는 여러 형태가 있으며, 이 설계는 이를 하나의 모델로 통일합니다. 바로 상호작용 요청(prompt)입니다. 상호작용 요청에는 유형(kind), 요청 페이로드(request), 사용자 응답(response)이 있습니다. 범용 코어 internal/agent/hitl.Broker가 영속화, 대기, 복제본 간 전달, 일시 중단과 복구를 맡고, 각 유형은 페이로드 구조, 응답 검증, 프런트엔드 카드만 제공합니다.

    kind시나리오응답일시 중단 가능(suspendable)
    tool_approvalMCP 도구 실행 전 승인승인/거부, 수정한 파라미터, 이유예
    mcp_oauthMCP 서비스가 사용자의 OAuth 권한 부여를 먼저 요구권한 부여함/포기예
    ask_user(계획)Agent가 사용자에게 먼저 질문하고, 팝업이나 양식으로 답을 받음질문의 schema에 따라 작성예
    MCP elicitation(계획)MCP 서버가 도구 호출 도중에 사용자에게 입력을 요청elicitation schema에 따름아니요
    브라우저 사람 개입(계획)로그인, 캡차 등 사람이 브라우저에서 조작해야 하는 경우완료/포기아니요

    일시 중단 가능의 경계: 상호작용이 외부 호출 전에 일어나면(승인, OAuth, 질문) 실행을 안전하게 DB에 저장하고 끝낸 뒤 나중에 스냅숏에서 복구할 수 있습니다. 상호작용이 외부 호출 도중에 일어나면(elicitation 동안 MCP 세션과 도구 호출이 모두 열려 있음, 브라우저 개입은 복제본의 연결에 의존) 실행 상태를 직렬화할 수 없어 메모리에서 짧게 기다릴 수밖에 없고, 타임아웃이 나면 실패로 처리합니다. 레코드의 suspendable 표시는 요청한 쪽이 채우며, Broker는 이를 보고 짧은 대기가 끝났을 때 일시 중단할지 닫을지를 정합니다.

    아래에서는 도구 승인을 중심으로 흐름을 설명합니다. 일시 중단 가능한 다른 유형도 완전히 같은 경로를 따르며, "복구할 때 응답을 막혀 있던 호출에 어떻게 넘기는가"만 다릅니다(6.1의 PreDecided 참고).

    1. 배경과 목표

    현재 approval.Gate.RequestAndWait는 동기 블로킹 방식의 승인입니다. Agent를 실행하는 goroutine이 그 자리에서 기다리고, 프로세스 메모리에 전체 ReAct 상태가 남아 있으며, 대기 상한은 기본 10분(tool_approval_timeout_seconds)입니다. 여기에는 네 가지 한계가 있습니다.

    1. 타임아웃은 goroutine 누수를 막는 안전장치일 뿐이라 "다음 날 승인"을 지원할 수 없습니다.
    2. waiter가 프로세스 메모리에만 있어, 배포, OOM, Pod 스케줄링이 일어나면 승인 대기 상태가 모두 사라집니다.
    3. AgentSteps는 턴이 끝날 때 handleComplete만 DB에 쓰므로, 대기 중 프로세스가 죽으면 그 턴에서 이미 끝낸 단계를 모두 잃습니다.
    4. 대기 중에는 세션이 계속 "실행 중" 상태입니다.

    목표:

    • 사용자가 바로 옆에 있을 때의 경험은 그대로 둡니다. 짧은 시간 동안은 여전히 메모리에서 기다리며 추가 지연이 없습니다.
    • 짧은 대기 임계값을 넘기면 실행 상태를 영속화하고 이번 실행을 끝내 goroutine과 세션 점유를 풀어 줍니다.
    • 사용자가 (만료 시각 전) 언제든 승인하거나 거부하면, 어느 복제본이든 새 실행을 시작해 중단된 그 턴을 이어 실행한 뒤 ReAct 루프를 계속하고, 출력은 같은 어시스턴트 메시지에 씁니다.
    • 다중 복제본 배포에서도 올바르게 동작합니다. 상태는 데이터베이스를 기준으로 하며, Redis는 깨우기와 이벤트 스트림에만 씁니다.

    이번 범위가 아닌 것:

    • 논블로킹 지연 승인 모드(도구가 즉시 "승인 대기"를 반환). 이 설계의 인프라에 의존하며, 나중에 개별 도구의 선택 모드로 따로 설계합니다.
    • 내장 도구의 승인(승인은 여전히 MCP 도구에만 연결합니다).
    • MCP elicitation과 브라우저 사람 개입의 구체적인 연동(모델이 이를 담을 수 있다는 것만 보장합니다. 0절 참고).

    3. 전체 방안

    상호작용 하나는 두 단계를 거칩니다.

    • 짧은 대기 단계(hot): 지금과 같이 실행 goroutine이 메모리에서 기다리며 기본 최대 120초입니다. 사용자가 이 사이에 응답하면 결과를 waiter에 바로 전달하고 실행은 그 자리에서 이어집니다.
    • 일시 중단 단계(suspended): 짧은 대기 임계값을 넘기면 일시 중단 가능한 상호작용은 실행 상태를 DB에 저장하고, 실행은 awaiting_input으로 끝납니다. 사용자가 응답하면 복구 작업이 어느 복제본에서든 엔진을 다시 만들어 실행을 이어 갑니다. 일시 중단할 수 없는 상호작용은 짧은 대기가 끝나면 바로 expired로 닫습니다.

    타임아웃 때가 아니라 상호작용에 들어가는 순간 전체 스냅숏을 DB에 씁니다. 따라서 짧은 대기 단계에서 프로세스가 죽어도 회수 작업이 일시 중단 상태로 바꿀 수 있어 단계를 잃지 않습니다.

    원문 그래프
    stateDiagram-v2
    [*] --> pending: 进入交互，写快照，持有租约
    pending --> answered: 用户回答（任意副本 CAS）
    pending --> suspended: 短等待超时且可挂起（持有者 CAS）\n或租约过期（回收任务 CAS）
    pending --> expired: 短等待超时且不可挂起
    pending --> canceled: 用户停止运行
    suspended --> answered: 用户回答
    suspended --> superseded: 用户发新消息 / 回溯 / 删除会话
    suspended --> expired: 超过过期时间（回收任务）
    answered --> executing: 回答需要触发外部副作用（如批准的工具调用）
    answered --> done: 回答已交给模型（拒绝、OAuth、提问）
    executing --> done: 工具结果已持久化
    executing --> failed: 执行中断，结果未知
    done --> [*]
    failed --> [*]
    canceled --> [*]
    superseded --> [*]
    expired --> [*]

    answered는 "사용자가 응답했다"는 뜻일 뿐이며, 응답 내용(승인인지 거부인지, 무엇을 채웠는지)은 response에 있고 "누가 실행을 이어 가는가"와는 관계가 없습니다. 보유자 waiter가 아직 살아 있으면 그것이 메모리에서 이어 가고, 아니면 복구 작업이 이어 갑니다. 시스템 측에서 닫은 이유(타임아웃, 취소, 대체)는 close_reason에 적어 사용자 응답과 따로 저장합니다.

    // 已完成的轮次，与将来写入 Message.AgentSteps 的内容一致
    CompletedSteps []types.AgentStep     `json:"completed_steps"`
    KnowledgeRefs  []*types.SearchResult `json:"knowledge_refs,omitempty"`
    CurrentRound   int                   `json:"current_round"`
    TurnUsage      types.TokenUsage      `json:"turn_usage"`

    // 被打断的那一轮
    PendingRound PendingRound `json:"pending_round"`
}

type PendingRound struct {
    // 本轮的 thought / reasoning；ToolCalls 只含阻塞调用之前已完成的调用
    Step         types.AgentStep `json:"step"`
    // 模型在这一轮发出的全部调用，参数均为已解码的持久形式
    Calls        []PendingCall   `json:"calls"`
    // 被交互阻塞的调用下标，之后的调用尚未执行
    BlockedIndex int             `json:"blocked_index"`
}

type PendingCall struct {
    ID                string                 `json:"id"` // 已规范化
    Name              string                 `json:"name"`
    Arguments         string                 `json:"arguments"` // 已解码
    UnresolvedHandles []string               `json:"unresolved_handles,omitempty"`
    ProviderMetadata  types.ToolCallMetadata `json:"provider_metadata,omitempty"`
}

    types.ResumableAgentRequest는 원래의 Query, AgentID, SummaryModelID, ReasoningEffort, SharedAgentReadOnly, KnowledgeBaseIDs, KnowledgeIDs, TagScopes, MCPServiceIDs, SkillNames, WebSearchEnabled, QuestionOrigin, UserMessageID, Language를 저장합니다. 세션, 첨부 파일, 이미지는 복구 시 저장소에서 다시 읽습니다. 로컬 브라우저 연결은 특정 복제본의 WebSocket에 묶여 있으므로 복구 시에는 항상 사용할 수 없는 것으로 봅니다. AgentTenantID(P3에서 추가)는 에이전트가 속한 워크스페이스를 기록해 복구 시 공유 에이전트를 해석하는 데 씁니다. 스냅숏의 UserMessages는 UserMessagesBefore가 참조하는 보충 메시지 본문을 저장하며, 복구 시 원래 턴 경계에 맞춰 넣습니다. 오래된 스냅숏에 본문이 없으면 같은 세션의 메시지 기록에서 채웁니다. 이미 소비한 이벤트는 여전히 steer 목록의 consumed 표시로 중복을 제거합니다.

    임시 핸들 처리(핵심): 모델 출력의 cN/dN/res:// 핸들은 이번 실행의 modelcontext.Registry 안에서만 유효합니다. 복구 후의 Registry는 새로 만든 것이라 번호가 다를 수 있습니다. 이번 턴의 user 메시지와 도구 결과는 모델에 보내기 전에 모두 인코딩되므로, 스냅숏에는 렌더링된 메시지를 저장하지 않고 원래 query와 디코딩된 단계만 저장합니다. think.go는 모델 응답을 받을 때 이미 response.ToolCalls에 DecodeToolCalls를 실행하므로 Function.Arguments가 곧 디코딩된 파라미터이며(ModelArguments는 DB에 저장하지 않음), 스냅숏은 이것과 UnresolvedHandles를 그대로 저장합니다. 복구 시에는 디코딩 단계를 건너뛰며, UnresolvedHandles가 비어 있지 않은 호출은 이전처럼 실행 전에 실패합니다.

    이미 끝낸 단계의 thought, 도구 파라미터와 결과는 원래 디코딩된 형태로 저장됩니다(modelcontext의 약속은 "모델 출력은 도구, 저장소, UI가 소비하기 전에 먼저 디코딩한다"입니다). 복구 뒤 LLM을 호출할 때마다 EncodeMessages가 다시 인코딩하며, 번호의 일관성은 새 Registry가 스스로 보장합니다.

    MCP 도구 레지스트리를 복구할 때는 끝낸 이력과 일시 중단된 턴에서 이미 보낸 호출을 함께 읽어, 처음 호출될 때 지연 로딩되는 도구도 다시 만들 수 있게 합니다.

    5. 백엔드 흐름

    5.1 상호작용 진입(보유자, 짧은 대기 단계)

    두 계층으로 나뉩니다. 범용 코어 hitl.Broker.Await(ctx, Spec)가 영속화와 대기를 맡고, 유형별 어댑터 계층이 페이로드를 만들고, 유형 전용 이벤트를 보내고, 응답을 해석합니다. 도구 승인의 어댑터 계층은 approval.Gate입니다. MCPTool.Execute가 승인이 필요하다고 판단하면 Gate.RequestAndWait를 호출하고, 이것이 ToolApprovalPromptRequest를 만든 뒤 Broker.Await를 호출합니다. Broker.Await의 단계:

    1. 호출자가 ToolExecContext.Snapshot으로 현재 실행 스냅숏을 얻어(6.1 참고) Spec.Suspend에 넣습니다. 스냅숏을 얻지 못하면 일시 중단하지 않고 메모리 대기로 돌아갑니다.
    2. 스냅숏이 있으면 먼저 agent_run_suspensions를 쓰고, 그다음 agent_prompts(status=pending, suspendable=true, owner_instance, lease_until=now+30s)를 씁니다. 두 단계는 같은 트랜잭션이 아닙니다. 스냅숏을 먼저 저장하므로 회수 작업이 상호작용 레코드를 볼 때 스냅숏은 반드시 이미 있습니다. 상호작용 레코드 쓰기에 실패하면 이어서 스냅숏을 삭제합니다. 상호작용이 일시 중단으로 끝나지 않으면(응답, 타임아웃, 취소, DB 쓰기 실패) Await는 종료 전에 (assistant_message_id, prompt_id) 조건으로 스냅숏을 삭제하므로, 같은 메시지의 더 새로운 스냅숏을 잘못 지우지 않습니다.
    3. 로컬에 waiter를 등록하고 어댑터 계층의 Emit을 호출해 이벤트를 보냅니다(도구 승인은 여전히 tool_approval_required이고 hot_wait_seconds 필드를 새로 추가합니다. timeout_seconds는 같은 값으로 남겨 예전 프런트엔드와 호환합니다).
    4. 다음 이벤트 중 하나를 기다립니다.
      • Pub/Sub 깨우기(채널 weknora:agent_prompt:wake): 데이터베이스에서 응답을 읽으며 데이터베이스를 기준으로 합니다.
      • 3초마다 데이터베이스 상태를 폴링해 Pub/Sub 메시지 손실에 대비합니다.
      • 짧은 대기 타이머 만료: 일시 중단 가능하면 pending → suspended CAS를 실행하면서 expires_at을 씁니다. 일시 중단할 수 없으면 pending → expired를 실행합니다. CAS가 실패하면 사용자가 막 응답했다는 뜻이므로 응답 읽기로 넘어갑니다.
      • ctx 취소(사용자 중지): pending → canceled CAS를 실행합니다. 실패하면 마찬가지로 응답 읽기로 넘어갑니다.
    5. 백그라운드에서 10초마다 lease_until을 갱신하며, 갱신 CAS는 갱신 가능한 상태와 이번 실행의 owner_instance 토큰을 함께 검증합니다.
    6. 응답을 얻으면 어댑터 계층이 Consume하며, CAS가 이번 실행의 소유권 토큰과 일치하고 성공해야만 계속할 수 있습니다. 소유권을 잃은 대기자는 종료하며 더 이상 DB에 저장하거나 완료 이벤트를 보내지 않습니다. 저장소 오류는 소유권 상실로 치지 않습니다. 먼저 재시도하고, 필요하면 레코드를 다시 읽어 같은 소유자의 목표 상태가 저장됐는지 확인합니다. 여전히 answered이거나 읽기에 실패하면 저장소 오류를 반환하고 도구를 실행하지 않습니다. 소유권 토큰으로 상호작용을 최대한 닫고, 일반 실패 마무리를 거쳐 실패 이벤트를 보내 잘못 detach해 미완료 메시지를 남기는 일을 막습니다.
      • 외부 부수 효과가 필요한 경우(승인된 도구 호출): CAS answered → executing, 도구 실행, 다시 CAS executing → done(MarkExecuted), 스냅숏 삭제.
      • 그 밖의 경우(거부, OAuth, 질문): CAS answered → done, 응답을 호출자에게 넘기고 스냅숏 삭제.
      • 일시 중단: Suspend 표시가 있는 결과를 반환하고(6.2 참고), 엔진은 이번 턴을 멈추고 실행을 끝냅니다.

    일시 중단 기능을 끄면(prompt_suspend_enabled=false) 4단계의 짧은 대기 타이머는 기존 tool_approval_timeout_seconds를 쓰고, 만료되면 지금 로직대로 타임아웃으로 기록합니다. 데이터베이스 레코드는 감사와 인스턴스 간 Resolve를 위해 그대로 씁니다.

    P1에서는 2~6단계 중 스냅숏과 일시 중단을 뺀 부분을 구현했으며, 타임아웃은 모두 expired로 닫습니다. P2에서 스냅숏과 일시 중단을 보완했습니다. HTTP 스트리밍 진입점(Web, 임베드 페이지, API)의 요청만 QARequest.Suspendable을 설정하며, 스위치가 켜져 있을 때만 엔진이 Snapshot을 제공합니다. IM과 MCP server 진입점은 설정하지 않으므로 기존 타임아웃대로 블로킹합니다. 보유자가 짧은 대기 중에 회수 작업이 레코드를 suspended로 바꾼 것을 발견하면(자신의 리스가 이미 만료된 경우) 마찬가지로 일시 중단으로 반환합니다.

    5.2 사용자 응답(임의의 복제본)

    기존 인터페이스 POST /agent/tool-approvals/{pending_id}와 MCP OAuth 콜백은 유지하며, 내부에서는 모두 Broker.Resolve를 거칩니다. 범용 인터페이스 POST /agent/prompts/{prompt_id}(임베드 페이지는 POST /embed/.../sessions/{session_id}/prompts/{prompt_id})의 요청 본문은 {kind, response}이고, response는 해당 유형의 응답입니다(P4.5 구현 완료). 이 인터페이스는 ask_user와 tool_approval을 받습니다. mcp_oauth는 OAuth 콜백으로만 완료할 수 있어 400으로 거부합니다. 예전 인터페이스는 호환 계층으로 남깁니다. Broker.Resolve의 단계:

    1. id로 레코드를 읽습니다. kind가 인터페이스가 선언한 유형과 다르거나 session_id가 라우트의 세션과 다르면 모두 not_found를 반환해 레코드 존재 여부를 드러내지 않습니다. 그다음 tenant_id와 user_id를 검증합니다(호출자 userID가 비어 있으면 불일치로 봄). 임베드 페이지 인터페이스는 channel과 session의 소속을 추가로 검증합니다.
    2. 해당 유형에 등록된 검증 함수를 호출합니다. 두 종류의 응답 모두 알 수 없는 필드를 거부합니다. 도구 승인: 응답은 {approved, modified_args?, reason?}이며 approved는 필수입니다. modified_args는 승인할 때만 적용되며 반드시 JSON 객체여야 합니다. P2부터는 도구의 InputSchema로도 검증하며, 도구 정의는 MCP 메타데이터 스냅숏에서 가져오고 가져오지 못하면 요청을 거부합니다. 질문: 질문의 schema로 검증합니다. 검증에 실패하면 400을 반환합니다.
    3. 레코드가 아직 pending인데 보유자 리스가 만료된 경우(보유자는 이미 종료했고 회수 작업은 아직 스캔하지 않은 경우), 먼저 회수 작업의 규칙대로 suspended로 바꾸고(owner_instance를 비우고 메시지를 입력 대기로 바꿈) 아래 CAS로 넘어갑니다. 그래야 이번 응답이 이미 없는 waiter에게 기록되지 않고 바로 실행을 복구합니다.
    4. 이전 상태를 구분하면서 RETURNING을 지원하지 않는 경우와도 호환되도록 CAS 두 개를 차례로 시도합니다.
      • UPDATE … SET status='answered', response=?, resolved_* WHERE id=? AND status='suspended' AND (expires_at IS NULL OR expires_at > now). 이와 함께 새 owner_instance 토큰을 만들고 lease_until을 설정해 응답을 받은 복제본에 넘깁니다. 성공하면 그 복제본이 실행을 복구합니다(5.4). (P3 구현 완료)
      • UPDATE … WHERE id=? AND status='pending'. 성공하면 Pub/Sub로 보유자를 깨우며, 보유자가 데이터베이스를 폴링해 대비하므로 ack를 기다리지 않습니다. (P1 구현 완료)
      • 둘 다 실패하면 레코드를 다시 읽어 already_resolved, expired, not_found 중 하나를 반환합니다.
    5. 응답 본문에 resumed: bool을 추가합니다. true면 프런트엔드는 오프셋 0부터 그 메시지의 이벤트 스트림에 다시 연결해야 합니다(예전 이벤트는 이미 비워짐). (P3에서 POST /agent/tool-approvals/{id}에 구현. MCP OAuth 콜백은 일시 중단하지 않으므로 복구 결과를 무시합니다.)

    예전의 Pub/Sub ack 기반 인스턴스 간 전달은 P1에서 제거했으며, Pub/Sub는 깨우기 역할만 남았습니다.

    5.3 일시 중단하고 실행 종료(보유자)

    엔진은 Suspend 신호를 받으면(6.2) 현재 턴을 멈추고 "최종 답변 합성" 경로를 건너뛰며, EventAgentComplete를 보냅니다. 여기에 Suspended(*types.PromptSuspension, pending_id, kind, expires_at 포함)를 새로 추가합니다.

    AgentStreamHandler.handleComplete는 Suspended일 때:

    • IsCompleted를 설정하지 않고 RunState=awaiting_input을 설정합니다. 끝낸 단계, 참조, 사용량은 평소대로 씁니다.
    • 평소대로 샌드박스 체크포인트를 찍습니다.
    • 산출물(artifacts)을 수집하지 않고 대체 답변도 보내지 않으며, 복구 후 실제로 완료될 때 처리합니다.
    • 메시지가 DB에 저장되면 이벤트 스트림에 run_suspended 이벤트(pending_id, kind, expires_at 포함)를 보내고, 이어서 complete(data.suspended에도 일시 중단 정보 포함)를 보내 현재 SSE를 정상적으로 끝냅니다.

    바깥쪽 defer:

    • DB 저장은 UpdateMessage만 호출하며(Updates는 비어 있지 않은 run_state를 씀), 채팅 이력 지식베이스 쓰기, 후속 질문 제안 생성, 장기 기억 기록은 하지 않고 복구 후 완료될 때 합니다.
    • steer 큐 처리: 아직 소비하지 않은 after 계열 메시지는 평소대로 kickNextRunFromSteerBacklog를 트리거합니다. 새 턴이 시작되면 8.1에 따라 이번 승인을 대체하며, 의미는 "사용자가 새 메시지를 보냈다"와 같습니다. 소비하지 않은 inject 계열 메시지는 after로 처리합니다. 다음 턴은 Resume을 비우고 이전 턴의 스냅숏을 재생하지 않습니다.
    • ClearLiveRun. liveAgentRun은 awaiting_input 메시지를 실행 중인 작업이 없는 것으로 보므로 남은 live-run 표시를 지웁니다.

    5.4 실행 복구(응답을 받은 복제본)

    처음에는 asynq 작업 agent:resume_run으로 복구를 전달할 계획이었습니다. 구현하면서 응답 요청을 받은 복제본이 프로세스 안에서 바로 복구하고, 작업 중복 제거 대신 상호작용 레코드의 리스를 쓰도록 바꿨습니다. Resolve의 CAS가 성공하면 그 복제본이 리스를 보유하고, 복구하는 동안 계속 갱신합니다. 복제본이 중간에 죽으면 리스가 만료되고 회수 작업이 마무리합니다(5.6의 2번 항목). 이렇게 하면 Redis 큐에 의존하지 않고 단일 머신과 다중 머신의 동작이 같아집니다.

    진입점은 session.Handler.ResumeSuspendedRun이며, MCPServiceHandler가 resumed=true일 때 호출하고 바로 반환하며 실행은 백그라운드에서 진행합니다.

    1. Broker.KeepLease가 새 소유권 토큰으로 실행이 끝나거나 상호작용이 answered / executing을 벗어날 때까지 리스를 갱신합니다. 먼저 이전 실행이 DB에 저장하고 live-run 표시를 풀 때까지 기다립니다. 이전 보유자와 연락이 끊기거나 그 리스가 만료되면, 영속 스냅숏에서 아직 저장되지 않은 대기 메시지를 복구한 뒤 남은 표시를 정리합니다.
    2. 스냅숏을 읽어 이 상호작용의 것인지 확인하고, 스냅숏의 Request에서 ResumableAgentRequest를 풀어 언어 설정을 복구합니다.
    3. 응답 요청의 신원(Resolve에서 이미 세션 소유자로 검증됨)으로 세션과 어시스턴트 메시지를 읽습니다. 메시지는 여전히 awaiting_input이면서 미완료여야 합니다. AgentID와 AgentTenantID로 에이전트를 다시 해석합니다(공유 에이전트는 원래 워크스페이스 기준으로 해석).
    4. 메시지의 run_state를 비운 뒤 live run을 게시합니다. liveAgentRun은 awaiting_input을 유휴로 보므로, 먼저 비우지 않으면 복구 중인 실행이 남은 표시로 간주되어 지워집니다.
    5. StreamManager.ResetEvents로 해당 메시지의 이벤트 목록을 비웁니다(steer 목록은 유지). 복구 요청은 원래의 Query와 RequestID를 그대로 써서 기억, 후속 질문, 이력 그룹이 이번 턴의 의미를 유지하게 합니다.
    6. skipSSE=true로 executeQA를 거치며, steer 이어받기의 서버 측 실행 시작과 같은 경로입니다. 세션 상호 배제, 샌드박스 turn lease, setupSSEStream, 완료 시 DB 저장을 모두 재사용합니다. setupSSEStream은 agent_query 뒤에 run_resumed를 덧붙입니다. AgentQA는 QARequest.Resume을 보면 Execute 대신 engine.Resume을 호출합니다.
    7. 실행이 끝나면 상호작용을 확인합니다. 여전히 answered라면 도구를 실행하기 전에 실행이 실패했다는 뜻이므로(세션 점유, 에이전트 로딩 실패 등) 상호작용을 failed로 표시하고 5.6의 방식으로 메시지를 마무리합니다. 그렇지 않으면 (assistant_message_id, prompt_id) 조건으로 스냅숏을 삭제합니다. 다시 일시 중단된 경우 새 스냅숏은 새 상호작용에 속하므로 삭제되지 않습니다.
    8. 2, 3단계가 실패하면(스냅숏 없음, 에이전트 삭제됨, 메시지 상태 불일치) 마찬가지로 failed로 표시하고 메시지를 마무리합니다.

    run_resumed에는 pending_id만 들어 있습니다. 일시 중단 전의 단계는 재생하지 않으며, 프런트엔드는 이미 표시한 부분을 유지하고 복구 뒤의 이벤트를 덧붙입니다. 완료 이벤트의 agent_steps는 전체 목록입니다.

    5.5 도구는 최대 한 번만 실행

    • 막혀 있던 호출이 응답을 받으면 CAS answered → executing(승인) 또는 answered → done(거부)을 하고, 도구 실행이 끝나면 executing → done을 합니다.
    • 복구 실행 중인 복제본이 executing 동안 연락이 끊기면, 회수 작업이 상호작용을 failed로 표시하고 메시지를 마무리할 때 그 호출을 "결과 불명"으로 기록하며 도구를 재실행하지 않습니다.
    • 복구 실패(에이전트 사용 불가 등, 도구 실행 전에 발생): 그 자리에서 failed로 표시하고 마무리하며 재시도하지 않습니다.

    5.6 회수 작업

    housekeeping의 cron 방식을 재사용해 1분마다 실행합니다. 리스 만료 후의 상태 업데이트는 스캔 시점의 소유권 토큰과 현재 리스가 여전히 만료 상태인지를 함께 검증해, 스캔 뒤에 갱신되거나 넘겨받은 실행을 잘못 회수하지 않게 합니다.

    1. status='pending' AND lease_until < now: 보유자와 연락이 끊긴 경우입니다. 일시 중단 가능하고 스냅숏이 이 상호작용의 것이면 suspended로 CAS하고(expires_at 기록), 스냅숏의 DisplaySteps()로 메시지의 agent_steps를 덮어쓰고 awaiting_input으로 표시합니다. 그렇지 않으면 expired로 CAS합니다. 스냅숏은 승인 진입 시 이미 썼으므로 여기서 바로 쓸 수 있습니다. (P2 구현 완료. 컨테이너에서 1분마다 실행되는 AgentPromptReaper가 처리하며, 스위치를 꺼도 장애로 남은 pending 레코드를 닫기 위해 실행됩니다.)
    2. status IN ('answered','executing') AND lease_until < now이고 스냅숏이 여전히 이 상호작용의 것: 복구 실행 중인 복제본과 연락이 끊긴 경우입니다. failed로 CAS하고, 메시지를 완료로 마무리하며, 막혀 있던 호출과 그 이후 호출을 실패로 기록하고(executing이면 결과 불명이라고 설명), 스냅숏을 삭제합니다. 짧은 대기 중에 응답된 상호작용의 스냅숏은 보유자가 이미 삭제했으므로 영향을 받지 않습니다.
    3. status='suspended' AND expires_at < now: expired로 CAS하고, 메시지를 완료로 마무리하며(LLM 호출 없음), 막혀 있던 호출과 그 이후 호출을 "만료됨"으로 기록하고, 스냅숏을 삭제합니다.

    마무리는 service.SuspendedRunService가 일괄 처리합니다(회수 작업, 8.1 대체, 복구 실패가 공유). 단계는 RunSnapshot.ClosedSteps(reason)에서 가져와 모든 tool_call에 결과가 있도록 보장하고, IsCompleted=true, run_state를 비웁니다. GORM의 Updates가 빈 문자열을 건너뛰므로 UpdateMessage가 run_state 열을 따로 씁니다. 본문에는 설명 문구를 덧붙이지 않고, 이유는 실패한 도구 결과에 적습니다. (P3에서 2, 3번 항목 구현 완료.)

    리스와 만료 시각은 애플리케이션 측 시계로 쓰고 비교합니다(Postgres와 SQLite의 시간 표현식이 호환되지 않음). 배포 시 각 복제본은 NTP로 시간을 맞춰야 합니다. 30초 리스와 10초 갱신이면 흔한 초 단위의 시계 오차를 충분히 견딥니다.

    6. 엔진 변경

    6.1 진행 중인 턴 추적

    AgentEngine에 roundProgress를 새로 추가하고 뮤텍스로 보호합니다.

    • executeToolCalls 전에 이번 턴의 thought, reasoning, 전체 response.ToolCalls를 등록합니다.
    • 순차 경로와 병렬 경로는 호출이 끝날 때마다 결과를 씁니다. 병렬 경로에서 MCP 호출은 장벽이므로, 거기까지 실행하면 그 앞의 호출은 모두 끝난 상태입니다(g.Wait()). 그래서 스냅숏이 확정적입니다.
    • snapshot(blockedIndex)가 RunSnapshot을 만듭니다. 막힌 호출 앞에 끝나지 않은 호출이 있으면 오류를 냅니다(이때는 일시 중단하지 않음). 파라미터는 원래 디코딩된 형태입니다(4.4).

    ToolExecContext에 필드 두 개를 추가합니다.

    • Snapshot func() ([]byte, int, error): 인코딩된 스냅숏과 형식 버전을 반환합니다. 실행을 일시 중단할 수 없으면 nil입니다. (P2)
    • Answered *types.AgentPrompt: 복구할 때 막혀 있던 그 호출에 넘기는(tool_call_id로 맞춤) 이미 응답된 상호작용 레코드입니다. 상호작용을 시작한 도구는 이를 보면 대기를 건너뛰고, 각자의 어댑터 계층이 response를 결과로 해석합니다. MCPTool.Execute는 처음의 IsEnabled 검증을 그대로 실행하고(그사이 관리자가 도구를 비활성화했다면 비활성화를 따름), Gate.ResumeDecision으로 승인 결정을 얻어 tool_approval_resolved를 보냅니다. 도구가 이후에 더 이상 승인이 필요 없더라도 사용자가 파라미터를 고쳤을 수 있으므로 사용자의 결정대로 실행합니다. ask_user는 답을 도구 결과로 바로 반환합니다. (P3에서 MCP 부분 구현 완료.)

    일시 중단 가능한 상호작용을 시작할 수 있는 도구는 모두 병렬 실행의 장벽이어야 합니다(MCP 도구는 이미 그렇고, ask_user는 CanRunConcurrently 화이트리스트에 넣지 않습니다). 그래야 한 실행에 같은 시점에 막혀 있는 상호작용이 최대 하나뿐이고 스냅숏이 확정적입니다.

    6.2 일시 중단 신호

    types.ToolResult에 Suspend *types.PromptSuspension(json:"-")을 추가합니다.

    • 순차 경로: 호출이 Suspend를 반환하면 뒤의 호출은 실행하지 않고, 막힌 호출은 append하지 않으며 tool_result 이벤트도 보내지 않고, executeToolCalls가 그 일시 중단 정보를 반환합니다.
    • 병렬 경로: 장벽 호출이 반환된 뒤 표시를 확인하고, 그 앞에서 끝난 호출을 원래 순서대로 append하고 보낸 다음 멈춥니다.
    • runReActIteration은 이를 받으면 이번 턴의 step을 RoundSteps에 합치지 않고 LLM도 다시 호출하지 않으며, state.Suspended와 state.SuspendedStep에 기록한 뒤 루프를 빠져나옵니다. executeLoop는 handleMaxIterations를 건너뜁니다.
    • emitCompletionEvent는 일시 중단 시 RoundSteps에 중단된 턴에서 끝낸 부분(SuspendedStep)을 더해 메시지 표시에 씁니다.

      • 정상 실행과 같은 tool_call / tool_result 이벤트를 보낸 뒤 step을 append합니다.
    5. 정상적인 executeLoop에 들어가 다음 턴부터 시작합니다.

    8. 세션 수준 의미

    8.1 일시 중단 중 사용자가 새 메시지를 보낼 때

    executeQA는 rejectIfOtherAgentRunLive와 되돌리기 검사 뒤, holdQATurn 전에 다음을 합니다(복구 실행 자체는 이 단계를 건너뛰며, steer 이어받기의 새 턴도 마찬가지로 대체합니다).

    1. 이 세션에서 status='suspended'인 상호작용을 찾아 superseded로 CAS합니다.
    2. 해당 메시지를 완료로 마무리합니다. 막혀 있던 호출과 그 이후 호출의 결과를 "사용자가 응답하지 않고 대화를 이어 감"으로 기록해 완전한 step으로 채우고, 본문은 그대로 둔 채 스냅숏을 삭제합니다. (P3 구현 완료, SuspendedRunService.SupersedeSession 참고.)
    3. 이렇게 하면 새 턴의 LoadAgentHistory가 완전하고 규칙에 맞는 이전 턴(모든 tool_call에 대응하는 tool 결과가 있음)을 볼 수 있습니다.

    프런트엔드 안내 문구는 "새 메시지를 보내면 처리 대기 중인 작업을 포기합니다"라고 분명히 알립니다. ask_user는 예외입니다. 카드에서 바로 답할 수 있고, 사용자가 입력창으로 답하면 일반 새 메시지로 처리하며(그 질문을 대체), 모델은 새 턴의 이력에서 질문과 새 메시지를 볼 수 있습니다.

    8.2 사용자 중지

    • 짧은 대기 단계: 지금과 같이 canceled로 처리합니다.
    • 일시 중단 단계: 실행 중인 작업이 없으므로 화면에 중지 버튼을 표시하지 않습니다. 사용자는 바로 거부를 누를 수 있습니다.

    8.3 되돌리기, 분기, 삭제

    • 되돌리기: SessionRewindService.Rewind는 세션 소속을 검증한 뒤, 되돌릴 지점을 읽기 전에 8.1대로 일시 중단을 대체하고 기존 로직을 실행합니다. (P3 구현 완료)
    • 분기: 대체하지 않습니다. 분기는 되돌릴 지점 이전의 메시지만 복사하며, 완료되지 않은 되돌릴 지점은 여전히 거부되고, 원본 세션의 일시 중단은 영향을 받지 않습니다.
    • 메시지나 세션 삭제: 따로 처리하지 않습니다. 상호작용은 만료될 때 회수 작업이 닫으며, 마무리할 때 메시지가 이미 없으면 스냅숏만 삭제합니다.

    9. 프런트엔드 변경

    1. handleMsgList: 메시지가 run_state==='awaiting_input'일 때:
      • agent_steps로 타임라인을 다시 만들고, 끝에 pending_prompt로 만든 상호작용 카드를 덧붙입니다(kind별로 렌더링).
      • continue-stream을 호출하지 않으며, isReplying=false, 입력창을 쓸 수 있습니다.
      • 타임라인에 "진행 중" 자리 표시 애니메이션을 표시하지 않습니다.
    2. 상호작용 카드는 kind별로 렌더링 컴포넌트를 등록합니다(도구 승인, OAuth는 기존 카드 재사용, ask_user는 질문 양식).
      • 짧은 대기 단계의 카운트다운이 0이 되면 문구를 "백그라운드 대기로 전환됨, 나중에 처리할 수 있습니다"로 바꾸고 버튼은 계속 쓸 수 있습니다.
      • 일시 중단 단계에서는 만료 시각을 표시합니다.
    3. 응답한 뒤 응답이 resumed=true면: isReplying=true로 설정하고 그 메시지에 continue-stream을 호출합니다. 복구 작업 전달에 지연이 있으므로 404면 500ms 간격으로 최대 10번 재시도합니다. run_resumed 이벤트부터 기존 타임라인에 덧붙이며, 이미 다시 만든 단계를 바꾸지 않습니다.
    4. run_suspended: 현재 스트림을 끝내고, 카드를 일시 중단 스타일로 바꾸며, isReplying=false.
    5. 일시 중단 상태에서 새 메시지 보내기: 먼저 확인 안내를 띄우고, 보내기에 성공하면 메시지 목록을 새로 고치며, 예전 카드에 "포기함"을 표시합니다.
    6. 사이드바 세션 목록: "처리 대기" 배지를 선택적으로 표시(2기).
    7. i18n: 새 문구를 추가하고 i18n-locale-align 절차에 따라 모든 언어에 반영합니다.

    11. 보안

    • Resolve는 리소스 단위로 권한을 확인합니다. 라우트의 세션과 인터페이스가 선언한 유형이 레코드와 일치해야 하며(불일치하면 존재하지 않는 것으로 처리해 세션이나 유형을 넘나드는 응답을 막음), 테넌트와 세션 소유자도 일치해야 합니다. 임베드 페이지는 channel과 session을 추가로 검증합니다.
    • 응답은 해당 유형에 등록된 검증 함수를 통과해야 하며, 등록되지 않은 유형은 모두 거부합니다.
    • pending_prompt와 요청 페이로드는 세션 소유자에게만 반환하며, 기존 SSE의 공개 범위와 같습니다.
    • modified_args는 InputSchema로 검증하며, 통과하면 원래 파라미터를 통째로 바꾸고 예전 키를 남기지 않습니다(기존 로직과 같음).
    • ask_user의 답은 사용자 입력이므로 모델에 넘길 때 신뢰할 수 없는 데이터로 감싸며(도구 결과와 같은 취급), 시스템 프롬프트에 이어 붙이지 않습니다.
    • 복구 시 다시 검증합니다: 도구가 활성화돼 있는지, 여전히 승인이 필요한지, 에이전트에 여전히 접근할 수 있는지, 세션이 여전히 그 사용자의 것인지. 하나라도 만족하지 않으면 도구를 실행하지 않습니다.
    • 스냅숏은 영속 ID와 디코딩된 파라미터만 저장하고 자격 증명은 저장하지 않습니다. MCP 자격 증명은 실행 시 기존 방식대로 해석합니다.
    • 만료, 대체, 중지 모두 상호작용 레코드를 남겨 감사 요구를 충족합니다.

    12. 내장 질문 도구 ask_user

    Agent가 사용자에게 정보를 보충받거나 선택을 받아야 할 때 호출하며, P4 이후의 별도 단계로 진행합니다.

    • 파라미터의 options는 항목별로 나열한 문자열 배열이어야 합니다. 올바른 배열 문자열은 여전히 호환 파싱할 수 있습니다. [로 시작하지만 파싱할 수 없는 문자열은 더 이상 단일 옵션으로 감싸지 않으며, 옵션 배열 안에 직렬화된 목록이 들어 있는 경우도 거부하고, 모델이 재시도할 수 있게 도구 파라미터 오류를 반환합니다.
    • 파라미터: question(필수), 선택적으로 options(단일 또는 다중 선택), fields(간단한 양식, 텍스트·숫자·단일 선택·다중 선택 유형으로 제한), allow_free_text. 파라미터 schema를 엄격히 제한하고 필드 수와 옵션 수에 상한을 두어 모델이 지나치게 큰 양식을 만들지 못하게 합니다.
    • 실행: kind='ask_user'인 상호작용을 만들고 Gate.AskUser → Broker.Await를 거칩니다. 스냅숏이 있으면 짧은 대기 뒤 일시 중단하고, 없으면 타임아웃까지 블로킹합니다. 응답 검증은 이번 fields / options에 따라 필수 항목, 타입, 값 범위를 확인하며, 알 수 없는 필드는 모두 거부합니다. 사용자는 "답하지 않음"({"declined": true})을 고를 수도 있습니다.
    • 결과: 답은 "The user answered. / Selected / Fields / Text" 형식으로 도구 결과가 되어 모델에 돌아갑니다. 사용자가 거부하거나, 타임아웃이 나거나, 대체되면 명확한 "사용자가 답하지 않음(이유)"을 반환하고 다음 단계는 모델이 정합니다. 도구 결과의 data에는 질문과 답을 함께 저장해, 이력을 다시 만들 때 이 호출을 도구 호출 한 줄이 아니라 응답이 끝난 카드로 렌더링합니다.
    • 일시 중단과 복구: 도구 승인과 같으며, 복구 시 ToolExecContext.Answered로 답을 바로 반환합니다.
    • 비대화형 채널: Web과 임베드 페이지의 HTTP 스트리밍 질의응답만 대화형으로 표시합니다(QARequest.Interactive → engine.SetInteractive). API Key 호출자는 응답 인터페이스에 접근할 수 없으므로 승인을 일시 중단할 수 있더라도 대화형으로 치지 않습니다. IM, API Key 등의 채널에서 호출하면 도구는 카드를 보내지 않고 모델에 "이번 턴의 답변에서 바로 질문하고 이번 턴을 끝내라"고 알리며, 사용자의 다음 메시지가 곧 답입니다.
    • 스위치: DefaultAllowedTools와 내장 에이전트(스마트 추론, 데이터 분석가)의 도구 목록에 넣으며, 에이전트 설정에서 체크를 해제할 수 있습니다. allowed_tools를 명시적으로 설정한 사용자 정의 에이전트는 직접 추가해야 합니다.
    • 프런트엔드: AskUserCard가 옵션(단일/다중 선택), 양식 필드, 자유 텍스트를 렌더링합니다. 승인 카드와 카운트다운 및 "백그라운드 대기로 전환됨" 로직(usePromptCountdown)을 공유합니다. 입력을 기다리는 메시지는 단계를 접지 않고 카드가 항상 보입니다.

    13. 단계별 구현

    단계내용외부 동작 변화
    P1새 표 두 개와 messages.run_state 마이그레이션(Postgres 000119, SQLite 000037). 범용 코어 hitl.Broker(영속화, 리스, 폴링 대비, Pub/Sub 깨우기, kind별 응답 검증). 도구 승인과 OAuth를 그 위의 어댑터 계층으로 변경. Resolve가 session과 kind에 묶임없음, 여전히 블로킹 방식
    P2(구현 완료)엔진 roundProgress, 스냅숏, Suspend 신호. handler 일시 중단 마무리. run_suspended 이벤트. 회수 작업 1번 항목짧은 대기를 넘기면 일시 중단하지만 아직 복구할 수 없음(기능 스위치 기본값 꺼짐)
    P3(구현 완료)engine.Resume, 프로세스 내 복구와 리스, ResetEvents, run_resumed. 8.1 새 메시지와 되돌리기 대체. 회수 작업 2, 3번 항목. SuspendedRunService 일괄 마무리백엔드 기능 완성(기능 스위치 기본값 꺼짐, 프런트엔드 미적용)
    P4(구현 완료)기능 스위치 기본값 켜짐. 메시지 목록이 awaiting_input 메시지에 pending_prompt를 첨부(시작한 사람에게만 보이며, 카드 필드와 expires_at 포함). 프런트엔드가 run_suspended / run_resumed를 처리하고, 일시 중단 카드에 "백그라운드 대기로 전환됨"과 마감 시각을 표시. 응답이 resumed: true를 반환하면 Web은 continue-stream으로 같은 메시지에 다시 연결(복구 스트림이 나타날 때까지 잠시 재시도). 임베드 페이지는 continue-stream이 없어 메시지 목록을 폴링하고 끝나면 다시 불러옴. 새 메시지를 보내면 일시 중단 카드에 "포기함" 표시. i18n도구 승인을 오래 일시 중단하고 어느 복제본에서든 복구할 수 있음
    P4.5(일부 구현)구현: ask_user 내장 도구(12절)와 그 양식 카드, 범용 인터페이스 POST /agent/prompts/{prompt_id}(임베드 페이지 포함)와 SDK 메서드. 미구현: MCP OAuth의 일시 중단 연동(OAuth는 여전히 블로킹 대기만 함)Agent가 사용자에게 질문할 수 있음
    P5문서, Swagger 생성물 재생성(현재 주 브랜치의 Swagger 생성물이 많이 뒤처져 있어 따로 commit)

    14. 테스트 요점

    • 범용 코어(P1에서 다룸): 복제본 간 응답이 데이터베이스를 거쳐 보유자에게 도달. 세션, 유형, 테넌트, 사용자 바인딩. 등록되지 않은 유형 거부. 응답 검증 실패. 응답과 타임아웃이 동시에 일어나면 응답이 이김. 타임아웃과 취소가 레코드를 남김. executing → done.
    • 상태 기계: 모든 CAS 전이의 성공과 실패 분기. 동시 Resolve, Resolve와 짧은 대기 타임아웃의 동시 발생, Resolve와 사용자 중지의 동시 발생 포함.
    • 스냅숏: 순차 경로와 병렬 경로에서 막힌 호출이 턴의 처음, 중간, 끝에 있는 경우. 실행하지 않은 호출에 임시 핸들이 있을 때 복구 후 파라미터가 올바른지.
    • 복구: 복구 후 LLM에 보내는 메시지 시퀀스가 일시 중단하지 않았을 때와 하나하나 같음(golden 테스트로 고정). 복구 중 다시 일시 중단. 복구 시 도구가 비활성화됨. 복구 시 에이전트가 삭제됨.
    • 최대 한 번 실행: executing 단계에서 장애를 흉내 내고, 재시도 시 재실행하지 않음.
    • 다중 복제본: Gate 인스턴스 두 개가 데이터베이스 하나와 Redis를 공유하고, Resolve가 보유자가 아닌 쪽으로 감. 보유자가 짧은 대기 단계에서 사라진 뒤 회수 작업이 일시 중단으로 바꾸고 다시 복구.
    • 세션 의미: 일시 중단 중 새 메시지 보내기, 되돌리기, 세션 삭제. 이력 재구성 결과가 규칙에 맞음.
    • 프런트엔드: 새로 고친 뒤 카드가 올바르게 표시됨. 승인 후 이벤트 스트림에 연결. run_suspended / run_resumed 렌더링.

    15. 확정된 결정

    1. 짧은 대기는 기본 120초, 일시 중단 후 기본 7일에 만료합니다.
