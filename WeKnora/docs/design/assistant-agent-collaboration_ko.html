    Assistant 위임과 하위 Agent 협업

    상태: 6개 도구 스케줄링 루프, 부모 대기 지점 자동 복구, 하위 작업 승인 전달을 구현했습니다. 남은 범위는 아래 전달 경계를 참고하십시오. 날짜: 2026-10-17.

    0. 이번 구현과 전달 경계

    이번에는 try_agent 도구, 임시 시험 실행 서비스, 등록, 프롬프트, 화면 문구를 제거했습니다. 협업 도구는 여섯 개만 남기며, read_agent, close_agent는 추가하지 않습니다.

    연결 완료:

    • 로그인한 Web 사용자 신원이 있는 비공유 reasoning Agent는 어시스턴트가 아니어도 부모 작업으로서 6개 도구를 등록할 수 있습니다. 직속 하위 인스턴스는 send_message만 등록하며 /root에만 보고할 수 있습니다. spawn_agent에서 agent_id를 생략하면 현재 실행 설정을 상속한 임시 인스턴스를 만들고, 지정하면 같은 워크스페이스의 기존 템플릿에 위임하며 기존 템플릿 자격 제한을 유지합니다. 설치 모드에서는 협업을 열지 않습니다.
    • 하위 인스턴스의 send_message는 별도의 설명과 schema를 쓰며 target(열거형 /root)과 message만 포함합니다. 하위 인스턴스에는 부모의 지시 전달 흐름을 설명하지 않고, 부모가 쓰는 expected_run_id도 노출하지 않습니다. 도구는 위임 런타임이 주입하므로 Agent 템플릿에 미리 설정할 필요가 없습니다. 일반 독립 실행도 부모 작업의 신원 조건을 만족하면 자기 작업을 나눌 수 있습니다. 능동적 전송은 모델의 호출에 달려 있으며, 도구 단계 자동 기록과 종료 상태 결과 자동 전달은 런타임이 따로 맡습니다.
    • agent_collaborations 유계 집계 레코드는 작업, 메일함, 결과, 이벤트를 한 번의 version CAS 안에서 함께 갱신하며 PostgreSQL / SQLite와 호환됩니다. 아래 전체 목표 설계의 여러 표를 대체하며, 작업을 가져갈 때 프로세스 잠금에 의존하지 않습니다. 정식 마이그레이션에는 활성 부모 작업 고유 인덱스가 있습니다.
    • 협업 하나당 실행 중인 하위 턴은 최대 3개, 이번 턴에서 쓰는 인스턴스는 16개, 인스턴스당 8턴 기록(부모 턴을 넘어서는 직전 종료 상태 하나만 이어 실행 기준점으로 유지)입니다. 대기열에 있는 작업은 실행 슬롯을 차지하지 않고, 유휴 인스턴스는 실행기에 상주하지 않습니다. 요청 중복 제거 키는 실제 tool-call 메타데이터에서 나오며, 누적 입력과 결과에는 크기 제한이 있습니다.
    • send_message는 idle 인스턴스를 시작하지 않습니다. followup_task는 실행 중이면 메일로 들어가며, 그 턴에서 처리되지 않은 추가 요구만 다음 턴으로 바뀝니다. 결과는 하위 세션의 메시지, 도구 단계, 참조를 먼저 저장한 뒤 이벤트를 게시합니다.
    • 하위 메일함은 실행기에 넘기기 전에 현재 run/owner 리스로 보호되는 CAS로 delivered_sequence를 저장합니다. 메시지 본문은 스냅숏 재구성을 위해 그대로 남깁니다. 실행기 panic, 반환값 유실, 승인 복구 시작 실패 시에는 영속 커서로 마무리하며, 실제로 전달되지 않은 followup에 대해서만 새 턴을 만듭니다. 전달이 곧 실행 성공은 아니며, 실패한 작업은 여전히 부모가 결과를 보고 다음 단계를 정합니다.
    • 엔진은 턴 경계에서 출처가 붙은 assistant 메시지를 자동으로 주입합니다. wait_agent는 알림만 반환하고 본문을 소비하지 않습니다. 자연 종료 시에는 반드시 하위 작업을 기다려야 하며, 최신 결과가 한 번의 모델 호출에 참여해야 합니다. 반복 상한에 이르면 명확히 오류를 내고 남은 위임을 취소합니다.
    • 중단, 부모 작업 취소, 루트 세션 중지 인터페이스, 일시 중단된 부모 작업의 supersede 모두 영속적인 취소 경로가 있습니다. 이전 run/owner, 만료된 리스, 이전 부모 메시지의 중지 지시는 새 실행을 덮어쓸 수 없으며, 늦게 도착한 성공이 이미 취소된 작업을 되살리지 않습니다.
    • 부모 엔진은 wait_agent와 자연 종료 시 하위 작업을 기다릴 때 안전한 스냅숏, 이미 관찰한 커서, 절대 마감 시각을 저장합니다. 프로세스가 재시작하면 스케줄러가 데이터베이스의 결과/타임아웃을 스캔해 CAS로 부모 리스를 가져가고 원래 부모 메시지를 복구합니다. 이미 끝난 도구는 다시 실행하지 않습니다. 대기 타임아웃은 재시작으로 다시 계산되지 않습니다. 실행 중인 부모 엔진은 원래 대기 지점에서 계속하며, 두 번째 부모 모델을 추가로 시작하지 않습니다.
    • queued 하위 작업은 복구합니다. 영속 승인 스냅숏이 있는 waiting 하위 작업도 복구할 수 있습니다. 일반 running이나 이미 승인을 소비하고 executing에 들어간 불확실한 실행은 needs_attention으로 바꾸며 부수 효과를 자동으로 재실행하지 않습니다. 사용자가 다음에 대화를 이어 가면 끝나지 않은 협업을 넘겨받아 영속 결과를 읽을 수도 있습니다.
    • 하위 작업의 승인/질문은 기존 HITL Broker를 쓰며, 스냅숏과 현재 run의 승인 연결을 먼저 DB에 저장한 뒤 부모 세션에 카드를 보여 줍니다. 승인 대기는 실행 슬롯을 풀어 줍니다. 응답은 백그라운드 큐가 소비하며, HTTP가 숨은 하위 세션을 직접 시작하지 않습니다. 동시 하위 작업의 여러 승인은 새로 고친 뒤에도 복구되며, 원래의 테넌트, 사용자, 하위 세션, 도구 호출 신원을 유지합니다.
    • 취소는 협업 집계에 먼저 기록한 뒤 승인을 닫고 스냅숏을 정리하는 쪽으로 수렴합니다. 닫기가 끝나기 전까지 cancelling을 유지하며, 재시작해도 정리를 계속합니다. 늦게 온 답은 다시 대기열에 넣을 수 없습니다. 복구 리스가 취소되면 승인 소비와 부수 효과 실행 전에 다시 확인합니다. Broker reaper는 아직 소비하지 않은 하위 작업의 answered 상태를 스케줄러에 돌려주며, executing 상태는 여전히 재실행을 금지합니다.
    • worker는 턴마다 사용자, 현재 워크스페이스 멤버 자격, Agent 사용 가능 여부를 다시 검증합니다. 기본 확인/읽기 전용 모드의 하위 작업은 스스로 쓰기 권한을 얻을 수 없고, operations 도구는 하위 작업에 상속되지 않습니다. 하위 세션과 실행 기록은 남기며, 시험 실행처럼 삭제하지 않습니다.

    페이지 이벤트와 표시(구현 완료):

    • 하위 작업 상태는 메인 모델의 텍스트와 독립적입니다. 영속 협업 그룹이 커밋된 뒤 collaboration_status 전체 화이트리스트 프로젝션을 게시하며, 데이터베이스 CAS version을 revision으로 씁니다. lease 하트비트는 UI를 갱신하지 않습니다. 같은 group의 이전 revision은 버리고, 같은 run의 종료 상태는 되돌아가지 않습니다. 템플릿 이름은 task/run 신원과 분리합니다.
    • 상태에는 현재 작업 이름, 실행/입력 대기/종료 상태, 도구 단계, 최근 능동 메시지와 prompt_id가 들어 있습니다. 토큰 단위의 사고나 원시 도구 입출력은 전달하지 않습니다. 메인 엔진의 attach/recover는 최신 스냅숏을 재생합니다. 메시지 이력 GET은 데이터베이스에서 같은 형태의 collaboration_status를 채우며 Redis가 살아 있는지에 의존하지 않습니다.
    • waiting / resumed는 실제 승인 상태가 바뀔 때 각각 한 번씩 부모 모델에 전달합니다. 복구는 ParentWait.After부터 소비를 이어 갑니다. 도구 단계는 UI 프로젝션만 갱신하며 매번 부모 모델을 깨우지 않습니다.
    • 메인 어시스턴트의 중간 설명은 별도의 progress 이벤트를 쓰며, 안정적인 이벤트 ID와 AgentStep.progress/progress_event_id가 영속 복구와 재생 중복 제거를 지원합니다. 최종 본문이나 사고 내용에는 쓰지 않습니다.
    • 페이지는 작업별로 목록을 계속 갱신하며, wait_agent의 여러 번 폴링은 대기 표시 하나로 합칩니다. 승인에는 소속 하위 작업과 실제 파라미터를 표시하고, 긴 MCP 도구 문서는 펼쳐 볼 수 있습니다. 실행 기록에는 보기 진입점을 남기며, 최종 본문은 여전히 부모가 통합해 정리합니다.
    • 승인 복구는 SSE 로그를 다시 만들며, 그 agent_query는 resume_pending_id와 resume_tool_call_id로 이번 이어 실행을 표시합니다. 프런트엔드는 이어 실행 전 각 steer 구간의 타임라인을 유지하고, 다시 연결할 때 이번 이어 실행의 후속 이벤트만 다시 만듭니다. 일반 전체 로그 재생은 여전히 빈 타임라인에서 다시 만듭니다.
    • 실시간 UI 알림은 최선 노력 전달이며, 복구 근거는 데이터베이스 상태입니다. 알림 전달이 실패해도 이미 커밋한 도구 작업을 롤백하지 않으며 도구를 다시 실행하지도 않습니다.
    • 부모 MCP 호출은 승인에 들어가기 전에 이 그룹의 현재 활성 하위 작업이 등록한 승인을 확인합니다. 같은 서비스, 네이티브 도구, 의미상 같은 JSON 파라미터(사용자가 수정한 파라미터 포함)이면 delegated_call_in_progress를 반환하며, 새 부모 승인을 만들지 않고, MCP를 호출하지 않고, 하위 권한을 빌리지 않습니다. 직접 호출과 프록시 호출이 이 검사를 공유합니다. 이미 끝났거나 취소된 하위 턴은 새 부모 호출을 막지 않습니다. 이 보호는 승인이 아직 등록되지 않았을 때의 프로세스 간 원자적 중복 방지와 같지 않으며, 기존 부모 승인 복구는 자체 생명 주기를 그대로 마칩니다.
    • 코드 영역 밖의 유효한 nonce를 가진 고립된 </think:…>는 같은 event ID의 answer.data.replace로 잘못 분류된 사고 접두부를 회수합니다. 일반 답변은 즉시 스트리밍을 유지하고, 표준 고립 종료 태그와 코드 리터럴은 보존합니다. 여는 태그가 없으면 종료 태그가 도착하기 전까지 접두부가 잠깐 보일 수 있으며, 확인되면 실시간으로 거둬들이고 최종 사고와 본문을 완전히 나눠 보관합니다. 16 KiB는 실시간 회수 미리 보기만 제한하며 최종 본문을 자르지 않습니다.
    • 2026-10-17 페이지 동시성 회귀 테스트: 레드팀 평가, 퍼즐 장인, 인기 순위 해설가 세 갈래를 실행했고, 승인 대기 중 새로 고친 뒤 복구됐습니다. 승인 후 하위 상태가 즉시 복구됐고, 세 결과가 최종적으로 통합되며 메인 작업이 끝났습니다. 추가로 부모가 인기 순위를 중복 호출하도록 일부러 유도해 중복 방지에 걸리는 것과 하위 승인만 남는 것을 확인했으며, 로그에는 실제 MCP 호출 성공이 한 번뿐이었습니다. 재시작, 취소, 늦은 상태, 승인 복구는 별도의 race 회귀 테스트로 다룹니다.

    이번 파라미터는 internal/agent/tools/collaboration.go를 기준으로 합니다: spawn_agent(task_name, message, agent_id?), list_agents(path_prefix?), send_message/followup_task(target, message, expected_run_id?), interrupt_agent(target, expected_run_id?), wait_agent(timeout_ms?). 대기는 기본 30초, 범위는 1–60초이며 범위 밖이면 거부합니다. 작업 기본 기한은 1시간입니다.

    프롬프트와 메시지 경계(정리된 구현):

    • 역할 프롬프트가 부모와 자식의 책임, 진행 상황, 최종 전달을 한곳에서 설명하고, 도구 설명은 호출 의미와 반환값만 정의합니다. 템플릿은 더 이상 협업 세칙을 반복하지 않습니다.
    • 부모 역할 프롬프트는 능동적 분할 전략도 한곳에서 정의합니다. 실질적인 작업을 시작하기 전에 독립된 범위를 판단하고, 실질적 작업량이 있으며 병렬화 이득이 있는 부분이 여럿이면 기본적으로 임시 하위 작업을 만듭니다. 간단한 요청, 강한 의존 단계, 즉시 막히는 작업, 충돌하는 수정은 로컬에 남기며, 사용자가 로컬 완료를 요구하면 따릅니다. 도구 설명은 이 결정 전략을 반복하지 않으며, 런타임은 키워드나 작업 길이로 하위 작업 생성을 강제하지 않습니다.

    2. 목표와 첫 버전 경계

    사용자가 reasoning Agent에 목표를 주면, 그 Agent는 자기 능력을 상속한 임시 하위 작업을 만들거나 이미 설정된 Agent를 골라 작업을 위임하고, 병렬로 작업을 나누고, 요구를 보충하고, 결과를 기다리고, 사람 상호작용을 처리하고, 재작업을 요구하고, 최종적으로 전달할 수 있습니다. 페이지를 새로 고치거나 서비스를 복구한 뒤에도 작업 상태와 이미 끝난 결과를 조회할 수 있습니다.

    현재는 부모 Agent 하나가 여러 직속 하위 Agent를 조율합니다.

    • agent_id 생략: 부모 작업 그 턴의 유효 설정 스냅숏을 씁니다. 실제로 고른 모델, 프롬프트, 지식베이스/문서/태그 범위, MCP, Skills, 샌드박스 설정, 실제 도구 집합이 포함됩니다. 새 CustomAgent 레코드는 쓰지 않습니다.
    • agent_id 지정: 기존 CustomAgent 템플릿 스냅숏을 쓰며, 권한 범위로 잘라 낸 뒤 실행합니다.
    • 현재 워크스페이스에서 쓸 수 있는 smart-reasoning Agent만 지원합니다. 공유 테넌트 간 실행은 열지 않습니다. 템플릿 모드는 내부 관리 템플릿 제한을 유지합니다. 상속 모드는 부모 작업의 실행 권한으로 동작하며, 부모가 일반 Agent인지 내장 어시스턴트인지에 따라 전용 분기를 추가하지 않습니다.
    • 하위 Agent는 부모에게만 보고할 수 있고, 하위 Agent를 더 만들거나 형제를 직접 지휘하지 않습니다. 나중에 같은 모델 위에서 계층과 동급 협업을 열 수 있습니다.
    • 모델에는 원래의 협업 도구 여섯 개만 제공합니다. 결과 읽기, 컨텍스트 전달, 인스턴스 정리는 런타임이 맡으며, 인스턴스를 읽거나 닫는 도구는 추가하지 않습니다.
    • 기본적으로 하위 Agent는 최대 3개까지 동시에 실행하며, 조율자를 위해 실행 용량을 남겨 둡니다. 승인이나 하위 작업을 기다리는 동안에는 계산 슬롯을 풀어 줍니다.
    • 임시 하위 작업은 역할을 사용자 정의하거나 모델을 덮어쓸 수 없으며, 범용 DAG 편집기, 임의 실행 지점의 무손실 복구, 예약 스케줄링도 제공하지 않습니다.
    • 첫 버전은 기본적으로 독립 샌드박스입니다. 공유 지식베이스/Wiki 쓰기에는 리소스 범위와 충돌 제어가 있어야 하며, 쓰기 가능한 호스트 프로젝트 디렉터리를 기본으로 공유하지 않습니다.

    임시 하위 작업의 영속화와 범위

    • 설정 스냅숏은 서버의 실행 컨텍스트에서 오며, 도구 호출이 모델, 권한, 설정 스냅숏을 제출할 수 없습니다. MCP의 all은 부모 작업을 초기화할 때 구체적인 서비스 집합으로 해석합니다. 하위 실행이 등록하는 도구는 다시 부모 작업의 실제 도구 집합과 교집합을 취합니다.
    • 사용자, 워크스페이스 멤버 신원, 출처 Agent는 턴마다 다시 권한을 확인합니다. 지식베이스 읽기 권한, 쓰기 가능 범위, 워크스페이스 승인 상한도 다시 확인합니다. Skills는 권한이 확인된 이름만 저장하며, 런타임에 사용 가능한 내용과 자격 증명을 다시 불러오고 스킬 환경 변수는 영속화하지 않습니다.
    • 임시 하위 작업도 독립 세션과 샌드박스를 쓰며, 부모의 채팅 이력, 첨부 파일 경로, 끝나지 않은 호출을 복사하지 않습니다. 부모는 message에 완전한 작업과 필요한 배경을 제공합니다. followup_task는 같은 하위 세션과 설정을 유지하며, 승인 복구는 같은 실행 턴을 이어 갑니다.
    • 두 모드는 대기열, 메일함, 대기, 취소, 승인, 결과, 산출물 인계를 함께 씁니다. 임시 작업의 화면에는 task_name을 표시하며, 새로 저장한 템플릿처럼 위장하지 않습니다.
    • 회귀 테스트는 임시/템플릿 세 갈래 혼합 동시 실행, 재시작 후 설정 복구, 같은 인스턴스 추가 작업, 일반 부모 Agent 깨우기, 권한 축소와 도구 범위 비확장, 두 모드에서 실제 MCP 승인의 승인, 거부, 취소, 재시작 복구를 다룹니다.

    3. 세 가지 신원과 생명 주기

    반드시 구분해야 합니다.

    1. Agent 설정 agent_id: 템플릿 위임 때의 기존 CustomAgent ID이며, 동시에 여러 번 인스턴스화할 수 있습니다. 임시 인스턴스는 이 필드가 비어 있고, 출처와 유효 설정은 비공개 스냅숏에 저장합니다.
    2. 협업 인스턴스 member_id: 어떤 사용자 작업 안의 하위 Agent로, 영속 하위 세션과 메일함이 있습니다. 한 번의 작업이 끝난 뒤에도 재작업을 받을 수 있습니다.
    3. 실행 턴 run_id: 인스턴스의 한 번의 실행입니다. 시작과 재작업은 새 턴을 만들고, 승인 복구는 원래 턴을 이어 갑니다.

    사용자 목표 하나의 경계로 collaboration_id를 따로 두며, 루트 세션과 시작 메시지에 연결합니다. 같은 루트 세션의 서로 다른 작업을 session ID만으로 섞을 수 없습니다.

    인스턴스 상태는 open → closed이며 런타임이 관리합니다. 실행 상황은 현재 턴으로 나타냅니다. 활성 턴이 없는 open 인스턴스는 idle입니다. 하위 턴 하나가 끝나도 인스턴스는 followup에 쓸 수 있으며, 협업 전체가 끝나거나 취소되면 일괄 닫습니다. 상주 상태 loaded / unloaded는 인스턴스 상태와 독립적입니다. unloaded인 open 인스턴스는 followup 때 다시 로드할 수 있으며, closed로 잘못 판단하면 안 됩니다.

    턴 상태:

    queued → running → succeeded | failed | interrupted
                ↘ awaiting_input → running
                ↘ awaiting_children → running    （协调者）
queued/running/awaiting_* → cancelling → cancelled
running → needs_attention                        （副作用结果未知等）

    역주: 위 상태도의 괄호 주석은 각각 "(조율자)", "(부수 효과 결과 불명 등)"이라는 뜻입니다.

    • succeeded는 실행이 끝나고 결과를 저장했다는 뜻일 뿐이며, 전달 품질이 검수를 통과했다는 뜻이 아닙니다. 첫 버전은 기계가 판정할 수 있는 accepted/rejected 상태를 도입하지 않습니다. 부모가 결과를 보고 재작업이나 전달을 정하며, 런타임은 결과 버전, 전달, 처리에 참여한 부모 턴, 재작업 연결만 기록합니다.
    • interrupt_agent는 현재 턴을 멈추고, 인스턴스와 이력은 유지하며, 다시 followup할 수 있습니다. root/self 대상은 거부하고, idle 인스턴스에는 다시 로드하지 않고 활성 턴 없음을 반환합니다. 일시 중단된 턴도 prompt/wait 복구 자격을 취소해야 하며, 늦게 온 승인으로 중단된 턴을 되살릴 수 없습니다. 종료가 확인되기 전에는 같은 인스턴스에서 다음 턴의 쓰기 작업을 시작할 수 없습니다.
    • 인스턴스 닫기와 리소스 정리는 런타임이 일괄 실행합니다. 닫은 뒤에는 더 이상 자동으로 시작할 수 없으며, 아직 실행 중인 턴은 먼저 취소하고 종료를 확인해야 합니다. 인스턴스를 닫아도 이력과 산출물은 삭제하지 않습니다.
    • 사용자의 "전체 작업 중지"는 협업을 cancelling으로 두고, 대기/실행/일시 중단 중인 모든 턴을 취소하며, 깨우기 자격을 닫습니다. 이미 일어난 수정은 롤백하지 않습니다.
    • 각 취소 요청은 generation을 지닙니다. 늦게 온 이벤트는 감사에 기록할 수 있지만, 이미 취소된 작업을 다시 시작할 수 없습니다.

    4. 모델에 제공하는 도구

    원래 정의의 여섯 도구만 유지하며, 읽기나 닫기 도구는 추가하지 않습니다. 아래는 WeKnora에서의 권장 파라미터와 의미이며, 파라미터는 엄격한 schema로 검증합니다. 파라미터를 맞췄다고 원래 정의와 필드 단위로 호환된다는 뜻은 아닙니다.

    도구주요 파라미터의미와 반환
    spawn_agentagent_id, task_name, message, context_mode?, resource_refs?, expected_output?, limits?인스턴스, 하위 세션, 첫 턴, 대기열 이벤트를 만들고 즉시 member_id, run_id, task_path, status를 반환함. 완료를 기다리지 않음
    list_agentspath_prefix?, include_closed?, cursor?현재 협업 안의 인스턴스와 현재 턴 요약, 막힌 이유, 읽지 않은 이벤트 수, 산출물 요약을 반환함. Agent 설정을 나열하는 것과 다름
    send_messagetarget, message, expected_run_id?메시지를 영속 전달함. 실행 중이면 안전 경계에서 받고, idle이면 메일함에 남기며 새 턴을 시작하지 않음. event_id, delivery_state를 반환
    followup_tasktarget, message, expected_run_id?idle이면 새 턴을 만듦. running이면 추가 요구로 전달함. 일시 중단 중이면 요구를 저장하되 승인을 자동으로 승인하지 않음. 재작업 이유는 message에 적고, 런타임이 당시 결과 버전과 연결함. 실제 run_id와 전달 상태를 반환
    interrupt_agenttarget, expected_run_id지정한 턴을 중단함. 원래 상태와 interrupt_requested를 반환하며, 종료 확인은 이후 이벤트로 나타냄
    wait_agenttimeout_ms?현재 조율자의 메일함이나 입력 변화를 기다리고, 깨움/타임아웃/사용자 입력 중단 알림을 반환함. targets나 모델이 제공한 커서는 받지 않음. 본문과 출처는 런타임이 읽어 전달함

    Agent 선택은 먼저 agent.list / agent.get을 재사용하고, can_delegate, 실행할 수 없는 이유, 기능 요약을 추가로 반환합니다. 별도의 Agent 검색 체계는 당분간 추가하지 않습니다.

    target은 member_id를 우선하며, 같은 협업 안의 경로도 쓸 수 있습니다. task_name은 같은 부모 인스턴스 아래에서 유일합니다. 같은 요청을 재생하면 원래 인스턴스를 반환하고, 다른 요청이 같은 이름을 쓰면 충돌을 보고하며 조용히 재사용하지 않습니다. 모든 도구의 신원, 테넌트, 협업 루트, 부모 인스턴스는 실행 컨텍스트가 주입하며 모델이 지정할 수 없습니다.

    원래 정의의 wait_agent 책임을 유지합니다. 대기와 업데이트 보고를 맡고, 본문은 런타임이 영속 메일함과 결과 기록에서 읽어 안전 경계에서 따로 전달합니다. wait를 호출하지 않아도 실행 중인 부모는 결과를 받을 수 있습니다. 도구가 반환한 업데이트 표시는 본문이 소비됐다는 뜻이 아닙니다. 본문과 출처가 부모 컨텍스트에 영속적으로 기록됐을 때만 전달 커서를 앞으로 옮깁니다. 두 경로는 같은 중복 제거 기록을 씁니다.

    wait는 wait-any 의미를 씁니다. 관련 인스턴스 중 하나라도 새 메시지, 종료 상태, 사용자 처리 대기 상태가 있으면 반환하며, 결과를 모두 받았는지는 조율자가 판단합니다. 기본 대기 30초, 최소 10초, 최대 1시간이며 모두 서버 설정입니다. 최솟값보다 작으면 최솟값으로 맞추고, 최댓값보다 크면 거부하며, 0을 기본적으로 즉시 읽기로 해석하지 않습니다. 요청한 대기 시간은 이번 wait의 전체 마감 시각이며, 일시 중단과 재시작으로 초기화할 수 없습니다. 런타임의 짧은 대기 임계값을 넘으면 스냅숏을 쓰고 일시 중단하며, deadline에 이르면 데이터베이스 주기 스캔도 반드시 복구를 트리거해야 하고 하위 이벤트의 깨우기에만 기대면 안 됩니다. 타임아웃은 하위 작업을 취소하지 않습니다.

    예시:

    {
  "agent_id": "existing-market-agent-id",
  "task_name": "market_analysis",
  "message": "分析提供的市场材料，区分事实、推断和缺失数据。",
  "context_mode": "brief",
  "resource_refs": [{"kind": "knowledge", "id": "authorized-document-id"}],
  "expected_output": "给出分析结论、证据引用和待核实事项；不修改原文。"
}

    역주: 예시의 message는 "제공한 시장 자료를 분석하고 사실, 추론, 누락 데이터를 구분하라", expected_output은 "분석 결론, 증거 인용, 확인할 사항을 제시하고 원문은 수정하지 말 것"이라는 뜻입니다.

    인스턴스 ID는 기존 Agent 설정 ID와 섞어 쓰지 않습니다. 모델은 기본적으로 대상 Agent에 저장된 설정을 쓰며, 첫 버전은 임의의 모델 override를 제공하지 않습니다.

    5. 컨텍스트, 권한, 사람 상호작용

    5.1 컨텍스트 전달

    • 기본 context_mode=brief: 작업 설명, 부모가 명시적으로 제공한 필요한 배경, 검사를 거친 리소스 참조, 전달 요구 사항.
    • none: 작업과 명시적 참조만 전달하고 부모 이력을 상속하지 않습니다.
    • all: 이후 버전에서 권한 범위 안의 부모 대화 스냅숏을 엽니다. 부모의 시스템 프롬프트, 도구 권한, 끝나지 않은 tool-call 쌍은 복사하지 않습니다. 첫 버전은 이 파라미터를 만나면 명시적으로 거부해야 합니다.
    • 생성 시 이력 경계와 Agent 설정 버전/스냅숏을 고정합니다. 스냅숏은 키 본문이 아니라 자격 증명 참조를 저장합니다. 실행 중 설정을 바꿔도 기존 인스턴스가 조용히 바뀌지 않습니다. 권한 회수는 복구와 민감한 작업 전마다 다시 확인합니다.
    • 만료된 URL이나 부모의 cN/dN 같은 임시 참조 핸들을 그대로 넘기지 않습니다. 안정적인 리소스 ID로 바꾸고 하위 세션에서 다시 해석합니다.
    • 하위 결과는 artifact/document ID로 인계합니다. 부모가 명시적으로 골라 다음 하위 Agent에 다시 넘기며, 다시 권한을 확인하고, 전체 컨텍스트나 파일 시스템 전체를 바로 공유하지 않습니다.

    5.2 권한 부여

    유효한 리소스/동작 권한은 "사용자의 현재 권한 ∩ 워크스페이스 정책 ∩ 이번 작업의 권한 범위 ∩ 대상 Agent의 허용 범위"입니다. 부모 assistant 자신에게 어떤 전문 도구가 설치되지 않았다고 하위 Agent도 쓸 수 없는 것은 아니므로, 부모와 자식의 도구 이름 교집합을 단순히 취하면 안 됩니다.

    하위 실행마다 DelegationContext를 만들어 root/member/run, 사용자, 실행 테넌트, 리소스 범위, 허용 동작, 승인 정책, 예산을 기록합니다. 모든 도구 진입점, MCP 호출, 샌드박스 기능은 런타임이 제약을 집행하며, 프롬프트에만 적어 두면 안 됩니다. 범위가 명확하지 않거나 제약을 집행할 수 없는 쓰기 기능은 열지 않고, 권한 부여 필요/지원 안 함으로 표시합니다.

    첫 버전은 등록 시점에 내장 assistant만 하위 인스턴스를 만들고 제어할 수 있게 제한합니다. 하위 인스턴스는 부모에게 메시지를 보내는 기능만 있습니다. 하위 Agent를 통해 관리 목록, 다른 사용자의 세션, 호스트 디렉터리에 대한 추가 권한을 얻을 수 없습니다.

    Agent 메시지는 source=agent, 보낸 인스턴스와 턴을 저장하며, 협업 자료일 뿐 사용자 권한이 아닙니다. 기존 drainSteerMessages는 내용을 user 메시지로 쓰므로 하위 Agent 보고에 그대로 재사용할 수 없습니다. 전용 mailbox 주입 경로와 출처가 붙은 메시지 직렬화를 새로 추가하며, 사용자 발언으로 위장하거나 시스템 지시로 격상하면 안 됩니다.

    5.3 승인과 질문

    하위 Agent의 ask_user, 도구 승인, OAuth는 여전히 HITL Broker를 재사용합니다. 요청의 귀속은 하위 세션/하위 메시지에 두고, 메인 대화에는 Agent 이름, 작업, 작업 범위가 붙은 대리 카드만 보여 줍니다. 응답은 서버가 루트 작업에서 하위 prompt까지의 귀속, 사용자 신원, 현재 상태를 검증한 뒤 라우팅합니다. 편의를 위해 prompt의 session_id를 부모 세션으로 바꾸면 안 됩니다.

    사용자 승인은 그 작업/명시된 범위만 허용합니다. assistant가 대신 승인할 수 없고, 거부를 다시 위임으로 바꿀 수도 없습니다. 다른 하위 작업은 계속할 수 있으며, 부모는 그 작업이 사용자를 기다리고 있음을 볼 수 있습니다. 루트 작업을 중지하면 미결 prompt도 함께 닫으며, 늦게 온 응답으로 작업을 복구할 수 없습니다.

    7. 신뢰성 있는 전달과 부모의 이어 실행

    7.1 메시지는 자동으로 새 작업이 되지 않는다

    send_message는 메일함에만 쓰고 새 턴을 만들지 않습니다. 실행 중이면 다음 모델 호출 전과 자연 종료 전에 읽고, idle이면 다음 시작 때까지 남깁니다. followup_task는 "요구 전달"과 "소비자 보장"을 한 트랜잭션에서 처리합니다. 현재 턴에 넘기거나, 현재 턴이 끝난 뒤 새 턴을 하나 만들며, 종료 경쟁 속에서 잃어버리면 안 됩니다.

    메시지 전달과 followup 라우팅은 member/current_run을 잠근 뒤에 결정합니다. expected_run_id가 이미 바뀌었으면 충돌을 반환하며, 이전 결과에 대한 재작업을 새 턴에 넘기지 않습니다. 일시 중단 중에 메시지만 추가하는 것은 승인 복구와 같지 않습니다. 대기, 일시 정지, 취소 중인 인스턴스는 각각 명확한 queued, paused, rejected 상태를 반환합니다.

    클라이언트 요청 ID / 부모 도구 호출 ID는 서버 중복 제거 키로 매핑합니다. 모델이 같은 이름의 도구를 다른 호출 ID로 반복 출력하는 것은 본래 멱등(idempotent)하지 않으므로, 여전히 이름 중복, 현재 턴, 비즈니스 범위 제약이 필요합니다. expected_run_id가 맞지 않으면 충돌을 반환하며, 나중의 실행을 중단하거나 덮어쓰지 않습니다.

    메일함 이벤트는 수신자별로 커밋 순서대로 번호를 매기며, "전역 자동 증가 ID의 크기"를 커밋 순서와 같게 보지 않습니다. 영속 컨텍스트 주입 기록과 커서 전진은 원자적으로 처리해야 합니다. 새로 고침이나 장애 뒤에 같은 이벤트를 재생할 수 있지만, 모델 이력에 중복으로 쓰면 안 됩니다. 대상은 같은 collaboration 안으로 격리하며, 페이지 커서는 수신자와 필터 조건에 묶습니다.

    "영속 컨텍스트에 들어감"과 "부모가 처리함"을 반드시 구분해야 합니다. delivered_to_run을 기록한 뒤에도 프로세스가 아직 모델을 호출하지 않았을 수 있습니다. 이후 모델 요청이 실제로 그 이벤트를 포함하고, 부모 턴이 완료되거나 관련 후속 작업을 커밋했을 때만 handled_by_run을 기록합니다. 장애 복구 시 처리되지 않은 이벤트는 영속 메시지나 스냅숏에서 다시 컨텍스트 구성에 참여하며, 전달 커서가 이미 앞으로 갔다고 버리면 안 됩니다. 새 부모 턴에 다시 연결할 때 원래 메시지를 중복 삽입하지 않습니다.

    7.2 대기는 실행 상태다

    짧은 대기는 메모리에서 이벤트를 기다릴 수 있습니다. 짧은 대기 임계값을 넘으면 wait, 엔진 스냅숏, 이미 소비한 커서를 쓰고 awaiting_children으로 두며 계산 리소스를 풀어 줍니다. 영속 구독을 먼저 하고 이벤트를 다시 확인해, "확인한 뒤 구독하기 전에 완료됨"으로 깨우기를 놓치는 틈을 없앱니다.

    현재 AgentEngine.Resume은 answered AgentPrompt를 요구하고, AgentRunSuspension도 prompt_id에 묶여 있습니다. 범용 복구 페이로드(human_prompt / agent_wait)와 공통 스냅숏 복구 로직을 추출하고, 예전 HITL 데이터와의 호환을 유지해야 합니다. 가짜 "승인된 prompt"를 만들어 wait를 복구하지 마십시오. wait를 복구할 때는 원래 wait 도구 호출을 마치고 업데이트 알림을 반환하며, 런타임이 해당 본문을 영속 전달한 뒤 같은 턴을 이어 갑니다.

    스냅숏은 pending_tool과 between_rounds 두 복구 단계를 모두 다뤄야 합니다. 명시적 wait 복구 시에는 원래 도구 결과를 채웁니다. 부모의 자연 종료 검사에서 아직 하위 작업이 남아 있음을 발견하면, 턴 경계에 이어 실행 지점을 저장하며 존재하지 않는 wait 도구 호출을 지어내지 않습니다. 기존 RunSnapshot의 BlockedIndex/PendingRound 구조는 전자만 다루므로 버전을 매겨 확장해야 합니다. 대기 단계의 메시지, 단계, 이벤트 커서, 상태의 커밋에는 일관된 복구 프로토콜이 있어야 하며, waiting 표시 하나만 저장하면 안 됩니다.

    하위 턴 결과, 산출물 기록, 종료 상태, 부모 메일함 이벤트, outbox는 커밋할 수 있는 트랜잭션 경계 안에서 게시합니다. 파일 객체를 먼저 쓰고 데이터베이스 참조를 나중에 커밋하며, 고아 파일은 비동기로 정리합니다. 읽을 수 있는 결과가 커밋된 뒤에만 "완료"를 알립니다.

    부모 처리 규칙:

    부모 상태하위 이벤트 처리
    running메일함에 쓰고 안전 경계에서 주입함. 두 번째 병렬 부모 턴을 열지 않음
    awaiting_childrenCAS로 wait를 가져가고, 이미 도착한 이벤트를 합쳐 한 번 복구함
    awaiting_input이벤트를 저장하고 미결 사용자 상호작용을 우선 유지함. 하위 완료 때문에 이를 우회하지 않음
    active이지만 현재 턴은 끝남런타임이 발행한 완료/실패/중단/사용자 입력 필요 이벤트만, continuation_generation이 맞고 pending_result_runs와 연결될 때 중복 제거된 조율 후속 턴을 만들 수 있음. 일반 send_message는 대기열에만 들어감
    paused/needs_attention/failed/cancelling/cancelled/completed상태와 결과를 저장하고 자동으로 깨우지 않음

    처음 spawn할 때 런타임은 이번 목표에 대해 제한된 이어 실행 자격을 만듭니다. spawn/followup마다 pending_result_runs를 원자적으로 갱신합니다. 자격은 generation, 사용자 취소/일시 정지, 전체 예산의 제약을 받으며, 원래 목표의 이어 실행만 허용하고 하위 메시지가 목표나 한도를 바꾸게 두지 않습니다. 백그라운드 복구는 시스템 이벤트가 트리거하며, 일반 메시지 본문에 "완료됨"을 써서 위조할 수 없습니다. 하위 승인이 처음 입력 대기 상태에 들어가면 부모에게 한 번 알릴 수 있지만, 이 때문에 부모 모델을 반복해서 시작하면 안 됩니다.

    협업에 아직 미결 하위 작업이 있으면, 부모의 일반 답변은 현재 턴을 끝낼 수 있지만 목표 전체를 완료로 표시할 수는 없습니다. 부모가 정상적으로 최종 답을 만들면 런타임은 DB에 저장하기 전에 종결 검사를 합니다. 모든 하위 턴이 종료했고, 미결 prompt/재작업/처리 대기 종료 이벤트가 없으며, 마지막 모델 요청이 현재 필요한 결과를 포함해야 합니다. 결과가 모델 요청 뒤에 도착했다면 부모에게 처리할 기회를 한 턴 더 줘야 하며, "이미 컨텍스트에 주입함"만으로는 부족합니다. 검사를 통과하면 최종 전달을 기록하고 인스턴스를 일괄 닫습니다. 여기서 판정하는 것은 실행 흐름의 종료이며, 답변 품질이 합격이라는 기계적 증명이 아닙니다. 실패한 분기는 여전히 사실대로 보고해야 합니다.

    부모 모델의 비정상 종료, 콘텐츠 필터링, 예산 소진, 사용자 중단은 정상적인 최종 답 종결 흐름을 탈 수 없으며, 각각 failed/needs_attention/paused/cancelled 등의 이유를 유지합니다. 새 하위 이벤트와 경쟁할 때는 협업 잠금과 버전 CAS로 계속할지 완료할지를 정하며, "작업 완료"를 먼저 게시하고 상태를 나중에 확인하면 안 됩니다. 스트리밍 텍스트는 먼저 보여 줄 수 있지만, 최종 완료 표시는 이 검사를 기다려야 합니다.

    사용자의 새 메시지, 중지, 되돌리기, 시스템 깨우기는 세션 상호 배제와 generation 검사를 함께 씁니다. 사용자 입력이 우선합니다. 새 메시지는 런타임에 들어가 컨텍스트를 갱신하고, 되돌리기/삭제는 이전 복구 자격을 무효로 합니다. 일반적인 새 메시지는 이전 작업을 모두 암묵적으로 취소하지 않습니다. 백그라운드 결과 주입에는 대상을 표시해 새 질문의 답으로 취급되지 않게 해야 합니다.

    7.3 런타임 읽기와 정리

    결과 읽기는 내부 서비스 인터페이스를 쓰며 모델 도구로 등록하지 않습니다. 하위 턴이 끝나면 런타임은 member_id + run_id + result_version으로 커밋된 결과, 참조, 산출물을 읽어 출처가 붙은 부모 컨텍스트 자료를 만듭니다. 짧은 결과는 완전히 전달하고, 긴 결과는 요약, 명확한 잘림 표시, 안정적인 리소스 참조를 전달합니다. 오류, 막힘, 미완료 항목을 조용히 버리면 안 됩니다. 전체 텍스트는 기존 message.list 작업으로 해당 하위 세션을 읽을 수 있고, 문서/파일은 기존 리소스 읽기 기능을 그대로 씁니다. 연동할 때는 새로 추가한 하위 세션 kind의 권한 확인과 결과 펼치기 기능을 반드시 검증해야 합니다. 부모가 실제로 읽을 도구가 없는 핸들만 주면 안 됩니다. 펼칠 수 없으면 전달 가능한 원본을 남기고 제약을 명시해야 합니다. 사용자가 전체 과정을 보는 것은 하위 세션 상세를 그대로 씁니다.

    정리는 다음 규칙을 따릅니다.

    • 하위 턴이 끝나면 실행 슬롯과 임시 실행 리소스를 풀고, 인스턴스, 세션, 복구 가능한 작업 공간 상태는 남겨 이후 재작업을 허용합니다.
    • 루트 작업이 완료되면 같은 종결 트랜잭션에서 generation, 다른 활성/일시 중단 턴과 미결 상호작용이 없음, 처리 대기 결과와 followup이 없음을 검증하고, 현재 부모 턴을 끝내며, 최종 전달과 처리 기록을 저장하고, 인스턴스와 깨우기 자격을 닫습니다. 검사는 곧 끝날 부모 턴 자신을 막는 항목으로 세면 안 됩니다. 동시 followup과 같은 협업 상태 잠금을 놓고 경쟁해, 정리한 뒤에도 대기열에 들어가는 일을 막습니다.
    • 사용자가 취소하거나 삭제하면 먼저 cancelling에 들어가 새 작업을 막고 미결 턴과 prompt를 취소합니다. 실행자가 종료하기를 기다린 뒤 인스턴스를 닫습니다. 외부 호출 결과를 모르면 확인 대기 상태와 감사 정보를 남기며, 롤백했다고 주장하지 않습니다.
    • 샌드박스, 리스, 임시 파일의 해제는 멱등한 정리 작업으로 처리합니다. 정리가 실패하면 재시도할 수 있으며 Agent를 다시 실행하지 않습니다. 작업 공간에서 복구해야 할 내용은 먼저 영속화한 뒤 리소스를 풉니다.
    • 일시 정지는 인스턴스를 닫지 않습니다. 재개는 여전히 현재 권한과 예산 검사를 받습니다. 닫힌 이전 인스턴스는 메시지나 followup으로 암묵적으로 다시 열 수 없습니다.
    • 이력, 결과, 산출물은 기존 보존/삭제 규칙에 따라 처리하며, 계산 리소스 정리와 함께 삭제하지 않습니다.

    일반적인 유휴 언로드는 루트 작업 종결과 다릅니다. 언로드는 인스턴스 상주 리스를 보유하고, 먼저 곧 사라질 메모리 큐로 동시 전달이 들어오지 못하게 막은 뒤, 세션/작업 공간 상태와 전달되지 않은 메일을 저장하고, 마지막으로 리소스를 풉니다. send_message는 인스턴스를 로드하지 않고 데이터베이스 메일함에 바로 쓸 수 있습니다. followup은 먼저 로드/실행 자격을 가져간 뒤 복구합니다. 작업 트리가 닫힌 뒤에는 이런 지연 로딩을 허용하지 않습니다. 최대 인스턴스 수, 최대 상주 수, 최대 실행 수를 따로 설정하며, 동시 모델 요청만 제한하고 유휴 샌드박스를 무한히 남겨 두면 안 됩니다.

    8. 복구, 예산, 쓰기 충돌

    • 대기했지만 실행하지 않은 턴은 다시 가져갈 수 있습니다. 승인/하위 작업 대기는 저장된 스냅숏에서 복구할 수 있습니다.
    • 일반 실행 중 프로세스 장애는 임의 지점의 무손실 복구를 약속하지 않습니다. 읽기 전용이며 재생 가능한 턴은 정책에 따라 재시도합니다. 결과를 알 수 없는 쓰기 호출이 있으면 needs_attention으로 두고, 증거를 남겨 외부 상태를 확인하며, 턴 전체를 자동으로 다시 실행하지 않습니다.
    • 리스가 만료되면 이전 owner는 새 결과를 커밋하거나 다음 도구 호출을 시작할 수 없습니다. 외부 쓰기 작업이 멱등 키/버전 조건을 지원하지 않으면 fencing만으로 정확히 한 번을 보장할 수 없습니다.
    • 워크스페이스, 사용자, 협업 전체, 단일 턴의 실행 동시성, 최대 인스턴스 수, 시간, token, 모델 호출 예산을 함께 제한합니다. 생성 시 허용 여부를 판단하고, 실행 전에 한도를 예약하고, 끝난 뒤 정산합니다. 하위 호출은 반드시 루트 작업으로 합산해야 합니다.
    • max_completion_tokens는 단일 모델 출력 제한일 뿐이며 작업 전체 예산으로 삼을 수 없습니다. 공급자 과금이 정확하지 않거나 중단되면 추정값과 실제값을 모두 남깁니다. 예산이 부족하면 새 호출을 더 이상 나누지 않습니다.
    • 동시성 슬롯은 실제 실행만 셉니다. 하위 작업을 기다리는 부모가 슬롯을 모두 차지하게 두지 않습니다. 다중 테넌트는 공정하게 대기열에 들어가며, 모델 도구 호출 안에서 슬롯을 무한히 기다리며 블로킹하지 않습니다.
    • 기본은 격리된 샌드박스입니다. Wiki/문서 쓰기는 리소스 ID별로 실행 리스를 신청하고, 버전 조건/OCC로 일반 사용자의 동시 편집을 감지합니다. 모델 간 약속이나 협업 내부 잠금만으로는 부족합니다. 쓰기 범위와 충돌 제어를 제공할 수 없는 기능은 당분간 병렬 위임에 넣지 않습니다.

    9. 프런트엔드, 결과, 검수

    메인 대화에는 영속 하위 작업 카드 묶음을 보여 줍니다. Agent 이름, 작업, 실행 상태, 막힌 이유, 결과 요약, 산출물, 과정 보기, 요구 추가, 중지가 들어갑니다. waiting과 idle을 구분하며 모두 "실행 중"으로 표시하면 안 됩니다. 시스템 복구로 생긴 메시지에는 "작업 계속 처리" 출처를 붙이며, 사용자 메시지로 위장하지 않습니다.

    권장 결과 구조: run_id, result_version, status, summary, artifact_refs, evidence_refs, changes, unresolved_items, usage, error. 완전한 내용은 하위 세션/산출물에 저장하고, 런타임이 부모에게 필요한 컨텍스트를 읽어 전달합니다.

    assistant는 런타임이 전달한 결과와 전달 요구 사항을 검사하고, 부적합하면 followup의 message로 재작업 이유를 설명합니다. 런타임은 수정 대상 결과 버전을 연결하고 새 턴을 만듭니다. 최종 답은 기존의 일반 모델 출력을 그대로 쓰며, 별도의 구조화된 "검수 성공" 프로토콜을 요구하지 않고 acceptance 메타데이터나 review 파라미터도 추가하지 않습니다. 런타임은 어떤 버전이 최종 부모 턴과 이후 재작업에 들어갔는지 기록하지만, 의미상 검수 통과를 자동으로 추론하지 않습니다. 최종 답변은 산출물, 실제 수정, 실패와 미완료 부분을 명확히 보고하며, "도구 성공"으로 작업 검수를 대신하지 않습니다.

    • 하위 작업 두 개의 완료 이벤트가 동시에 도착하거나 이벤트가 wait 등록보다 먼저 도착해도, 부모 턴은 하나만 복구되고 결과를 빠뜨리지 않는다.

    • 실행 중 작업 전체를 중지하면, 늦은 완료나 승인이 다시 깨우지 않는다. 이미 일어난 수정은 사실대로 남기고 보여 준다.
    • 쓰기 작업 뒤, 결과를 DB에 저장하기 전에 장애가 나면 결과를 확인 대기로 표시하고 무작정 반복 실행하지 않는다.
    • 하위 메시지는 사용자 권한 신원을 갖지 않는다. 테넌트를 넘거나 다른 작업의 target은 거부된다. 권한 회수는 복구 시점에 적용된다.
    • 부적합한 산출물은 재작업할 수 있고, 런타임이 새 버전을 전달하면 부모가 다시 검수한다. 최종 다운로드 파일은 검수 결과와 일치한다.
    • 모델 도구 목록에는 협업 도구가 정확히 여섯 개 있다. wait는 업데이트만 알리고 본문은 자동 전달되며, wait와 백그라운드 전달이 결과를 중복 주입하지 않는다.
    • 하위 턴이 끝난 뒤에도 followup할 수 있다. 루트 작업이 끝나면 런타임이 일괄 닫으며, 늦은 followup은 인스턴스를 다시 열지 않는다.
    • 정리와 followup이 동시에 일어나면 합법적인 결과는 하나뿐이다. 리소스 정리 실패는 멱등하게 재시도할 수 있으며, 이력과 산출물은 계속 읽을 수 있다.
    • idle 부모에게 보낸 일반 메시지는 모델을 시작하지 않는다. 시스템 종료 이벤트는 원래 작업에 이어 실행 자격이 남아 있을 때만 깨우며, 취소 후에는 되살릴 수 없다.
    • 결과를 DB에 저장하고 전달 커서를 앞으로 옮긴 뒤, 모델 요청 전에 프로세스가 죽어도 복구 후 결과가 여전히 부모 처리에 참여하며 이력을 중복으로 쓰지 않는다.
    • 하위 결과가 부모의 마지막 모델 요청 뒤에 도착하면 부모는 새 버전을 처리한 뒤 종결해야 한다. 종결 검사는 부모 턴 자신 때문에 막히지 않는다.
    • 유휴 언로드가 메시지/재작업과 동시에 일어나도 메시지를 잃지 않고 다시 로드는 한 번만 일어난다. 일반 언로드는 재작업 능력을 유지하며, 닫힌 뒤에는 다시 로드할 수 없다.
    • 부모에게는 긴 결과를 실제로 완전히 읽을 수 있는 경로가 있다. 새로 추가한 하위 세션 kind가 소유권 검사를 우회하거나 참조를 읽을 수 없게 만들지 않는다.

    부모 턴을 넘는 이어 실행과 산출물 읽기(2026-10-18)

    • 이전 부모 턴이 정상적으로 끝나면, 다음 사용자 입력이 새 협업 그룹을 만들고 같은 계정, 같은 스페이스, 같은 메인 세션에서 가장 최근에 완료된 그룹의 유휴 하위 인스턴스 식별자를 상속합니다. list_agents는 previous_turn으로 이어 갈 수 있는 인스턴스를 표시합니다. followup_task는 새 하위 턴을 만들되 원래 하위 세션과 그 샌드박스 바인딩을 재사용합니다. 이전 그룹은 완료 상태를 유지하며, CAS로 유일한 후속 협업 그룹을 기록해 동시에 들어온 새 요청이 같은 하위 세션을 복제하는 일을 막습니다. 후속 그룹이 아직 만들어지지 않은 상태에서 프로세스가 종료하면, 다음 요청이 그 가져가기 기록을 재사용합니다. 이전 메일함, 승인, 리스, 중복 제거 키, 이벤트는 상속하지 않습니다. 가장 최근 그룹이 이미 취소됐다면 그것을 건너뛰어 더 이전의 인스턴스를 상속하지 않습니다.
    • 상속한 인스턴스는 실제로 작업을 추가하기 전에는 이번 턴의 타임라인 카드로 표시하지 않으며, 이번 턴의 16개 인스턴스 한도도 차지하지 않습니다. 이어 실행 카드는 followup_task가 있는 위치에 고정합니다.
    • 하위 턴 결과는 영속화된 파일 메타데이터를 지닙니다. 부모 엔진은 이미 전달된 이벤트 장부에서 파일 참조를 복구하고, 완료 시 파일을 부모 메시지에 묶습니다. 일반 Markdown 링크와 이미지 표기는 같은 파일 카드와 미리 보기 경로를 씁니다. 같은 이름의 파일은 안정적인 리소스 참조로 구분하고, 하위 파일 출처 경로는 하위 세션별로 격리해 버전을 잘못 판단하지 않게 합니다.
    • 협업 실행의 read_file은 전달된 파일의 resource:// 참조와 모호하지 않은 sandbox:<文件名>(파일 이름)을 지원합니다. 읽기 범위는 현재 세션 산출물과 런타임에 묶인 완료된 하위 턴 메시지입니다. 스페이스, 계정, 메시지, 파일 삭제 상태를 검증하고, 리소스의 원래 저장 백엔드에서 읽으며, 파일 하나의 읽기 상한은 8 MiB이고, 텍스트는 기존 줄/문자 커서로 페이지를 나눕니다. 하위 샌드박스 디렉터리는 부모 Agent에 노출하지 않습니다. 계속 편집해야 하면 여전히 원래 하위 Agent에 위임합니다.
    • 자동 회귀 테스트는 턴을 넘는 재시작, 같은 하위 세션 재사용, 추가 요청 중복 제거, 이전 그룹 취소 격리, 계정/세션을 넘는 요청 거부, 긴 줄 페이지 나누기, 같은 이름 파일의 모호성, 이어 실행 카드의 타임라인 위치를 다룹니다.

    부모·하위 Agent의 책임 경계(2026-10-18)

    • 사용자가 기존 에이전트에게 작업 실행을 요구하면, 부모 Agent는 위임, 소통, 산출물 읽기, 결과 검사, 최종 정리를 맡고, 하위 Agent는 자기 템플릿, MCP, Skills, 작업 공간으로 실행합니다. 설정 조회는 데이터 읽기이며 역할 전환이 아니고, 도구, 샌드박스, 승인 권한을 넘겨주지도 않습니다.
    • 이미 위임한 작업은 부모 Agent가 MCP를 중복 호출하거나 Skill을 다시 실행하지 않습니다. 보충 요구와 재작업은 send_message / followup_task로 원래 인스턴스에 돌려줍니다. 부모 Agent는 겹치지 않는 작업에는 여전히 자기 도구를 쓸 수 있습니다.
    • 승인 대기, 실패, 복구는 자동 인수 신호가 아닙니다. 사용자가 부모 Agent에게 넘겨받으라고 명시적으로 요구하면, 먼저 아직 활성 상태인 하위 작업을 중단하고 멈췄는지 확인하고, 이미 일어난 효과를 점검한 뒤, 부모 Agent 자신의 권한으로 실행합니다.
    • 이 부분은 기존 역할 지침에 모아 둔 행동 약속이며, 런타임이 모든 의미상 중복을 판단할 수 있다고 주장하지 않습니다. 런타임은 계속 독립된 권한, 승인 귀속, 취소, 실행 소유권을 유지하고, 하위 승인 호출과 맞는 중복 방지 검사를 남깁니다. 공유 MCP 서비스를 이유로 부모 Agent를 통째로 막지는 않습니다.
