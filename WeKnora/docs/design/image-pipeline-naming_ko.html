    이미지 파이프라인: 설정 키와 트레이스 키의 명명 규칙

    상태: 시행 중(「문서 사진 OCR 전 기하 전처리」와 함께 도입) 적용 범위: internal/application/service/image_*.go, internal/types/image_actions.go, internal/types/knowledgebase.go, 프런트엔드 지식베이스 설정 패널

    이 문서는 장기 규칙입니다. 파이프라인, 액션, 파라미터, 트레이스 필드를 새로 추가할 때는 이 문서에 따라 이름을 짓고, 기존 키 이름을 바꿀 때는 §6의 목록에 따라 소비 측을 함께 수정합니다. 기계적으로 검사할 수 있는 부분은 모두 테스트로 고정해 두었습니다(§7). 따라서 이 "규칙"은 단순한 관례가 아니며, 어기면 테스트가 실패합니다.

    0. 하나의 대원칙

    이름 = 소속 + 이름. "소속"은 같은 컨테이너에 여러 주체가 쓸 때만 드러내 적는다.

    이 원칙 하나로 "왜 액션에는 접두사를 붙이고 파이프라인에는 붙이지 않는가"와 "왜 DB에 저장하는 키는 밑줄을, 파라미터는 점을 쓰는가"를 함께 설명할 수 있습니다.

    1. 세 가지 컨테이너, 세 가지 키 형태

    컨테이너누가 쓰는가키 형태예
    설정(image_processing_config 필드 / image_pipeline_params 슬롯)패널과 API(사용자의 선택)KB 필드는 snake_case, 파라미터는 <pipeline>.<key> 또는 <pipeline>.<action>.<name>image_attrs_enabled, default.ocr_enabled, smartocr.preprocess.mode
    DB 저장 산출물(chunks.image_info, 지식과 함께 이동)액션 자신명사, snake_case, 상태어 없음caption, ocr_text, attrs, sha256
    처리 트레이스(span output, runContext.out)여러 액션 + 프레임워크 + 서비스 계층config 컨테이너(설정 에코) · <action>.result · <action>.<数据名>(데이터 이름) · 이미지 수준의 접두사 없는 이름config, ocr.result, ocr.chars, outcome, actions

    점은 "소속 경계"에만 씁니다(한 단계). 이름 내부에는 밑줄만 쓰고, 한 세그먼트 안에 점이 또 나와서는 안 됩니다(그러면 경로 분리가 모호해집니다. §8 참고).

    슬롯은 저장 위치이지 두 번째 소속이 아닙니다. 어떤 설정이 누구 이름으로 쓰였다면 그 주체의 슬롯에 저장되고(types.SlotKey가 생성하고 types.ImagePipelineParam이 읽어 옵니다), 오직 그곳에만 저장됩니다. 다른 철자로 대신 찾아보는 대체 경로는 없습니다. 읽히지 않으면 "저장된 적 없음"이며, 양쪽 모두 필드 선언의 기본값으로 돌아갑니다.

    이 규칙은 preprocess.mode와 ocr_on_unobserved에도 똑같이 적용됩니다. 두 키는 한때 지식베이스 최상위(preprocess_mode, image_actions.ocr.on_unobserved)에 있었지만, 슬롯으로 옮길 때 호환 읽기를 남기지 않았습니다. 두 키 모두 main에 들어간 적이 없어 배려해야 할 기존 데이터가 없으므로, 이전 값은 모두 버리고 새 기본값으로 다시 설정하면 됩니다("사용자가 업로드하거나 다시 파싱할 때 반드시 설정 패널을 한 번 거친다"는 점이 이번에 과감히 버릴 수 있었던 전제입니다). 프런트엔드도 같은 규칙을 그대로 따릅니다(pipelineParamKey / readPipelineParam). 양쪽의 읽기 방식이 같아야 "패널에 보이는 값이 곧 런타임에 쓰는 값"이 됩니다.

    2. 소속 판단 기준: 튜닝 항목을 "액션"에 둘까, "파이프라인"에 둘까

    다음 두 질문을 순서대로 던집니다.

    1. 이 파라미터는 무엇을 결정하는가?
      • 이 액션 자신이 어떻게 실행되는지(호출 방식, 내부 하위 항목, 개입 전략)를 결정하면 → 액션 전용: <pipeline>.<action>.<name>
      • 다른 액션을 실행할지 / 실행 순서 / 여러 액션 사이의 선택(오케스트레이션)을 결정하면 → 파이프라인 전용: <pipeline>.<name>
      • 지식베이스 전체의 스위치와 선택에 속하면 → KB 필드: snake_case
    2. 재사용했을 때 의미가 안정적인가? 같은 액션을 다른 파이프라인이 재사용해도 의미가 그대로라면 → 액션 전용입니다(필드 정의, 문구, 패널 렌더링을 하나로 재사용할 수 있습니다).

    판단 기준은 "주어가 누구인가"가 아닙니다. 예를 들어 ocr_on_unobserved의 주어는 OCR이지만, 이 값은 "관찰에 실패했을 때 OCR을 계속 스케줄링할지"를 결정합니다. 이는 오케스트레이션이므로 파이프라인 전용입니다.

    전략은 설정에 속하고 상태에 속하지 않습니다. 속성 전략(어떤 관측값이 OCR을 트리거하는지, 관측되지 않으면 어떻게 할지)은 사용자/KB의 선택이며 스위치와 같은 급입니다. 한 번의 실행이 그 전략에 따라 어떤 결정을 내렸는지가 상태입니다.

    3. 세 계열의 어형(컨테이너를 넘나들어도 섞이지 않음)

    계열어형예
    설정 계열*_enabled · mode · 전략 이름ocr_enabled, thinking_enabled, preprocess.mode, ocr_on_unobserved
    상태 계열<action>.result, 값 = 상태어 + 원인ocr.result = skipped_no_text
    데이터 계열명사: chars / raw_chars / preview / bytes / error / error_code / attrsocr.chars, preprocess.bytes, image_bytes
    • 불리언 스위치는 <name>_enabled로 통일합니다(시스템의 기존 관례와 일치: <name>_enabled가 십여 곳, enable_*는 옛 표기 세 곳).
    • 별도의 reason 키를 두지 않습니다. 원인은 result 값에 합칩니다(skipped_no_text, skipped_declined …).
    • 한 owner의 한 측면에는 키 하나만 두고, 같은 사실을 두 곳에 기록하지 않습니다.

    4. 상태어와 결과 어휘표

    상태어는 시스템의 기존 span 상태(types/knowledge_span.go의 pending/running/done/failed/skipped/cancelled)에서 가져오며, 이 규칙은 그 부분집합에 원인 접미사를 붙여서만 씁니다.

    키값
    caption.resultdone / empty / skipped_disabled / failed
    observation.caption_result위와 같음(스마트 모드에서 설명은 관찰의 부산물)
    observation.resultall_done / partial / none / failed(속성 차원만 다룸)
    preprocess.resultdone / failed / skipped_no_capability / skipped_off / skipped_no_text / skipped_already_tidy / skipped_declined
    ocr.resultdone / failed / skipped_no_text / skipped_attr_policy / skipped_observation_failed
    outcome(이미지 수준)done / partial_failure / failed / skipped_unreadable_image / skipped_no_content

    세 계층의 "상태어" 역할 분담: span의 status(프레임워크: 끝까지 실행됐는가) / 액션의 result(이 단계에서 무엇을 얻었는가) / 이미지의 outcome(이미지 전체가 어떻게 됐는가).

    5. 계약 키와 진단 키

    • 계약 키: 프로덕션 소비자가 있는 키입니다(트레이스에 쓴 뒤 누군가 다시 읽어 갑니다). 예를 들어 ocr.result(하위 span의 성공/실패와 이미지 전체를 "산출물 없음"으로 볼지 결정), ocr.error_code(span의 error_code로 들어가며 프런트엔드가 현지화된 제목에 사용)가 있습니다. 계약 키는 상수를 씁니다(쓰기와 읽기가 한 곳의 정의를 공유하고, 상수 주석에 소비자를 명시합니다). 쓰기와 읽기는 서로 다른 함수에 있으므로, 두 곳의 리터럴을 맞춰 두는 방식은 언젠가 어긋납니다.
    • 진단 키: 프로덕션에서 읽는 곳이 없고 사람, 로그, 테스트만 봅니다(preprocess.*, ocr.preview, config 등). 자유롭게 이름을 바꿀 수 있으며 이름만 고치면 됩니다.
    • 둘을 구분하는 이유: 변경 위험이 한눈에 드러납니다.

    6. 키 이름을 바꿀 때 함께 고칠 곳

    1. 쓰기 지점(액션/프레임워크/서비스 계층)
    2. 읽기 지점(소비자) — 가장 빠뜨리기 쉽습니다.
      • 액션 안의 resolve() 클로저(*.error_code / *.error / *.chars를 다시 읽어 span의 성공/실패를 결정)
      • 파이프라인의 결정 지점(observation.result를 읽어 skip 원인을 결정)
      • 서비스 계층의 이미지 전체 판정(ocr.result / caption.error를 읽어 outcome과 작업 계층에 오류를 보고할지 결정)
    3. 프런트엔드: 설정 패널의 i18n 문구 경로(imagePipeline.<pipeline>.<field.key>.<label|description>, 문구가 없으면 백엔드 Label로 자동 대체), 처리 타임라인의 error_code 문구
    4. 테스트: golden 시퀀스 테스트, 속성 결정 테스트, 오류 코드 테스트
    5. 문서: 이 파일과 관련 인터페이스의 doc comment
    6. 프런트엔드 슬롯 미러: frontend/src/utils/imageProcessingConfig.ts의 pipelineParamKey / readPipelineParam(types.SlotKey / types.ImagePipelineParam에 대응). 양쪽 철자가 반드시 같아야 합니다. 다르면 패널에서 쓴 값을 런타임이 읽지 못합니다. 프런트엔드는 필드 이름을 알지 못합니다. 레지스트리가 넘겨준 필드를 렌더링하고 슬롯 단위로 읽고 쓰므로, 필드를 추가·삭제하거나 이름을 바꿔도 프런트엔드를 고칠 필요가 없습니다.

    7. 어떤 테스트로 고정하는가

    규칙테스트
    액션이 선언한 키는 반드시 자신의 액션 id를 접두사로 가져야 하며, 접두사 없는 이름에는 점이 없어야 한다TestDeclaredActionFieldsAreNamespaced(internal/types)
    파이프라인은 액션이 선언한 점 포함 키만 가질 수 있고, 직접 만들어서는 안 된다TestPipelineFieldKeysAreOwned
    같은 owner 안에서 키는 유일하다TestPipelineFieldsArePrivate, TestFieldDeclarationOrder
    파라미터는 파이프라인별로 격리되고, 슬롯이 없는 키는 값으로 치지 않으며, 기본값으로 돌아간다TestParamIsIsolatedPerPipeline, TestParamReadsOnlyItsOwnNamespace
    파이프라인이 선언한 필드는 세 구역(상시 / 고급 / 설명)으로 나뉘며, 순서가 곧 패널 순서다TestFieldDeclarationOrder
    실제로 실행되는 액션 시퀀스TestImagePipelineActionSequences
    설정은 결과와 같은 형태여서는 안 된다(마지막 세그먼트가 result/chars/bytes… 이면 안 됨)TestNoSettingIsNamedLikeAResult
    <action>.result는 액션 id로 조립하며, 키 접두사는 반드시 등록된 액션이어야 한다TestActionResultKeysAreNamedAfterTheirAction, TestEveryActionTraceKeyCarriesAnActionNamespace
    모든 result 값은 어휘표 안에 있다(한 분기에서만 쓰는 값 포함)TestTraceResultsStayInTheirVocabulary
    슬롯 조립 시 접두사를 중복하지 않고, 슬롯만 인정하며, nil 슬롯은 미설정으로 본다TestSlotKeyDoesNotDoubleThePipelineID, TestImagePipelineParamReadsOnlyTheSlot
    실행이 읽은 설정 = 트레이스가 에코한 설정TestTheRunReadsTheSettingItsTraceEchoes
    프런트엔드가 쓰는 키와 읽는 키가 같고, 방식을 전환해도 파라미터를 잃지 않는다ImagePipelineSettings.test.ts, imageProcessingConfig.test.ts

    8. 알려진 제약

    • 점 포함 키는 string-keyed map 안의 평범한 문자열입니다(Go / JSON / JSONB 모두 문법 문제가 없습니다). 다만 다음 제약이 있습니다.
      1. 세그먼트 안에 점이 또 나와서는 안 됩니다.
      2. 구조체 필드 이름이나 DB 열 이름으로 쓸 수 없습니다(그래서 DB에 저장하는 image_info는 밑줄을 씁니다).
      3. TOML / YAML처럼 "점이 곧 구조"인 형식에는 담을 수 없습니다. 나중에 내보내야 한다면 이스케이프하거나 이름을 바꿔야 합니다.
      4. jq로 값을 꺼내려면 .["smartocr.ocr.thinking_enabled"]로 써야 합니다.
    • 파라미터 슬롯의 접두사는 문자열 연결("<pipeline>.<key>")입니다. 나중에 역으로 파싱해야 한다면 규칙은 "첫 번째 점에서 자른다"(strings.Cut)입니다.
