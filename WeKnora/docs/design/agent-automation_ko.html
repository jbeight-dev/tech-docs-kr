    Agent 자동화(예약 작업)

    상태: 첫 버전 구현 완료, 설계와의 차이는 §13 참고. 날짜: 2026-10-19.

    권한 부분은 Agent 실행 권한 모델 위에 세웁니다. 자동화는 자체 승인 정책이나 화이트리스트를 정의하지 않고, 그 모델의 deferred 실행 모드, automation 범위 권한 부여, ActingVia 신원만 씁니다. 권한 모델의 앞 세 단계가 이 요구 사항의 전제 조건입니다.

    0. 확정된 결정

    문제결정
    세션 형태두 가지 모두 지원하며 사용자가 고름: 실행마다 새 세션(기본값), 또는 자동화 하나에 장기 세션 하나 고정
    확인이 필요한 작업실행 모드는 deferred: 일시 중단하고 승인을 기다리며 알림을 보냄. 자동화에 설정한 기한을 넘기면 포기하고 이번 실행을 실패로 기록
    첫 버전 전달 채널사이트 내부만: 실행 이력 + 알림 센터. IM 능동 푸시, 아웃바운드 Webhook, 이메일은 이후 단계로
    생성 진입점설정 페이지 양식과 어시스턴트 대화 생성 모두 제공, 양식을 먼저 구현. 어시스턴트 생성은 같은 서비스 인터페이스와 검증을 재사용

    1. 목표와 경계

    사용자는 "언제, 누구의 신원으로, 어느 Agent에게 무엇을 시킬지"를 정한 자동화를 정의합니다. 시각이 되면 시스템은 백그라운드에서 사람 없이 Agent 대화를 한 차례 실행하고, 결과를 영속화하고, 사이트 내부에서 작성자에게 알립니다. 실행 중에는 멀티 Agent 협업으로 작업을 나눌 수도 있고, 승인이 필요한 쓰기 작업을 만나면 일시 중단했다가 사용자가 처리한 뒤 이어 갈 수도 있습니다.

    첫 버전에 포함하는 것:

    • 트리거 방식은 cron 주기와 일회성 예약이며 시간대를 지원합니다. 수동 "지금 실행"도 제공합니다.
    • 실행 주체는 내장 WeKnora 어시스턴트로 고정합니다. 다른 에이전트가 필요하면 작업 프롬프트에 위임 대상과 작업을 적고, 어시스턴트가 기존 협업 도구로 위임합니다.
    • 실행 이력, 실행 상세(세션 상세와 하위 작업 보기 재사용), 실행 중지, 자동화 일시 정지·재개.
    • 사이트 내 알림: 실행 성공, 실패, 승인 대기, 자동 일시 정지.
    • 어시스턴트는 operations로 자동화를 만들고 관리할 수 있으며, 사용자 확인이 필요합니다.

    첫 버전에 포함하지 않는 것: 이벤트 트리거(데이터 소스 동기화 완료, 새 문서, 인바운드 Webhook 등), IM·Webhook·이메일 전달, 공유 Agent의 테넌트 간 실행, API Key나 IM 사용자를 자동화 소유자로 두는 것, 자동화 간 의존성 오케스트레이션(DAG).

    2. 기존 기능과 공백

    기존 구현재사용 방식공백
    sessionService.AgentQA. 이미 협업 실행기, IM, MCP Server가 백그라운드에서 직접 호출한 번의 실행 진입점으로 사용호출자마다 "메시지 쌍 만들기, 이벤트 스트림 연결, 완료 감시, DB 저장"을 중복 구현하므로 통합 실행 서비스를 뽑아내야 함(§6 참고)
    협업 런타임 internal/agent/collaboration, agent_collaborations자동화의 루트 Agent가 부모 작업 조건을 만족하면 바로 spawn_agent 가능. 영속화, 리스, 복구, 하위 승인 전달은 그대로협업은 부모 작업에 Web 사용자 신원을 요구하므로 "작성자 신원으로 실행"이 필요(§5.1)
    internal/datasource/scheduler.go(robfig/cron, 초를 포함한 6필드)표현식 파싱과 검증 재사용각 인스턴스의 메모리에 cron을 등록하고 동시에 트리거하며 Redis TaskID로 중복을 제거함. Lite에는 Redis가 없고 재시작 중 놓친 트리거도 보지 못함. 자동화는 데이터베이스 기반 스케줄링으로 바꿈(§4)
    HITL Broker: 대기 타임아웃 시 suspended로 바꾸고 ExpiresAt 설정, reaper가 만료분 회수일시 중단하고 승인 대기자동화 설정으로 만료 시각을 덮어쓰고, 일시 중단 시 사이트 내 알림을 보내야 함
    Session.Kind(assistant, agent_delegated)automation을 추가하고 일반 세션 목록에 넣지 않음세션 목록과 권한 검사가 새 kind를 인식해야 함
    types.WithPrincipal, 실행 모드 표시백그라운드 실행 신원과 실행 컨텍스트 구성권한 모델이 실행 모드 열거형으로 합치고 ActingVia를 추가(권한 모델 §2.3, §2.6)
    메시지 산출물(artifact)과 파일 카드실행 결과물없음
    GlobalInvitationBell.vue초대 알림 전용범용 사이트 내 알림 센터가 없어 새로 만들어야 함(§7)
    어시스턴트 operations 목록automation 계열 작업 추가없음

    3. 데이터 모델

    3.1 automations

    필드설명
    id, tenant_id, owner_user_id소유자는 작성자의 계정 ID이며 자격 증명은 저장하지 않음
    name, description, enabled
    model_id선택 사항. 어시스턴트가 이번 실행에 쓸 모델을 덮어씀. 비어 있으면 어시스턴트 기본 모델을 따르며, 위임받은 에이전트는 각자의 모델을 그대로 씀
    instruction작업 프롬프트. 런타임 변수 지원(§5.4)
    triggerJSON: {type: cron, expr, timezone} 또는 {type: once, at, timezone}
    session_modeper_run(기본값) 또는 persistent
    persistent_session_idpersistent 모드의 고정 세션. 첫 실행 때 만듦
    carry_last_resultper_run 모드에서 지난 성공 실행의 결과 요약을 주입할지 여부
    misfire_policyskip(기본값) 또는 run_once: 중단·일시 정지 중 놓친 트리거를 최대 한 번만 보충 실행
    overlap_policyskip(기본값) 또는 queue: 이전 실행이 아직 진행 중일 때 이번 트리거를 어떻게 처리할지. queue는 최대 하나만 대기
    access_level실행 단계. 의미는 권한 모델 §2.2 참고. 기본값 confirm, auto_write는 반드시 명시적으로 선택해야 함. 런타임에도 워크스페이스의 어시스턴트 권한 상한 제약을 받음
    approval_timeout일시 중단하고 승인을 기다리는 최대 시간. 기본값 24시간
    limitsJSON: 단일 실행 최대 시간, 최대 반복 횟수, token 상한
    next_run_at, last_run_at, last_success_at스케줄링 상태
    consecutive_failures, paused_reason연속 실패 횟수와 자동 일시 정지 이유
    versionCAS 버전
    created_at, updated_at, deleted_at

    인덱스: 스케줄링 스캔용 (enabled, next_run_at), 목록용 (tenant_id, owner_user_id).

    3.2 automation_runs

    필드설명
    id, automation_id, tenant_id
    scheduled_at계획된 트리거 시각. 수동 실행이면 시작 시각
    trigger_kindschedule / manual / misfire
    status§4.3 참고
    session_id, user_message_id, assistant_message_id이번 실행에 해당하는 세션과 메시지
    owner, lease_until실행 소유권. 협업 런타임과 같은 CAS + 리스 의미
    pending_prompt_id일시 중단하고 승인을 기다릴 때의 prompt
    effective_configJSON: 이번에 실제로 쓴 Agent, 모델, 지식베이스 범위, 도구 집합 요약. 문제 조사용
    usage, error, started_at, finished_at

    고유 제약: (automation_id, scheduled_at, trigger_kind). PostgreSQL과 SQLite 마이그레이션을 함께 제공하며, PostgreSQL에서만 지원하는 잠금 문법은 쓰지 않습니다.

    보존 정책: 자동화마다 최근 N개의 실행 기록을 보존합니다(설정 가능, 기본값 200). 실행 기록을 정리할 때 per_run 모드의 세션도 함께 정리합니다. persistent 세션은 자동화와 함께 삭제됩니다.

    4. 스케줄링

    4.1 데이터베이스 기반 가져가기

    스케줄러는 인스턴스마다 tick(기본 15초)마다 다음을 실행합니다.

    1. enabled = true AND next_run_at <= now인 자동화를 배치 크기를 제한해 조회합니다.
    2. 레코드마다 하나의 트랜잭션 안에서: version으로 CAS를 해 next_run_at을 다음 트리거 시각으로 옮기고, queued 실행 기록을 하나 삽입합니다(고유 키 충돌은 다른 인스턴스가 이미 가져갔다는 뜻이므로 바로 건너뜁니다).
    3. 커밋한 뒤 실행을 전달합니다. Redis가 있으면 asynq의 새 큐 automation으로, Lite면 프로세스 내 실행기로 보냅니다. 전달은 깨우는 역할만 하며, 실제 실행권은 실행 기록의 CAS와 리스가 결정합니다.
    4. 별도의 스캔 작업이 queued 상태로 오래 가져가지 않은 실행 기록을 처리해 전달 손실을 막습니다.

    이렇게 하면 다중 복제본, Lite, 재시작 세 경우의 동작이 같아지며, 프로세스 내 cron 표나 Redis 중복 제거에 의존하지 않습니다.

    4.2 시간 계산

    • 데이터 소스와 같은 robfig/cron 6필드 파서를 쓰고, CRON_TZ= 접두사나 별도의 timezone 필드를 추가로 지원합니다. 모두 IANA 시간대로 계산한 뒤 UTC로 저장합니다.
    • 검증할 때 앞으로의 트리거 시각 3개를 계산해 돌려주며, 양식과 어시스턴트 모두 사용자에게 보여 줍니다.
    • 최소 트리거 간격은 시스템 설정으로 조절할 수 있으며(기본 5분), 너무 촘촘한 표현식은 거부합니다.
    • 일회성 트리거는 실행 후 자동으로 enabled = false가 됩니다.
    • 놓친 트리거: skip은 바로 미래로 옮깁니다. run_once는 trigger_kind = misfire인 실행을 하나 삽입한 뒤 미래로 옮기며, 놓친 것을 하나씩 보충 실행하지 않습니다.

    4.3 실행 상태

    queued → running → succeeded | failed | cancelled
              ↘ awaiting_approval → running
              ↘ needs_attention                      （进程崩溃时执行结果未知）
queued → skipped                                     （重叠策略或自动化已暂停）

    역주: 위 상태도의 괄호 주석은 각각 "(프로세스가 죽어 실행 결과를 알 수 없을 때)", "(중첩 정책 또는 자동화가 일시 정지된 경우)"라는 뜻입니다.

    • overlap_policy = skip: 가져갈 때 같은 자동화에 running이나 awaiting_approval 실행이 있으면 새 실행을 skipped로 기록하고 이유를 남깁니다.
    • 프로세스 장애 복구는 협업과 같습니다. queued는 다시 가져갈 수 있고, awaiting_approval은 승인 응답으로 복구하며, 일반 running은 needs_attention으로 바꾸고 부수 효과를 자동으로 재실행하지 않습니다.
    • 단일 실행이 limits의 최대 시간을 넘으면 실행을 취소하고 failed로 기록합니다. 일시 중단하고 승인을 기다린 시간은 실행 시간에 넣지 않으며, 일시 중단 기한의 제약을 따로 받습니다.

    5. 실행

    5.1 실행 신원

    • 실행 전에 소유자를 불러와 다시 검증합니다. 계정이 유효한지, 여전히 워크스페이스 멤버인지, 내장 어시스턴트를 여전히 쓸 수 있는지, 지식베이스와 MCP의 권한 범위가 여전히 성립하는지 확인합니다. 하나라도 실패하면 이번 실행은 failed이며, 자동화를 일시 정지하고 paused_reason을 기록하고 알림을 보냅니다.
    • 검증을 통과하면 컨텍스트를 구성합니다: Principal{web_user, owner_user_id, ActingVia: "automation:<id>"}. 테넌트와 워크스페이스는 자동화 레코드에서 가져옵니다. 라우팅 계층이 소유자로 인증하므로 operations를 쓸 수 있고, 루트 Agent는 협업 부모 작업 조건을 만족해 spawn_agent할 수 있습니다. 감사 로그는 ActingVia로 대리 실행을 구분합니다.
    • 하위 작업은 권한 모델 §2.5에 따라 처리합니다. 단계는 부모 작업을 넘지 않고, 이번 실행의 권한 부여를 상속합니다.

    5.2 실행 모드와 권한 부여

    • 실행 모드는 deferred입니다(권한 모델 §2.3). ask_user를 등록하지 않습니다. OAuth가 필요한 MCP는 오류를 반환하고 모델이 결과에서 설명합니다. 정보가 부족하면 모델이 결과물에 빠진 항목을 적습니다.
    • 모든 호출은 권한 모델의 Decide가 판단하며, 자동화는 입력 두 가지만 제공합니다. 실행 단계 access_level, 그리고 automation 범위의 장기 권한 부여입니다.
    • 장기 권한 부여는 자동화를 만들거나 편집할 때 생깁니다. 사용자가 "실행 시 확인 불필요"로 쓰기 계열 도구와 리소스 범위를 체크하고, 대화에서와 같은 승인 카드로 승인하면 권한 부여 표에 기록합니다(권한 모델 §2.4). destructive 도구도 미리 권한을 줄 수 있지만 구체적인 리소스 범위(예: 특정 지식베이스)를 반드시 지정해야 하며, 승인 카드에서 쓰기 계열 권한 부여와 따로 나열하고 되돌릴 수 없음을 표시합니다. Always 도구는 미리 권한을 줄 수 없습니다(권한 모델 §2.4).
    • Decide가 ask를 반환하면 평소대로 HITL로 들어가 실행을 일시 중단하며, 만료 시간은 approval_timeout을 씁니다. 실행은 awaiting_approval로 기록하고 사이트 내 알림을 보내며, 사용자는 실행 상세(즉 자동화 세션)에서 처리합니다. 승인 카드에서 "이 세션에서 허용"을 고르면 세션 권한 부여로 기록됩니다. 이후 실행에도 적용하려면 자동화 설정에서 장기 권한 부여를 추가합니다.
    • 하위 작업의 ask는 협업의 기존 승인 전달을 통해 자동화 세션에 표시되며, 규칙은 같습니다.
    • 소유자가 장기 권한 부여를 취소하거나 단계를 낮추면 다음 호출부터 즉시 적용됩니다.
    • 시스템 프롬프트에 자동화 실행 안내를 덧붙입니다: 지금 온라인 사용자가 없음, 트리거 시각과 실행 번호, 완전한 결과물을 반드시 만들 것, 사용자에게 묻지 말 것, 막히면 사실대로 설명할 것. 이 안내는 런타임 알림으로 주입하며 Agent 템플릿에는 쓰지 않습니다.

    5.3 세션 형태

    • per_run: 실행마다 kind = automation 세션을 새로 만들고, 제목은 "자동화 이름 · 트리거 시각"입니다. carry_last_result = true이면 지난 성공 실행의 최종 답변(길이 상한으로 잘라 표시)을 배경 자료로 이번 사용자 메시지에 넣습니다. 협업 하위 인스턴스는 실행 사이에 상속하지 않습니다.
    • persistent: 모든 실행이 같은 세션에 기록되며, 매번 메시지 한 쌍을 덧붙이고 기존 다중 턴 이력과 컨텍스트 압축을 그대로 씁니다. 같은 세션에서의 실행은 기존 세션 수준 상호 배제가 동시 실행을 막습니다. 사용자가 그 세션에서 직접 대화 중이라면 이번 트리거는 overlap_policy에 따라 건너뛰거나 대기합니다. "지난번과 비교" 같은 경우에 적합하지만 컨텍스트가 계속 늘어나므로 양식에서 안내해야 합니다.
    • 두 모드의 세션 모두 일반 세션 목록에 넣지 않으며, 자동화 상세에서 들어갑니다.

    5.4 런타임 변수

    instruction은 다음 변수를 지원하며, 런타임에 치환한 뒤 사용자 메시지로 씁니다.

    • {{now}}: 이번 트리거 시각(자동화 시간대)
    • {{last_run_at}}, {{last_success_at}}: 지난 실행 시각, 지난 성공 시각. 첫 실행이면 비어 있고 설명을 붙임
    • {{run_id}}, {{automation_name}}

    변수는 텍스트 치환만 하며 표현식을 실행하지 않습니다.

    5.5 가드레일

    • 테넌트별 자동화 개수 상한, 전역 동시 실행 상한(협업 하위 작업의 전역 동시성 상한과 따로 셈).
    • 단일 실행의 token, 반복 횟수, 시간 상한. 넘으면 끝내고 기록합니다.
    • 연속 실패가 임계값(기본 3회)에 이르면 자동으로 일시 정지하고 알립니다.
    • 자동화를 삭제할 때는 먼저 진행 중인 실행을 멈춘 뒤 보존 규칙에 따라 정리합니다.

    6. 통합 실행 서비스

    협업 실행기, IM, MCP Server는 지금 각자 "사용자와 어시스턴트 메시지 만들기, 이벤트 스트림과 실시간 실행 표시 연결, 완료·오류 이벤트 감시, DB 저장, 일시 중단 스냅숏 정리"를 구현하고 있습니다. 자동화는 네 번째 백그라운드 호출자입니다. 자동화를 구현할 때 먼저 AgentRunService를 뽑아냅니다.

    • Start(ctx, RunSpec): RunSpec은 세션, 질의, Agent 스냅숏, 실행 모드, 실행 단계, 신원(ActingVia 포함), 승인 위임 훅, 제한을 담습니다. 실행 결과(최종 답변, 산출물, usage, 일시 중단 여부)를 반환합니다.
    • Resume(ctx, prompt): 승인 복구.
    • Interrupt(ctx, session, message): 중지.

    협업 실행기를 먼저 이 서비스로 옮기고, 기존 협업 회귀 테스트로 퇴행이 없음을 확인합니다. IM과 MCP Server의 이전은 이 요구 사항의 범위가 아니며 나중에 따로 할 수 있습니다.

    7. 사이트 내 알림 센터

    초대와 섞지 않는 범용 알림 모델을 새로 추가합니다.

    • notifications: id, tenant_id, user_id, kind, title, body, link, source_type, source_id, read_at, created_at.
    • 첫 유형: automation.succeeded, automation.failed, automation.awaiting_approval, automation.paused.
    • 자동화마다 "성공 시 알림 여부"를 설정할 수 있습니다(기본값 끔, 실패, 승인 대기, 일시 정지 때만 알림). 빈번한 작업이 알림을 도배하지 않게 하기 위해서입니다.
    • 프런트엔드는 상단 바의 종 아이콘에 초대와 알림을 합쳐 보여 줍니다. 실시간 푸시는 우선 폴링으로 하고 나중에 SSE를 연결합니다.

    나중에 IM, Webhook, 이메일을 추가할 때는 알림의 다른 전달 방식으로 확장하며 실행 모델은 바꾸지 않습니다. IM은 먼저 Adapter에 선택적인 능동 전송 인터페이스를 추가해야 합니다. 기존 SendReply는 반드시 받은 메시지를 기반으로 해야 하기 때문입니다.

    8. 인터페이스와 프런트엔드

    API(모두 소유자 또는 스페이스 관리자 권한을 검증):

    • GET/POST /automations, GET/PUT/DELETE /automations/:id
    • POST /automations/:id/pause, /resume, /run(지금 실행)
    • POST /automations/validate-trigger: 유효 여부와 앞으로의 트리거 시각 3개를 반환
    • GET /automations/:id/runs, GET /automation-runs/:id, POST /automation-runs/:id/cancel
    • GET /notifications, POST /notifications/read

    프런트엔드:

    • 자동화 목록: 이름, 트리거 설명, 다음 실행, 최근 상태, 활성화 스위치.
    • 편집 양식: 실행 모델, 작업 프롬프트(변수 안내 포함), 트리거 방식(프리셋 "매일/매주/매월"과 고급 cron), 시간대, 세션 형태, 실행 단계, 장기 권한 부여(실행 시 확인이 필요 없는 쓰기 계열과 destructive 도구, 리소스 범위를 체크. destructive 항목은 따로 묶고 구체적인 리소스를 반드시 골라야 하며 저장할 때 승인 카드를 띄움), 승인 대기 기한, 제한, 알림 옵션.
    • 실행 이력과 상세: 상세는 자동화 세션을 바로 열며, 기존 메시지 흐름, 하위 작업 카드, 승인 카드, 산출물 서랍을 재사용합니다.

    9. 어시스턴트 통합

    operations에 추가: automation.list, automation.get, automation.create, automation.update, automation.pause, automation.resume, automation.run_now, automation.delete.

    • 쓰기 작업은 기존 confirm 승인을 거칩니다. 승인 카드는 사람이 읽을 수 있는 트리거 설명, 앞으로의 트리거 시각 3개, 실행 단계, 만들어질 장기 권한 부여를 보여 줍니다. 장기 권한 부여는 사용자가 승인 카드에서 승인하며, 모델이 대신 줄 수 없습니다.
    • 모델은 자연어를 cron과 시간대로 바꾸고, 서버가 검증합니다. 모델은 소유자를 설정할 수 없으며, 소유자는 현재 사용자로 고정됩니다.
    • 어시스턴트 읽기 전용 단계에서는 나열하고 보는 것만 할 수 있습니다.

    10. 구현 순서

    1. 전제: 권한 모델 1–4단계(Decide 정리, 규칙 수정, 권한 부여 통일, ActingVia와 deferred 모드).
    2. 실행 기반: 두 표와 마이그레이션, AgentRunService 추출과 협업 실행기 이전, 데이터베이스 스케줄러(Redis와 Lite 두 가지 전달), 실행 신원, automation 세션 kind, 두 가지 세션 형태.
    3. 관리와 가시성: API, 목록/양식/실행 이력 페이지, 지금 실행과 중지, 가드레일과 자동 일시 정지.
    4. 알림과 승인 흐름 완결: 알림 센터, 일시 중단된 승인의 알림과 만료 처리.
    5. 어시스턴트 통합: operations와 승인 카드 표시.
    6. 후속: 이벤트 트리거, IM 능동 푸시, 아웃바운드 Webhook, 이메일.

    11. 검수 시나리오

    • 두 인스턴스가 같은 만기 자동화를 동시에 스캔해도 실행 기록은 하나만 생기고 한 번만 실행된다.
    • Lite를 재시작하면 중단 중 놓친 트리거를 misfire_policy에 따라 처리한다. run_once는 한 번만 보충 실행한다.
    • 시간대가 Asia/Shanghai인 "매일 9:00"은 UTC 서버에서 베이징 시간 기준으로 트리거된다. 서머타임이 있는 시간대에서도 트리거 시각이 정확하다.
    • overlap_policy = skip일 때 이전 실행이 끝나지 않았으면 이번 실행은 skipped로 기록된다.
    • 소유자가 워크스페이스에서 제외되면 다음 실행은 실패하고, 자동화는 일시 정지되며 알림이 간다. 이전 권한으로 실행하지 않는다.
    • 어시스턴트를 쓸 수 없으면 실행이 실패하고 명확한 이유를 준다. 위임 대상을 쓸 수 없으면 어시스턴트가 구체적인 장애를 보고한다.
    • 장기 권한 부여에 해당하는 쓰기 계열 도구는 승인 카드를 띄우지 않는다. 해당하지 않으면 일시 중단하고 알리며, 승인 후 원래 턴부터 이어 가고 한 번만 실행한다. approval_timeout을 넘기면 실행이 실패하고, 늦게 온 승인으로는 복구되지 않는다.
    • destructive 도구를 설정에서 미리 권한 부여하지 않았다면 실행 때마다 일시 중단하고 묻고, 승인 카드에 "앞으로 모두 허용"이 없다. 설정에서 지식베이스 X에 미리 권한을 주면 X의 문서 삭제는 바로 실행되고, 다른 지식베이스의 문서 삭제는 여전히 일시 중단하고 묻는다.
    • Always 도구(관리자가 매번 승인을 요구한 MCP, 스킬 설치)는 설정에서 체크할 수 없고, 실행 때마다 일시 중단하고 묻는다.
    • 장기 권한 부여를 취소하면 다음 실행에서 같은 호출이 다시 일시 중단하고 묻는다.
    • 자동화 실행 중 spawn_agent로 하위 작업을 만들면 하위 작업은 이번 실행의 권한 부여를 상속하고, 단계는 부모 작업을 넘지 않으며, 결과는 이번 실행에 모인다.
    • 감사 로그에서 자동화가 실행한 쓰기 작업에는 ActingVia = automation:<id>가 붙는다.
    • 실행 중 프로세스가 죽으면 실행은 needs_attention이 되고, 이미 일어난 도구 호출을 재실행하지 않는다.
    • ask_user는 쓸 수 없다. OAuth가 필요한 MCP는 멈춰 있지 않고 오류를 반환한다.
    • 시간이나 token 상한을 넘으면 실행이 끝나고 실패로 기록된다. 연속 3회 실패하면 자동으로 일시 정지된다.
    • per_run과 carry_last_result는 지난 결과를 올바르게 주입한다. persistent 모드에서는 여러 번의 실행이 같은 세션에 기록되고 이력이 이어진다.
    • 자동화 세션은 일반 세션 목록에 나타나지 않고, 다른 사용자는 접근할 수 없다.
    • 어시스턴트가 자동화를 만들 때 보여 주는 트리거 시각이 서버 계산과 같다. 읽기 전용 단계에서는 만들 수 없다.
    • 협업 실행기를 AgentRunService로 옮긴 뒤 기존 협업, 복구, 승인 회귀 테스트가 모두 통과한다.

    12. 미정 문제

    • 공유 스페이스에서 스페이스 관리자가 멤버가 만든 자동화를 보거나 비활성화할 수 있는가.
    • persistent 세션이 오래 실행된 뒤의 컨텍스트 압축 전략이 일반 세션보다 더 공격적이어야 하는가.
    • 알림 센터를 워크스페이스별로 격리해 보여 줘야 하는가.
    • 테넌트별 개수와 동시성 상한의 기본값, 그리고 시스템 설정 페이지에 둘지 여부.

    13. 구현 설명

    첫 버전은 §10의 1–4단계에 따라 구현했으며, 다음 몇 가지가 설계와 다릅니다.

    • AgentRunService를 뽑아내지 않았습니다. 실행기 automation_runner.go가 협업 실행기의 방식을 따라 메시지 쌍 만들기, 이벤트 스트림 연결, 완료와 오류 감시, DB 저장을 직접 처리합니다. 협업 실행기는 건드리지 않았습니다. 네 백그라운드 호출자의 통합은 별도 리팩터링으로 남깁니다.
    • 소유자만 접근할 수 있습니다. 인터페이스는 소유자로 필터링하며, 스페이스 관리자는 다른 사람의 자동화를 보거나 비활성화할 수 없습니다(§12의 첫 항목은 여전히 미정). API Key, IM 사용자, 자동화 실행 내부(ActingVia가 비어 있지 않음)에서는 자동화를 만들거나 관리할 수 없습니다.
    • 스케줄링은 데이터베이스만 씁니다. 모든 인스턴스가 15초마다 만기 레코드를 스캔하고 version CAS로 가져가며, Redis 전달은 거치지 않습니다. Lite와 다중 인스턴스 배포가 같은 로직을 씁니다.
    • 승인 만료는 스케줄러가 대조합니다. HITL Broker의 만료 시각은 바꾸지 않습니다. 승인 대기가 approval_timeout_minutes를 넘으면 실행을 실패로 기록하고 프롬프트를 닫습니다. Broker가 일시 중단된 프롬프트를 더 일찍 회수하면 실행은 마찬가지로 실패로 기록되며, 이유는 프롬프트가 닫힌 이유를 씁니다.
    • 장기 권한 부여는 과거 승인에서 승격합니다. 설정 페이지는 도구 목록 체크를 제공하지 않고, 이 자동화 실행 중 승인을 요청했지만 아직 권한을 주지 않은 쓰기 계열과 destructive 호출을 나열해 소유자가 하나씩 확인하게 합니다. 권한 부여는 Agent 설정과 소유자 역할(AutomationBinding)에 묶이며, 바뀌면 무효로 표시합니다. 매번 승인이 필요한 호출은 후보에 나타나지 않습니다.
    • 제한은 시간뿐입니다. limits에는 지금 max_duration_minutes(기본 30, 상한 240, 승인 대기 시간 제외)만 있습니다. token 상한은 따로 구현하지 않았으며, Agent 자체의 max_iterations가 제약합니다.
    • persistent 세션이 바쁘면 건너뜁니다. 장기 세션에 아직 진행 중인 실행(사용자가 그 세션에서 직접 대화 중인 경우 포함)이 있으면 이번 실행은 skipped로 기록됩니다.
    • 실행 진입점은 내장 어시스턴트로 고정(builtin-weknora-assistant)했으며, 자동화 표와 생성·수정 인터페이스는 agent_id를 제공하지 않습니다. 양식과 대화 생성이 같은 규칙을 쓰며, 프롬프트로 어시스턴트에게 다른 에이전트에 위임하라고 요구할 수 있습니다.
    • 프런트엔드 진입점: 사이드바 "자동화" 페이지(/platform/automations). 실행 상세는 자동화 세션을 바로 열고, 알림 링크 /platform/automations/:id?run=:runId는 해당 실행을 엽니다. 오른쪽 위의 종 아이콘이 초대와 알림을 합쳐 보여 주며 60초마다 폴링합니다.
    • 어시스턴트 승인 카드는 여전히 범용 operation 파라미터 표시이며, 트리거 설명과 앞으로의 트리거 시각을 따로 렌더링하지 않습니다. 어시스턴트가 먼저 automation.validate_trigger를 호출하고 대화에서 사용자에게 알려야 합니다.
