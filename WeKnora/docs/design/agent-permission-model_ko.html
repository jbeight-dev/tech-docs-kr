    Agent 실행 권한 모델

    상태: 백엔드 1–4단계 구현 완료. automation 범위와 ActingVia는 준비됐으며 자동화 요구 사항 연동을 기다리는 중. MCP 위험 관리 화면은 보류(§6). 날짜: 2026-10-19. 구현과 원래 설계의 차이는 §7을 참고하십시오.

    이 문서는 Agent 런타임에서 "어떤 동작은 바로 실행하고, 어떤 동작은 사용자 확인을 받고, 어떤 동작은 거부하는가"에 대한 판단을 통일합니다. 어시스턴트와 멀티 Agent 협업이 아직 출시 전이므로 이 기회에 규칙을 정리합니다. 자동화(agent-automation.md)는 이 모델 위에 바로 세우며, 자체 권한 개념을 따로 두지 않습니다.

    0. 확정된 결정

    문제결정
    단계 적용 범위내장 어시스턴트 전용에서 모든 smart-reasoning Agent로 확장
    일반 Agent 기본 단계auto_write와 동등. MCP는 여전히 테넌트의 도구별 스위치로만 승인하며, #1173에서 이미 출시된 동작을 유지
    어시스턴트 기본 단계confirm 유지. 워크스페이스 상한의 제약을 받음
    문서 구성이 문서를 독립적으로 관리하고, 자동화 문서는 이 문서를 참조

    1. 현황

    "이 도구 호출에서 사용자를 기다려야 하는가"를 지금은 여러 곳이 각자 판단합니다.

    위치대상판단 근거
    operations.Access.NeedsApprovalFor어시스턴트 operations 목록위험 등급 + 어시스턴트 단계
    tools.ConfirmedTool어시스턴트가 직접 호출하는 Wiki 쓰기 도구위와 같음. 비대화형 런타임에서는 바로 거부
    approval.Gate.NeedsApprovalMCP 도구테넌트 도구별 MCPToolApproval.RequireApproval. 협업 위임 시 덮어씀
    hitl.Delegation.RequireApproval협업 하위 작업Access != auto_write이면 하위 작업의 모든 MCP 호출에 승인 필요
    AgentCollaboration의 도구 필터(agent_collaboration.go)템플릿 하위 작업의 다른 쓰기 도구auto_write가 아니면 바로 오류를 내고 "부모 대화에서 승인해야 함"을 안내
    Interactive, Suspendable, WithUnattendedRun, WithMCPOAuthNonInteractive실행 모드독립된 표시 네 개를 각 도구가 따로 해석

    그 결과 생기는 문제:

    1. 단계가 내장 어시스턴트에만 적용됩니다. GrantsOperationCatalog는 BuiltinWeKnoraAssistantID에 대해서만 성립합니다. 일반 Agent에는 단계 개념이 없습니다.
    2. 읽기 전용 단계가 MCP를 다루지 않습니다. read_only는 operations 쓰기 작업, Wiki 쓰기 가능 범위, fill_page만 비웁니다. MCP 쓰기 도구는 여전히 테넌트 스위치만 봅니다.
    3. 부모와 자식의 규칙이 다릅니다. 같은 사용자, 같은 단계, 같은 MCP 도구라도 부모 작업은 바로 실행하고 하위 작업은 읽기 전용 조회까지 매번 승인을 받아야 할 수 있습니다.
    4. MCP에 위험 등급이 없습니다. 불리언 스위치만 있어 confirm과 auto_write가 MCP에는 의미가 없습니다. MCP 규격의 readOnlyHint / destructiveHint 애너테이션도 쓰지 않습니다(mark3labs/mcp-go는 이미 Tool.Annotations를 파싱합니다).
    5. 권한 부여 기억이 한 가지뿐입니다. AllowInSession은 Grant가 있는 Wiki 쓰기 도구에만 쓰입니다. MCP 승인은 기억할 수 없고, 하위 작업이 상속하지 않으며, 오래 유지되는 권한 부여도 없습니다.
    6. 신원으로 온라인 Web 사용자만 인정합니다. operations는 OperationIdentityFromContext에 의존합니다. 백그라운드 실행은 온라인처럼 보이는 Web 사용자를 만들어 낼 수밖에 없어 감사에서 구분할 수 없습니다.

    2. 모델

    권한은 세 계층으로 나눕니다. 앞의 두 계층은 현재대로 두고 세 번째 계층을 통일합니다.

    1. 기능 면: Agent가 볼 수 있는 도구. allowed_tools, MCP 활성화 스위치, Skills, 내장 어시스턴트 전용 기능. 변경 없음.
    2. 리소스 권한: 이 사용자가 건드릴 수 있는 리소스. 라우팅 계층 RBAC, 지식베이스 쓰기 가능 범위, 공유 Agent 읽기 전용. 변경 없으며, 실행과 복구 때마다 실제 사용자로 다시 검증합니다.
    3. 실행 정책: 사용 가능하고 리소스 권한도 있는 동작을 지금 확인 없이 바로 실행할 수 있는가. 유일한 결정 함수가 답합니다.
    Decide(ctx, Action) Decision // allow | ask | deny，附原因与命中的授权

    모든 도구 진입점(operations, 내장 쓰기 도구, MCP, 위임 하위 작업)이 이 함수를 호출합니다. 이 함수 말고는 흩어진 승인 판단이 더 이상 없습니다.

    2.1 동작 기술

    type Action struct {
    Kind     string // operation | builtin | mcp
    ID       string // operation ID、工具名，或 mcp:<service_id>/<tool_name>
    Risk     Risk   // read | probe | write | destructive
    Always   bool   // 每次都确认，授权不可豁免
    Resource string // 规范化的资源范围，例如 knowledge_base:<id,...>；无则为空
    Summary  string // 审批卡展示
}

    권한 부여 키 = Kind + ID + Resource이며, 기존 권한 부여와 맞춰 보는 데 씁니다.

    위험의 출처:

    동작 유형위험Always
    operations목록의 Risk목록의 AlwaysConfirm
    내장 쓰기 도구기존 assistantWriteToolRisk를 모든 Agent의 쓰기 도구로 확장아니요
    MCP 도구관리자가 도구별로 설정. 설정이 없으면 애너테이션에서 가져옴: readOnlyHint=true → read, 나머지 → writeRequireApproval=true를 Always로 매핑

    MCP 애너테이션은 외부 서비스에서 오므로 기본값으로만 쓰며, 규칙은 다음과 같습니다.

    • 관리자의 명시적 설정(mcp_tool_approvals.risk)이 우선하며, destructive는 관리자만 설정할 수 있습니다. destructiveHint는 채택하지 않습니다. write는 이미 단계에 따라 확인을 받으므로, 외부 서비스가 destructive를 선언하면 승인이 더 엄격해질 뿐 그 선언을 믿을 수 있는지는 구분할 수 없습니다. 그래서 판단을 관리자에게 맡깁니다.
    • 명시적 설정이 없으면 유효 위험은 "이번에 선언한 위험"과 "지금까지 관찰된 최고 위험"(observed_risk) 중 높은 쪽입니다. observed_risk는 올라가기만 하고 내려가지 않습니다. 서비스가 애너테이션을 read에서 write로 바꾸면 즉시 적용되지만, write에서 read로 되돌리면 적용되지 않으며 관리자가 명시적으로 read로 설정해야 합니다. 이 방식은 원래 설계의 "강등은 관리자 확인 필요" 절차를 대체하며, 별도의 확인 대기 상태가 필요 없습니다.

    2.2 단계

    AssistantAccessLevel을 실행 단계로 이름을 바꾸고(불필요한 변경을 피하려고 타입 이름은 유지할 수 있습니다), 모든 smart-reasoning Agent에 적용합니다.

    단계read / probewritedestructive 또는 Always
    read_onlyallow등록하지 않음등록하지 않음
    confirmallow권한 부여에 해당하면 allow, 아니면 askask
    auto_writeallowallowask

    유효 단계 = min(사용자의 이번 선택, Agent 상한, 워크스페이스 상한).

    • 내장 어시스턴트: 사용자가 패널에서 고른 단계를 그대로 쓰며, 기본값은 confirm입니다.
    • 일반 Agent: Agent 설정에 실행 단계 상한을 새로 두며, 기본값은 auto_write입니다. 사용자가 고르지 않으면 이 상한을 씁니다. 따라서 설정을 바꾸지 않았다면 일반 Agent의 MCP는 여전히 RequireApproval=true(즉 Always)일 때만 승인을 받으며, 현재와 같습니다.
    • read_only는 등록 단계에서 MCP 쓰기 도구와 Wiki 쓰기 도구를 포함한 쓰기 도구를 제거합니다. 그래도 Decide에 도달하는 쓰기 작업(예: 등록 후 위험이 바뀐 경우)은 ask가 아니라 deny를 반환합니다.
    • 각 Agent의 상한은 CustomAgentConfig.AccessLevel(빈 값이면 auto_write)에 저장하며 편집 화면에서 설정할 수 있습니다. 내장 어시스턴트는 워크스페이스의 MaxAccessLevel을 씁니다.

    모드출처ask 처리ask_userMCP OAuth
    attendedWeb 대화, 어시스턴트 패널승인 카드를 띄움. 일시 중단할 수 있고 새로 고친 뒤 복구사용 가능권한 부여 카드를 띄움
    deferred자동화실행을 일시 중단하고 알림을 씀. 사용자가 세션에서 처리하면 복구등록하지 않음실패하고 이유를 설명

    기존 IM 채널은 unattended를 유지합니다. 나중에 IM이 승인 카드를 지원하면 따로 전환합니다.

    2.4 권한 부여

    지금처럼 agent_prompts의 AllowInSession 응답에 기대는 암묵적 조회 대신 하나의 표로 통일합니다.

    필드설명
    id, tenant_id, user_id권한 부여는 사용자 본인에게 속함. user_id는 Principal.StorageID()
    grant_key권한 부여 키, 아래 참고
    label승인 카드에 표시하는 권한 부여 범위. 조회·취소 화면에 사용
    scopesession / automation
    scope_id루트 세션 ID 또는 자동화 ID
    prompt_id이 권한 부여를 만든 승인
    binding_hashautomation만: 권한 부여 전제의 해시. 아래 무효화 규칙 참고
    expires_at, revoked_at, created_at, updated_at, last_used_at

    표 이름은 agent_grants이고 고유 키는 (tenant_id, user_id, scope, scope_id, grant_key)입니다. 같은 권한 부여를 다시 승인하면 그 행을 재사용하고 revoked_at을 비웁니다. 권한 부여 키:

    • MCP 쓰기 도구: mcp:<service_id>/<tool_name>#<输入 schema 的 sha256 前 6 字节>(입력 schema sha256의 앞 6바이트). 서비스가 도구 파라미터를 바꾸면 키도 바뀌므로 이전 권한 부여는 자연스럽게 더 이상 맞지 않습니다.
    • Wiki 등 내장 쓰기 도구: 도구의 기존 Grant(도구 이름 + 정규화한 지식베이스 범위)를 그대로 씁니다.

    규칙:

    • 면제할 수 있는 범위는 범위(scope)별로 다르며, Always는 어떤 범위에서도 면제할 수 없습니다.

      위험sessionautomation
      write가능. 실행 중 승인 카드에서 "이 세션에서 허용"을 체크가능. 자동화를 만들거나 편집할 때 미리 권한 부여
      destructive불가가능. 자동화를 만들거나 편집할 때 미리 권한 부여하는 경우만, 아래 참고
      모든 위험이면서 Always불가불가
    • destructive의 자동화 권한 부여는 "매일 밤 만료된 문서 정리"처럼 삭제가 반드시 들어가는 작업을 위한 것입니다. 이것이 없으면 이런 자동화는 실행할 때마다 일시 중단됩니다. 제약은 다음과 같습니다(아직 구현하지 않았으며 자동화 요구 사항과 함께 구현합니다. §4 참고).
      • 자동화의 설정 양식에서 항목별로 체크하고 승인 카드로 승인해야만 합니다. 실행 중 승인 카드에는 "앞으로 모두 허용"이 없으며, 모델이 대신 권한을 줄 수도 없습니다.
      • 반드시 리소스 범위를 지정해야 합니다. 리소스가 있는 동작(예: 지식베이스 문서 삭제)은 구체적인 지식베이스 단위로 권한을 주며 "모든 지식베이스"에 권한을 줄 수 없습니다. MCP 도구에는 리소스 개념이 없으므로 도구와 파라미터 schema 단위로 권한을 줍니다.
      • 승인 카드는 destructive 권한 부여를 write 권한 부여와 따로 나열하고 "되돌릴 수 없음"을 표시하며, 따로 확인을 받아야 합니다.
      • 권한 부여 표에 risk 열을 추가해 승인 당시 동작의 위험을 기록합니다. 권한 부여는 그 위험 이하의 호출만 다룹니다. 도구가 destructive로 올라갔다고 write 권한 부여가 계속 유효하지는 않습니다.
      • 무효화 규칙은 다른 automation 권한 부여와 같습니다(§2.4 아래). 취소, 만료, 무효화된 뒤에는 다음 실행이 해당 호출에서 일시 중단하고 묻습니다.
      • 결정 로그와 감사는 평소대로 기록합니다. destructive 권한 부여에 해당한 호출은 사후 조사를 위해 agent_granted_destructive를 따로 기록합니다.
    • session: 승인 카드의 "이 세션에서 허용"이며, MCP 쓰기 도구로 확장합니다. scope_id는 항상 루트 세션 ID입니다. 루트 작업과 위임 하위 작업에서 승인한 권한 부여 모두 루트 세션 이름으로 기록하고, 하위 작업은 판단할 때 루트 세션으로 맞춰 봅니다. 권한 부여는 루트 세션과 함께 끝나며, 사용자가 세션을 삭제하면 함께 정리합니다. 협업 전용 범위를 따로 두지 않는 이유는, 사용자가 새 메시지를 보낼 때마다 새 협업 그룹이 만들어지고 이전 그룹의 유휴 하위 인스턴스를 상속하기 때문입니다. 권한 부여가 협업 그룹을 따라가면 같은 대화의 매 턴마다 같은 질문을 반복하게 됩니다.
    • automation: 자동화를 만들거나 편집할 때 사용자가 같은 종류의 승인 카드로 장기 권한 부여 한 묶음을 승인합니다. 자동화 실행 시에는 이 범위와 이번 실행 세션에서 새로 생긴 권한 부여만 인정합니다. 연동 시 주의할 점: 현재 승인 게이트웨이는 실행 컨텍스트의 GrantScope 하나만으로 조회하고 기록합니다. 자동화 진입점이 범위를 바로 automation으로 설정하면 실행 중 체크한 "이 세션에서 허용"이 장기 권한 부여로 기록됩니다. 게이트웨이가 automation 범위와 이번 실행 세션의 session 범위를 함께 조회하게 하고, 실행 중 생긴 권한 부여는 후자에만 쓰며, 장기 권한 부여는 설정 양식만 쓰게 해야 합니다.
    • 맞춰 볼 때는 사용자, 테넌트, 범위, 만료 여부, 취소 여부를 함께 검증합니다. 리소스 범위는 정확히 일치해야 하며 접두사로 추론하지 않습니다.
    • 권한 부여는 "물어볼지 말지"만 결정하며 기능 면이나 리소스 권한을 넓히지 않습니다. 도구가 등록되지 않았거나 리소스에 쓰기 권한이 없으면 권한 부여는 효력이 없습니다.
    • 조회와 취소 인터페이스를 제공합니다. 취소는 이후 호출에 즉시 적용되며 이미 실행한 호출에는 영향을 주지 않습니다.

    automation 권한 부여는 시간에 따라 주기적으로 만료되지 않고(생성 시 만료 시각을 고를 수 있으며 기본값은 만료 없음), 권한 부여의 전제가 바뀌면 무효화됩니다.

    • 실행 Agent 템플릿의 도구 집합, MCP 서비스, 프롬프트가 바뀐 경우. 권한 부여는 binding_hash(이 핵심 설정들의 해시)를 저장하며, 런타임에 해시가 다르면 무효로 봅니다.
    • MCP 도구의 위험이 올라가거나 도구 파라미터 schema hash가 바뀐 경우(스냅숏 복구의 schema hash를 재사용).
    • 소유자의 역할이 낮아지거나, 단계 상한이 낮아지거나, 권한 부여와 관련된 리소스의 쓰기 권한이 회수된 경우.
    • 자동화가 90일 연속 실행되지 않은 경우.

    무효화된 권한 부여는 삭제하지 않습니다. 승인은 ask로 바뀌고 이유가 붙으며, 자동화 실행은 일시 중단하고 알림을 보냅니다. 사용자가 다시 승인하면 binding_hash를 갱신합니다. 구현 방식:

    • binding_hash는 types.AutomationBinding{AgentID, Tools, MCPServiceIDs, SystemPrompt, OwnerRole, Ceiling}.Hash()로 계산하며 도구와 서비스의 순서와 무관합니다. 자동화 실행 진입점이 계산해 실행 컨텍스트의 GrantScope에 넣습니다.
    • AgentGrant.LapseAt은 무효화 이유를 알려 줍니다: changed(binding 불일치), expired, idle(90일 미사용), revoked. 앞의 세 가지는 승인 요청의 grant_lapsed 필드로 승인 카드에 전달해 설명을 표시합니다. 사용자가 직접 취소한 경우에는 안내하지 않습니다.
    • MCP 도구가 Always로 설정되면 더 이상 권한을 줄 수 없습니다. 위험이 destructive로 올라가면 session 권한 부여와 write 기준으로 승인한 automation 권한 부여 모두 더 이상 유효하지 않습니다(지금은 "destructive는 권한 부여 불가"가 이를 보장하며, destructive 자동화 권한 부여를 구현하면 권한 부여의 risk 열이 보장합니다). schema 변경은 권한 부여 키로 무효화됩니다.
    • 리소스 쓰기 권한 회수는 따로 처리할 필요가 없습니다. 권한 부여는 물어볼지 말지만 결정하며, 라우팅 계층이 여전히 실제 사용자로 쓰기 권한을 검증합니다.

    인터페이스:

    • GET /api/v1/agent/grants?session_id=<根会话 ID>: 현재 사용자가 그 세션에서 가진 유효한 권한 부여를 나열합니다.
    • DELETE /api/v1/agent/grants/:id: 현재 사용자의 권한 부여 하나를 취소합니다. 본인만 취소할 수 있습니다.
    • 프런트엔드는 세션 제목의 "더 보기" 메뉴에서 "허용한 작업" 목록과 취소 버튼을 제공합니다.
    • 세션을 삭제하면 그 세션의 session 범위 권한 부여를 함께 정리합니다.

    2.5 위임

    • Delegation.RequireApproval의 일괄 규칙과 협업 도구 필터의 단계 분기를 삭제합니다. 하위 작업은 부모 작업의 유효 단계와 루트 세션의 session 권한 부여로 같은 Decide를 호출합니다.
    • 템플릿 하위 작업의 단계 = min(부모 작업의 유효 단계, 템플릿 Agent의 단계 상한). 어시스턴트가 시작했거나(AssistantParent) 어시스턴트 설정을 상속한 하위 작업은 워크스페이스 어시스턴트 상한의 제약도 받습니다.
    • 템플릿 하위 작업의 쓰기 도구도 ConfirmedTool로 감쌉니다. 따라서 읽기 전용 단계에서 쓰기 호출은 오류로 하위 작업을 중단하지 않고, 거부 이유를 도구 결과로 돌려줍니다.
    • 권한 부여 범위는 실행 컨텍스트(types.WithGrantScope)에 두며, 하위 작업은 부모 작업의 루트 세션 범위를 상속합니다. 최상위 실행에서 설정되지 않았으면 요청의 GrantSessionID를, 그것도 없으면 이 세션을 씁니다.
    • 하위 작업의 ask는 기존 메커니즘대로 부모 세션으로 전달해 표시하며, 승인 귀속, 복구, 취소는 바뀌지 않습니다.
    • 이미 위임한 작업에 대한 부모 작업의 MCP 중복 방지 검사(delegated_call_in_progress)는 유지하며, 이 모델과 무관합니다.

    2.6 신원

    Principal에 선택 필드 ActingVia(예: automation:<id>)를 추가합니다.

    • 라우팅 계층은 여전히 해당 Web 사용자로 인증하며, operations를 쓸 수 있습니다.
    • StorageID()는 ActingVia를 포함하지 않습니다. 따라서 권한 부여, 세션 소유, HITL의 UserID는 모두 여전히 그 사용자에게 속하며, 사용자 본인이 일시 중단된 승인에 답할 수 있습니다.
    • operations를 디스패치할 때 AuditAgentAction.ActingVia를 요청과 함께 넘깁니다(디스패치가 신원을 다시 만들므로 원래 Principal에 기댈 수 없습니다). types.ActingViaFromContext는 먼저 AuditAgentAction에서, 그다음 Principal에서 값을 가져옵니다.
    • 지식베이스 활동 감사는 details.agent_acting_via에 이를 기록해 본인 조작과 대리 실행을 구분합니다.

    2.7 감사

    Decide의 read가 아닌 결과는 매번 policy.Record가 구조화 로그(agent policy decision)로 씁니다. 필드는 agent_action, agent_risk, agent_always, agent_level, agent_mode, agent_verdict이고, 대리 실행이면 agent_acting_via가 추가됩니다. 권한 부여 적중과 승인 생성은 승인 게이트웨이가 따로 로그를 남깁니다. 쓰기 작업을 실행하면 기존 감사 로그대로 기록합니다.

    4. 구현 순서

    1. 동작을 바꾸지 않는 정리(완료, b2719331e): internal/agent/policy를 새로 추가했습니다. Risk(operations.Risk는 그 별칭으로 바꿈), Action, Rules, Decide, Offered를 포함합니다. operations 승인, ConfirmedTool, MCP Gate.NeedsApproval, 협업 위임의 RequireApproval과 하위 작업 도구 필터 모두 Decide를 호출하도록 바꿨으며, 규칙은 현재 동작을 그대로 재현합니다. MCP는 일단 auto_write 단계에 Always(테넌트 스위치)와 ForceAsk(위임)를 더해 판단합니다. read_only에서 여전히 도달하는 쓰기 작업은 deny가 아니라 ask를 반환합니다. 기존 테스트는 단언을 고치지 않고 모두 통과했습니다.
    2. 규칙 수정과 실행 모드(완료, 실행 모드 e97cd5bfb, 나머지 a65b2fde6): MCP 위험 등급과 애너테이션 기본값, read_only가 MCP를 포함(등록 단계에서 제거, Decide에 deny 추가), 위임 일괄 규칙 삭제, 일반 Agent 단계 상한 설정, 실행 모드 통합. 실행 모드를 1단계에서 이곳으로 옮긴 이유는 통합하면 기존 동작이 반드시 바뀌기 때문입니다. 비대화형 실행에서 operations와 ConfirmedTool은 바로 거부하는데, MCP 승인은 승인 카드를 보내고 타임아웃까지 기다립니다(IM 채널이 그렇습니다). WithUnattendedRun은 현재 프로덕션 호출자가 없습니다.
    3. 권한 부여 통일(완료, a249d8a2d): 권한 부여 표, 루트 세션으로 맞춰 보는 session 범위, 승인 카드 "이 세션에서 허용"의 MCP 확장, 조회·취소 화면.
    4. 신원과 자동화 연동(완료, 2e875cca4): ActingVia, 결정 로그, automation 범위의 binding과 무효화 이유. deferred 모드는 2단계에서 구현했습니다. 자동화 요구 사항은 실행 진입점에서 모드, GrantScope, Principal.ActingVia만 설정하면 됩니다.
    5. 자동화 권한 부여 연동: 백엔드는 완료했습니다. 권한 부여 표의 risk 열, policy.Pregrantable(write와 destructive, Always 아님)이 권한 부여 키를 만들지 결정하고, policy.Grantable(write만)이 승인 카드에 "이 세션에서 허용"을 제공할지 결정하며, policy.Covers가 권한 부여가 더 높은 위험의 호출을 다루지 않도록 보장합니다. 게이트웨이는 먼저 실행의 GrantScope를, 다음으로 types.WithStandingGrantScope가 설정한 장기 범위를 조회하며, 실행 중 승인은 전자에만 씁니다. 자동화 설정 양식이 장기 권한 부여를 쓰는 인터페이스와 화면은 자동화 요구 사항과 함께 구현합니다.

    5. 검수 시나리오

    • 1단계를 마친 뒤 기존의 모든 승인 관련 테스트가 단언을 고치지 않고 통과한다.
    • 어시스턴트 read_only: MCP 쓰기 도구, Wiki 쓰기 도구, operations 쓰기 작업이 도구 목록에 나타나지 않는다. MCP 읽기 전용 도구는 쓸 수 있다.
    • 어시스턴트 confirm: 쓰기 계열 MCP는 승인 카드를 띄운다. "이 세션에서 허용"을 고르면 같은 세션, 같은 도구, 같은 리소스 범위에서는 다시 묻지 않고, 리소스 범위가 바뀌면 다시 묻는다. destructive는 매번 묻는다.
    • 설정을 바꾸지 않은 일반 Agent: MCP 승인 동작이 개편 전과 완전히 같다.
    • 협업: 부모 작업이 "이 세션에서 허용"을 승인하면 하위 작업이 같은 도구, 같은 범위를 호출할 때 카드를 띄우지 않는다. 하위 작업에서 승인한 권한 부여는 부모 작업과 형제 작업에도 똑같이 적용된다. 사용자가 다음 메시지를 보낸 뒤(새 협업 그룹) 이어서 실행되는 하위 작업도 이 권한 부여를 그대로 쓴다. 하위 작업이 읽기 전용 MCP를 호출하면 카드를 띄우지 않는다. 템플릿 하위 작업의 단계는 부모 작업을 넘지 않는다.
    • 자동화 권한 부여: 실행 템플릿의 도구 목록을 다른 사람이 바꾸면 다음 실행이 해당 호출에서 일시 중단하고 무효화 이유를 설명한다. 다시 승인하면 복구된다. 소유자가 강등되거나 리소스 쓰기 권한이 회수돼도 마찬가지로 무효화된다.
    • Always 도구(RequireApproval=true인 MCP, 스킬 설치 포함)는 어떤 단계와 권한 부여에서도 묻는다.
    • destructive: 대화에서는 매번 묻고 승인 카드에 "이 세션에서 허용"이 없다. 자동화에서는 설정에서 구체적인 리소스에 대해 미리 승인한 경우에만 바로 실행하며, 다른 지식베이스로 바뀌면 여전히 일시 중단하고 묻는다. 도구가 write에서 destructive로 올라가면 기존 write 권한 부여는 더 이상 유효하지 않다.
    • MCP 서비스가 도구 애너테이션을 read에서 write로 바꾸면 다음 호출부터 즉시 write로 처리한다. 반대 방향의 변경은 적용되지 않으며 관리자가 명시적으로 read로 설정해야 한다.
    • unattended 모드에서 ask는 바로 거부되고 모델에 이유를 알린다. deferred 모드에서는 일시 중단하고 알림을 만든다.
    • 권한 부여를 취소하면 다음 호출에서 다시 묻는다. 이미 실행한 호출은 영향을 받지 않는다.
    • 감사 로그에서 사용자 본인의 실행과 ActingVia의 실행을 구분할 수 있다.
    • 권한 부여로 등록되지 않은 도구가 나타나게 할 수 없고, 쓰기 권한이 없는 지식베이스를 쓰기 가능하게 만들 수도 없다.

    6. 미정 문제

    • MCP 도구 위험 관리 화면을 기존 MCP 서비스의 도구 목록(McpToolsList.vue)에 둘지, 별도의 정책 페이지에 둘지. 보류 중입니다. 백엔드는 이미 지원합니다. PUT /api/v1/mcp-services/:id/tool-approvals/:tool_name은 risk를 받고(빈 문자열은 애너테이션 추론으로 되돌림을 뜻함), GET은 명시적으로 설정한 risk와 observed_risk를 반환합니다. 화면은 나중에 정합니다.

    결정된 사항: 협업 범위를 두지 않고 권한 부여는 루트 세션으로 맞춰 봅니다(§2.4). automation 권한 부여는 전제가 바뀌면 무효화되며 시간에 따라 주기적으로 재확인하지 않습니다(§2.4). "모두 바로 통과" 단계를 새로 두지 않습니다. auto_write가 최고 단계이고, destructive는 자동화 범위에서 구체적인 리소스 단위로만 미리 권한을 줄 수 있으며, Always는 절대 면제하지 않습니다(§2.4). 이유: Always는 구체적인 도구에 대한 관리자의 결정이므로 사용자 단계가 이를 덮어써서는 안 됩니다. Agent가 읽는 지식베이스, 웹 페이지, MCP 결과에는 모두 주입된 지시가 들어 있을 수 있으므로, 전부 여는 단계를 두면 그런 내용이 되돌릴 수 없는 작업을 바로 일으킬 수 있습니다. 완화가 필요한 개별 MCP 도구는 관리자가 위험을 write로 조정하면 됩니다.

    7. 구현과 원래 설계의 차이

    • MCP 애너테이션은 readOnlyHint만 채택합니다. destructive는 관리자만 설정할 수 있습니다. 강등 확인은 observed_risk가 올라가기만 하고 내려가지 않는 방식으로 바꿨습니다(§2.1).
    • read_only에서 여전히 도달하는 쓰기 작업은 deny를 반환합니다(§2.2).
    • Decide는 순수 함수 Decide(Action, Rules) Verdict로 유지하며, Action은 Risk와 Always만 담습니다. 권한 부여 키는 Action에 넣지 않고 각 도구가 만들어 승인 게이트웨이에서 맞춰 봅니다. 권한 부여를 실행 모드 검사보다 먼저 맞춰 보므로 unattended와 deferred 실행도 기존 권한 부여를 인정합니다.
    • 권한 부여 표의 필드 이름은 grant_key, prompt_id이며, label, updated_at이 추가로 있습니다(§2.4).
    • 예전 AllowInSession 데이터는 호환하지 않습니다(§3).
    • 템플릿 하위 작업의 쓰기 도구는 감싸서 실행하도록 바꿨으며, 읽기 전용 단계의 거부는 도구 결과로 반환합니다(§2.5).
